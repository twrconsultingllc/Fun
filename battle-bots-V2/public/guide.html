01Quick start

The app is a static front end in public/ plus one serverless function in api/. The function is the only thing that holds your API key.

  1. Set GEMINI_API_KEY in the environment the function runs in (a .env file locally, project settings on Vercel). The browser never sees it.
  2. From battle-bots-V2/, run npm install, then serve the folder with something that runs the api/ route — vercel dev is what the layout is built for.
  3. Open the page. The model dropdowns fill themselves from a GET /api/get-actions call against Google's live catalog, and the telemetry log prints how many models came back.
  4. Pick a match mode, write a strategy line for each team, then hit Initiate Match.
The plain static server won't do. preview-server.mjs at the repo root serves files only — no /api. Under it the model list comes back empty and every tick logs an error, so the bots just hold their default stance.

02The control panel

Everything is set before the bell. Nothing here is editable mid-match except in the sense that the next tick reads your latest prompt — the panel stays live, so you can rewrite a team's orders while the match runs and the change lands on the following tick.

Readouts

Live AI telemetry keeps the last 14 lines: SENT per tick with each team's model, RECV per bot with its chosen skill and the model's own one-line reasoning, and ERROR for anything that failed. Match stats refresh about twice a second with each bot's equipped weapon, HP, damage out, damage in, accuracy and its most-used skill. Round history keeps the last five completed matches — winner, mode, winning model, winning strategy — in browser storage, so it survives a reload.

03How the AI actually controls the bots

The division of labour is the whole design: the model picks intent every few seconds, the engine executes it every frame. The model never sets a coordinate, never pulls a trigger, and never touches a bot directly.

TICKSnapshotEvery living team's view of the world is frozen at the same instant.

What each team is allowed to see

Every team gets its own snapshot, written from its point of view — there is no shared omniscient state and no peeking at another team's prompt. The payload holds:

  • Arena size, every cover block with its current hit points, and every pickup on the floor with its type and position.
  • For each of your own bots: position, velocity, current speed, HP, shield, weapon, seconds left on the fire cooldown, active skill and its remaining duration, whether a damage or speed boost is running, and how much damage it took since the last tick.
  • For each enemy, per bot: id, team, HP, exact distance, and a true/false line of sight flag computed against real cover.
  • A rolling log of the last 8 things that happened to this team, and the outcome of up to 5 previous matches with the orders that produced them.

Everything else — where an enemy is heading, what skill an enemy just picked, what the opposing commander wrote — is invisible. The model infers it or does without.

What it sends back

{ "orders": {
    "red-1": { "skill": "FLANK_LEFT", "reasoning": "under 12 words", "taunt": "under 8 words" },
    "red-2": { "skill": "DEFENSIVE_SHIELD", "reasoning": "...", "taunt": "..." }
} }

The response is requested as strict JSON. The server then re-validates it rather than trusting it: a skill name it doesn't recognise is replaced with SNIPE_STANCE and flagged as a fallback, reasoning is clipped to 120 characters, taunts to 80, and every bot is guaranteed an order. A malformed or half-empty reply degrades one bot's tactics; it can never stall a team. The real numbers behind a skill — damage multipliers, durations, speeds — are attached from the server's own catalog, so the model can't invent its own stats.

What happens to an order

Applying an order sets the bot's active skill, starts its duration timer, and sets an aggression value from 0 to 100. Aggression is the engine's master dial: it converts straight into a preferred fighting distance — 400 − aggression × 3.6 pixels — so a 100-aggression charger wants to be 40 px from your face while a 0-aggression retreater wants 400. It also controls how much a bot strafes (aggressive bots strafe less), tightens shot spread as it rises, and above 80 it lets a bot blind-fire at cover it can't see through, roughly half the time.

When the duration runs out the bot reverts to its baseline stance and keeps fighting on the engine's own logic — always targeting the nearest living enemy — until the next order lands.

Memory, and why bots adapt

Two memories feed the prompt. The match log is per team and holds the last 8 entries: what each of your bots chose last tick and how much damage it had taken, plus every kill and every pickup grab in the arena, which are broadcast to everyone. The round history is persistent, and tells a team whether it won or lost its last five matches and under which standing orders. That's the loop that makes a losing strategy visibly change its mind.

Rate limits and failure

Each team has its own in-flight guard and its own backoff. A 429 puts that team alone on an exponential cool-down — 4 s, 8 s, 16 s, up to a minute — while the other teams keep calling on schedule. A team that's mid-call skips the next tick rather than stacking requests; a team with no living bots is skipped entirely. Bots with stale orders keep fighting on their last instruction, so a throttled team degrades gracefully instead of freezing.

All four fire rates were cut to 20% of their original values (rounds used to run short) — reload times are roughly 5× longer than they look at a glance. Skill modifiers still stack on top: Snipe's doubled damage turns a railgun round into 90, and its halved rate stretches the reload to ~14.3 s.

Pickups — contested, first-come

One spawns 6 s into the match and roughly every 11 s after, up to three on the floor at once, always clear of cover and at least 70 px from any bot. Each lives 22 s and blinks out over its last 4. Anyone who touches one takes it, and everybody is told who got it on the next tick.

06Arena and combat rules

Cover is destructible, and that changes everything

Every block has 120 hit points. It blocks movement, blocks line of sight, and stops every projectile — piercing railgun rounds and charge beams included — while absorbing that shot's damage into its own HP. Cracks spread across it as it wears, and when it dies it bursts, kicks the camera and leaves open ground. Since the model is told each block's current HP, a wall that's nearly gone is a legitimately bad place to hide, and a good place to shoot through in two more volleys.

Damage order

A hit is soaked by the shield pool first and only touches HP once the shield is gone; shield absorption sparks violet instead of the shooter's colour. Both halves are still counted as damage taken, which is what the model reads next tick. At zero HP the bot explodes, the camera shakes, and every surviving team is told which bot died.

Winning

A match ends when only one team still has a bot standing — not on first blood, which is what makes 2v2 and free-for-all work. If the last bots die together it's a draw. The winner's scoreboard tally increments and persists while the page stays open; the round is written to history either way.

The button under the mode selector doubles as an abort: while a match is running it reads Abort AI Match and stops the AI loop immediately.

08What V2 added

V1 was one file, two hard-coded bots and a single model call that moved both sides. V2 rebuilt it in four passes.

PhaseWhat changed
1 — EngineThe 472-line monolith split into nine modules with a shared mutable world, so the arena supports N bots on N teams instead of exactly two. Match modes arrived with it.
2 — OpponentsEach team got its own prompt, its own model and its own API call, fired in parallel with independent rate-limit backoff. Reasoning, per-match memory, persistent round history and four-way free-for-all all landed here.
3 — SubstanceSkills stopped being two numbers and became real behaviours — roots, orbits, dashes, charge beams, shield pools. Four weapons, four pickups and destructible cover were added, and the catalog became a single file shared by the browser and the API.
4 — LegibilityReasoning and status drawn on the arena, muzzle flashes, shockwaves, camera shake, cracked cover, per-team audio pitch, the live match-stats table and the wide-screen layout.

One smaller change matters more than it looks: nothing hard-codes a model id any more. The default is resolved against Google's live catalog at call time and degrades to the closest flash-lite or flash sibling, because a stale id would 404 every single call.

09Tuning and troubleshooting

Writing prompts that actually change the match

The model sees exact distances, HP and line-of-sight flags, so conditional orders work far better than adjectives. "Push only when the enemy is under 100 HP, otherwise hold cover" gives it something to evaluate; "be aggressive" mostly collapses into charge spam. Naming a resource works too — telling a team to contest pickups makes it read the crate list it's already being handed.

If you're hitting rate limits

Raise the tick interval first — it's linear on request count, and at 10–12 s matches still read fine because skills last 3–5 s anyway. Free-for-all costs four calls a tick to 1v1's two. The log will tell you plainly when a team is backing off and for how long.

Running a fair model comparison

Give both teams the identical prompt, HP, speed and weapon, change only the model dropdowns, and run several rounds on the same layout. The round-history table records the winning model and its orders for exactly this. Bear in mind the arena itself isn't symmetric in free-for-all, and pickups spawn at random, so single rounds prove nothing.

Common failures

  • Dropdowns stuck on "Loading models…" — the GET failed. Missing or invalid GEMINI_API_KEY, or you're on a static server with no API route.
  • Bots fight but never change skill — every tick is erroring. Check the telemetry log; orders aren't arriving and bots are running on engine defaults.
  • Everything picks Snipe — that's the fallback skill. It means responses are arriving but with skill names the catalog doesn't recognise.
  • History is empty after a reload — browser storage is blocked or cleared. History is a nicety and is allowed to fail silently.

10Known quirks

Real behaviours of the current build, worth knowing before you read a number as gospel.

Shotgun accuracy can exceed 100%. A volley counts as one shot fired but five possible hits, so the ACC column overstates it. Compare shotguns to shotguns, not to railguns.
Taunts are generated but never displayed. The model writes one per bot, the server keeps it and the bot stores it — nothing draws it yet. It's a free hook if you want speech bubbles.
Line of sight is sampled, not solved. It tests 11 points along the sight line, so a shot can occasionally clip a thin corner the check called clear.
Targeting ignores orders. Every bot always shoots at the nearest living enemy. The model steers where a bot goes and how it fights, but it can't call focus fire on a specific target.
The scoreboard isn't the history. Win tallies reset when the page reloads; the round-history table persists. They can disagree.
