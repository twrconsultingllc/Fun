Claude Architect Lab

A hands-on project plan for the Claude Certified Architect — Foundations exam: a small local Node project that exercises the agent loop, custom tools, an MCP server, the Claude Agent SDK, structured output, and context management — the things the exam actually tests. The running example is a licensing consulting firm that helps client businesses obtain state-by-state money transmitter licenses (MTL) — so the project models two things side by side: the state rules themselves, and a case file per client tracking where they stand against those rules.

Read this first Every money-transmitter-licensing figure in this project — surety bond ranges, net worth requirements, review times — and every client named in it is a synthetic, illustrative sample built only to give the agents something realistic-shaped to reason about. No real person, business, or regulatory figure appears anywhere in this dataset. Real licensing decisions must be verified against NMLS and each state's actual regulator — not this dataset. The cost figures in section 10 are similarly illustrative, built from published API list prices checked at write time — re-verify current pricing before quoting a real number to anyone.

04 · What the agents reason about, part oneThe state-rules sample dataset

One JSON file, mcp-server/data/state-mtl-requirements.json, covers eight to ten states — California, New York, Texas, Florida, Illinois, Washington, Massachusetts, Georgia, Colorado, and Arizona. Every record has the same shape, and every record repeats the same warning rather than naming a specific regulator (regulator names and requirements change, and inventing a plausible-sounding agency name would be worse than not naming one): 

{
  "state": "California",
  "licenseName": "Money Transmitter License (sample)",
  "suretyBondRangeUsd": "50,000-500,000 (sample range only)",
  "netWorthRequirementUsd": "100,000 (sample only)",
  "nmlsRequired": true,
  "typicalReviewTimeWeeks": "12-20 (sample only)",
  "notes": "Illustrative sample only — verify against NMLS and the state regulator before relying on this."
}

A top-level "disclaimer" key repeats the same warning once for the whole file. A state simply not present in the sample set is a feature, not a bug: it forces the tools below to say "unknown — needs real research" instead of ever guessing. This file answers "what does a state require" in the abstract; it says nothing about any particular client, which is what the next section adds.

05 · What the agents reason about, part twoClient case files

A consulting firm's actual product isn't a shelf of state rules — it's the case file it keeps for every client it's shepherding through licensing. mcp-server/data/clients.json models that: three sample clients, each with the same shape a real firm would track — who they are, who controls them, what they do, and exactly where each state application stands. 

{
  "clientId": "meridian-payments",
  "legalName": "Meridian Payments LLC (sample)",
  "entityType": "LLC",
  "formationState": "Delaware",
  "einSample": "XX-XXXXXXX (sample — never a real EIN)",
  "controlPersons": [
    {
      "name": "Dana Whitfield (sample)",
      "title": "CEO / Managing Member",
      "ownershipPercent": 40,
      "birthYear": "1978 (sample — year only)",
      "backgroundDisclosure": "None disclosed (sample)"
    }
  ],
  "businessProfile": {
    "productLines": ["money transmission", "prepaid access"],
    "statesCurrentlyLicensed": ["California", "New York"],
    "annualTransactionVolumeUsd": "18,000,000 (sample)",
    "currentNetWorthUsd": "650,000 (sample)",
    "suretyBondsPostedUsd": { "California": "50,000 (sample)", "New York": "500,000 (sample)" }
  },
  "licensingEngagements": [
    {
      "state": "Texas",
      "status": "gathering_documents",
      "targetSubmissionDate": "2026-11-01 (sample)",
      "lastUpdated": "2026-09-10 (sample)",
      "checklist": [
        { "item": "Surety bond quote obtained", "status": "done" },
        { "item": "Net worth statement prepared", "status": "done" },
        { "item": "NMLS filing drafted", "status": "pending" },
        { "item": "Background checks for control persons", "status": "pending" }
      ]
    }
  ]
}

Two deliberate choices, both driven by the same worry — that a "pedigree" field is exactly the kind of thing that quietly becomes a template for real PII if nobody stops to think about it:

  • No field shaped like a real identifier. controlPersons tracks a birth year, not a date of birth, and never an SSN, address, or ID number — the fields a real intake form would need, minus anything that would look like a genuine identifier if this file were ever copy-pasted as a starting point.
  • Every name and figure is tagged (sample) inline, the same convention the state dataset already uses, so a value can never be mistaken for a real client's data even out of context.

licensingEngagements is the progress-tracking piece: one entry per state a client is pursuing, a status from a fixed enum (not_started, gathering_documents, submitted, under_regulator_review, deficiency_response, approved, denied, withdrawn, renewal_due, amendment_in_progress), and a per-item checklist — the same "go/no-go packet" idea from the original design, now scoped to one real client instead of one hypothetical business.

06 · Why both datasets existHow the agent gets used

A consulting firm asks three different shapes of question, and the two datasets above only pay off together once the agent has to answer all three:

Query typeExample questionNeeds
New / prospective client "Would Northstar Remittance qualify for a Washington MTL today, and what's the gap?" a client with no licensingEngagements yet, checked against the state dataset — client_gap_analysis
Ongoing client, change in circumstances "Quickship is adding a new 25% owner — which in-progress state applications need an amendment and a fresh background disclosure?" reading across a client's existing engagements and reasoning about which states' rules that change touches — judgment, not a lookup
Active application, in progress "What's still open on Meridian's Texas application, and is anything overdue?" get_client_progress against one client's checklist

The first and third are ordinary tool composition — this project already builds that muscle in gap-analysis.mjs and validate-expansion-checklist.mjs. The second is deliberately left as a stretch case rather than a fully-built milestone: evaluate-change-impact.mjs exists as a thinner tool that returns the states a change touches and lets the model reason about materiality, rather than trying to encode "which ownership changes trigger a refiling" as a lookup table it can't actually source. Scoping it that way keeps the lab honest about where a deterministic tool stops being the right shape for the problem — itself a Tool Design & MCP exam point, not scope creep.

08 · Putting it togetherThe example task

Every milestone shares one throughline scenario, run from inside a licensing consulting firm rather than from inside the business being licensed: "Meridian Payments is our client. They're already licensed in California and New York and want to expand into Texas, Florida, and Illinois — produce an expansion checklist, flag any gaps against their actual financials, and track it as a case." That single scenario is small enough to hold in your head, but real enough to force every exam-tested concept — and both datasets — to earn its place:

  • Gather: get_state_requirements looks up one state at a time from the sample dataset; get_client pulls Meridian's own profile and existing engagements.
  • Act: client_gap_analysis diffs Meridian's actual net worth and posted bonds against each target state's requirements — a real per-client gap, not a generic one — and update_checklist_item records progress as it happens.
  • Verify, twice, two ways: validate-client-checklist.mjs checks a client+state checklist deterministically (code); the mtl-compliance-reviewer subagent reviews it a second way (an LLM's judgment) — the page's built-in illustration of "verification doesn't have to mean asking the model again."
  • Split the work: the orchestrator's research worker only ever sees the lookup tools (state + client); its writing worker only ever sees the research worker's structured findings — never the raw tool calls. That narrowing is itself the "structuring multi-agent architectures" exam point, not incidental plumbing.
  • Answer ad hoc, client-scoped questions: the other two query types from section 06 — a prospective client (Northstar) and a client mid-change (Quickship) — are exercised directly against the MCP tools in client-tools.test.mjs, without a dedicated milestone file each; see the "Client sample set" decision in section 03 for why three clients was the deliberate stopping point.

10 · What this would cost for realProduction cost model

Illustrative, not a quote Every number below uses Anthropic's published per-token list prices, pulled from a maintained, dated pricing reference rather than recalled from training data (the "verified, not recalled" habit from section 02 — though unlike that section's live npm view checks, this is a cached reference table, not a same-session live fetch, so it carries whatever lag that table has against Anthropic's current published pricing). They are still a back-of-envelope model, not a bid: real traffic shape, prompt length, and hosting-provider choice will all move these numbers. Re-check current pricing at the time this would ever actually be quoted to anyone.

Model pricing used

ModelInput / MTokOutput / MTokWhere it fits
Claude Haiku 4.5$1.00$5.00the deterministic-lookup query types (progress tracking, plain gap analysis) — little reasoning needed
Claude Sonnet 5$2.00$10.00this project's default (section 03) — the balance point for most queries
Claude Opus 5$5.00$25.00reserved for the change-impact query type, where judgment quality matters more than cost

Prompt caching (used in context-budget.mjs) charges a premium to write a cache entry and a discount to read one: writes cost 1.25× the base input price on the default 5-minute TTL (2× on a 1-hour TTL), reads cost 0.1×. It only pays for itself once the same prefix gets read back more than once or twice — exactly the shape of a "static reference data queried repeatedly" case, which is why context-budget.mjs is built around it.

Per-query cost at this lab's scale

At the lab's deliberately small scale — 8–10 states, 3 clients — a single query's context is tiny: roughly 800 tokens of system prompt and tool schemas, ~1,500 tokens for the full state dataset, and ~400–600 tokens for one client's record, call it ~3,000 input tokens, plus a 300–1,500 token answer. On Sonnet 5, uncached that's roughly $0.009–$0.02 per query. With the static portion (system prompt + state dataset, ~2,300 tokens) cached and hit on every subsequent query, the uncached slice drops to the ~700 tokens that actually vary (the client record and the question) — roughly $0.005–$0.017 per query. Caching is doing its job here, but the dataset is too small for that job to show up as real savings yet.

That's the honest number for the lab as scoped. It is not the number for a real firm's dataset — which is the actual "would this survive contact with production" question worth asking:

Where caching actually starts to matter A real firm's reference data would cover all fifty states plus however many active client case files it runs — easily 40,000–60,000 tokens of static context instead of ~2,300. At 50,000 cached tokens, an uncached query costs roughly $0.10 in input tokens alone on Sonnet 5; the same query against a warm cache costs about $0.01 — a real order-of-magnitude difference. context-budget.mjs's before/after measurement is exactly the exercise that would confirm this at whatever scale gets built.

Monthly volume, a firm-sized guess

Say a firm carries 40 active client case files and an analyst asks the assistant roughly 15 questions per client per week across the three query types — progress checks, gap analysis, the occasional change-impact question. That's about 2,400 queries a month. At $0.01–$0.02/query on Sonnet 5, that's roughly $24–$48/month in model spend. Ten times the traffic (a firm ten times this size) scales roughly linearly to $240–$480/month — still a rounding error against staff cost. The lever that actually moves per-query cost is dataset size, not client count — see the caching callout above.

Hosting

The MCP server and the Node tooling around it have no GPU, no vector database, and — at 8–10 states and a few dozen clients — no real storage requirement; the whole dataset is a couple of small JSON files. Run on-demand (invoked only when a question comes in) the compute cost is close to zero between queries; run as a small always-on process it's the cost of the cheapest container or VM tier a provider offers — a handful of dollars a month, not a line item worth optimizing at this scale. Moving the client data into a real database once case volume grows past what a JSON file can track cleanly is a "when it's needed" step, not a "day one" cost.

The actual bottom line At this scale, and probably well past it, API spend is not the constraint. A consulting firm deciding whether to build something like this should be weighing analyst time saved and error rate against engineering and compliance-review time to build and maintain it — not against a token bill that, on these numbers, rounds to noise next to one analyst's hourly rate.

11 · Watch for theseKey implementation notes

  • API key: .env inside claude-architect-lab/, already covered by the root .gitignore's bare .env/.env.* patterns. Loaded via Node's built-in process.loadEnvFile() — no dotenv dependency.
  • Minimal dependencies: @anthropic-ai/sdk, @anthropic-ai/claude-agent-sdk, @modelcontextprotocol/sdk, zod (MCP tool schemas). No separate JSON-schema validator — output_config.format and MCP schemas already cover it.
  • No invented regulator names: the state dataset's notes field always points to NMLS/the state regulator rather than naming a specific agency, so nothing in it can be mistaken for a current, authoritative reference.
  • No real-shaped identifiers in the client dataset: clients.json never includes an SSN, full date of birth, street address, or anything else shaped like a genuine identifier — see section 05.
  • Not a browser toy: this project is not linked from index.html, and CLAUDE.md's "verify the live deployed site" rule does not apply to it.
  • No live API calls in automated tests: loop/logic tests stub Messages.create; sdk-version/agent.mjs's true end-to-end behavior is manual-run-and-eyeball only, same spirit as battle-bots-v2.core.test.mjs.
