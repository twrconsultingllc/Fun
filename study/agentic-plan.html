The engine underneath everything elseThe core loop: gather → act → verify

Every other loop on this page is a variation on, or an addition to, one basic shape: agent-loop.mjs's hand-rolled loop over the raw @anthropic-ai/sdk. Each iteration sends the full conversation so far to Messages.create, and what comes back decides what happens next: 

let turns = 0
while (turns++ < MAX_TURNS) {
  const response = await anthropic.messages.create({
    model, system: systemPrompt, tools: toolDefs, messages,
  })
  messages.push({ role: "assistant", content: response.content })

  const toolUses = response.content.filter(b => b.type === "tool_use")
  if (toolUses.length === 0) {
    // model produced a plain-text answer — a CANDIDATE final answer,
    // not yet a returned one; hand it to the verify phase below
    return await verify(response, messages)
  }

  // otherwise: run each requested tool, feed the results back in,
  // and loop again — this is the "gather" or "act" half of the cycle
  const results = await Promise.all(toolUses.map(runTool))
  messages.push({ role: "user", content: results })
}
throw new Error("max turns exceeded without a verified answer")

Two things make this a loop rather than a straight-line pipeline. First, the model itself decides how many gather/act iterations it needs — asking for one state's requirements, then deciding it needs the client's profile too, then deciding it needs two more states — before it ever emits plain text. Second, MAX_TURNS exists specifically to close off the failure mode where the model keeps calling tools indefinitely without ever converging: a feedback control on the loop itself, not just on its content.

The "verify" step is what keeps this from being just "call tools until the model stops." A plain-text response is a candidate answer, not an answer — it still has to pass through the two independent checks in "Two verify loops" below before anything gets returned to the person who asked the question.

Thirteen turns for one scenario, and only two of them (1 and 13) ever touch the human. Everything in between is the agent deciding, on its own, what it still doesn't know and what to check before it commits to an answer.

When the shape of the answer matters as much as its contentThe retry loop: forcing structured output

Turn 8 above glosses over something structured-output.mjs exists specifically to handle: the checklist can't just be readable prose, because update_checklist_item and the case file need it as strict JSON — one object per target state, a fixed set of fields, no free-form drift. The model is asked for that shape via output_config.format (the current structured-output API, not the deprecated forced-tool_choice trick), and a small loop of its own handles the case where the first attempt doesn't validate: 

attempt 1 → model returns JSON missing a required "targetSubmissionDate"
          → schema validation fails locally, no API round trip wasted on it
          → the validation error itself becomes the next user turn:
            "Your last response was missing targetSubmissionDate for
             Illinois. Return the full checklist again with that field
             included."
attempt 2 → model returns JSON with a "status" value not in the
             fixed enum ("in_review" instead of "under_regulator_review")
          → same pattern: the specific error goes back in, not a generic
             "try again"
attempt 3 → valid → loop exits, structured checklist moves on to
             validate-client-checklist.mjs

The loop is bounded — a small fixed retry cap, matching the MAX_TURNS idea from the core loop — because an unbounded "keep asking until it's valid" retry is exactly the kind of silent-forever failure mode the core loop's turn cap already exists to prevent. Past the cap, the failure surfaces to a human instead of looping quietly.

Not a tool loop — a fixed chain over textThe chain loop: draft → critique → revise

review-loop.mjs is a genuinely different shape from everything above it: no tools, no branching, no "loop until X" — a fixed three-step chain of separate model calls over one piece of text, the compliance memo:

  1. Draft — the checklist from the core loop above gets turned into a short, readable memo, written as if for a client or for legal.
  2. Self-critique — a second call, with a deliberately different prompt ("find gaps, vague language, or missing caveats in this memo — don't rewrite it, just list problems"), reviewing the draft from step 1.
  3. Revise — a third call incorporates the critique from step 2 into a final version of the same memo.

This always runs all three steps, in that order, every time — unlike the core loop's open-ended "keep gathering until the model stops" shape, or the retry loop's "keep trying until it validates" shape. It's prompt chaining, not agency: the value comes from asking the same model to look at its own output from a different angle, in a separate call that doesn't share the first call's momentum, rather than from the model deciding anything about how many steps to take.

The same job, done two different ways, on purposeTwo verify loops, two different mechanisms

Turns 9 and 10 in the trace above aren't redundant — they're the lab's deliberate illustration that "verify" doesn't have to mean one specific thing, and doesn't have to mean asking the model to grade its own homework:

validate-client-checklist.mjsmtl-compliance-reviewer subagent
MechanismDeterministic code — the same input always produces the same resultA second, separate LLM call with its own system prompt and (in the SDK version) its own scoped toolset
CatchesStructural failures: a missing target state, an invalid enum value, a required field left blankJudgment failures: a caveat that got dropped in revision, a claim stated more confidently than the underlying data supports, an awkward or unclear passage
Can't catchAnything about tone, clarity, or whether a technically-valid checklist still reads badlyIsn't guaranteed to notice a missing field the way a schema check mechanically will — LLM review is judgment, not a parser
Cost per checkFree — no API callOne more model call, priced like any other turn

Running both, rather than picking one, is the point: each one is blind to exactly the class of problem the other one exists to catch.

A feedback loop measured in tokens and dollars, not turnsThe economic loop: budget, compaction, caching

context-budget.mjs runs a scenario that deliberately stresses the loop above: instead of the model selectively fetching three states it already knows it needs (turn 4 in the trace), this version looks up every state and every client one at a time, on purpose, to make two separate feedback loops visible.

Loop 1 — compaction

After every Messages.create call, the response's own usage block (input_tokens, output_tokens) gets added to a running total. Once that total crosses a threshold — a fraction of the model's context window, sized against plan.html's own estimate that a full ten-state, three-client sweep runs a few thousand tokens — older tool-result turns get summarized into one condensed synthetic message, freeing budget before the next call. The trigger is the running total itself feeding back into whether the next iteration's messages array gets rewritten before it's sent — the same "measure, then act on the measurement" shape as the retry loop above, just on token counts instead of a schema check.

Loop 2 — prompt caching

A cache_control breakpoint marks the static prefix of the system prompt — the parts that don't change between calls: tool schemas and (per plan.html section 10) the full ten-state dataset. The first call that includes this prefix is a cache write, priced at a premium (1.25× normal input price on the default five-minute TTL, 2× on a one-hour TTL); every later call that reuses the same prefix is a cache read, priced at a 0.1× discount. This only becomes a real feedback loop — not just a discount — because context-budget.mjs measures before-and-after token counts across the whole ten-state, three-client sweep rather than asserting the saving: at this lab's small scale (~2,300 tokens of static context) the saving is real but modest; plan.html section 10 works out that the same pattern against a real firm's full dataset (40,000–60,000 tokens) is where caching stops being a rounding error and starts being roughly a 10× reduction in per-query cost. The loop only pays for itself once the same prefix is actually read back more than once or twice — which is exactly what gets measured, not assumed.

A loop that calls two smaller loopsThe delegation loop: two workers, one orchestrator

orchestrator.mjs takes the same Meridian scenario and splits it across two narrowly-scoped workers, each running its own instance of the core gather-act-verify loop internally:

  • Research worker — sees only the lookup tools (get_state_requirements, get_client, client_gap_analysis). Its job ends at turn 7 in the trace above: a structured JSON gap analysis, nothing else.
  • Writing worker — sees only the research worker's structured JSON output, never the raw tool-call transcript that produced it. Its job is turns 8 onward: draft the checklist and memo, running its own draft-critique-revise chain internally.

The orchestrator's own loop is one level up: decompose the task, run both workers (the writing worker only starts once the research worker's structured output is ready), then merge the result. The boundary between the two workers is deliberately narrow — structured data only, never raw tool-call noise — as its own feedback control: a malformed or overly verbose tool result in the research worker's transcript has no way to leak into the writing worker's prompt, because the writing worker never sees that transcript at all. That narrowing is the actual "structuring multi-agent architectures" exam point plan.html section 08 calls out — not incidental plumbing.

Verification moved inside the loop itselfThe control loop: Agent SDK hooks

sdk-version/agent.mjs runs the same Meridian scenario a third way, through @anthropic-ai/claude-agent-sdk's managed query() loop instead of the hand-rolled one at the top of this page. The interesting difference isn't the tools — it's where the "verify" moment sits. A PreToolUse hook fires before every tool call the SDK loop makes and can inspect the proposed call and its input before it runs, returning allow, deny, or a modified input. That's the same idea as turns 9–10 in the trace above — a check that can reject or redirect an action — but happening per-call, inline in the loop itself, instead of once at the very end against a finished draft. permissionMode adds the same idea at a coarser grain (default, dontAsk, acceptEdits, bypassPermissions, plan, auto) — a policy decided once per session instead of once per call. And the project's .claude/agents/mtl-compliance-reviewer.md subagent is the SDK's declarative version of the second-opinion verify loop from the section above: the same "one more LLM call with a narrower job" idea, wired through config instead of a hand-written function call.

Guesswork now, evals laterWhat's likely to break in production

This section is a prediction, not an incident report Nothing on this page has run against the real API yet (see the caveat at the top), so nothing below is a bug this project has actually hit. It's the set of failure modes that show up again and again in agentic LLM systems shaped like this one — tool-calling loops, structured-output retries, self-critique chains — applied to this specific design so there's a concrete list to test against once Sessions 5–9 actually run, instead of finding all of this out for the first time in front of a real client's case file.
Failure modeHow it would show upLikely causeCheap first responseIf it keeps happening
Ungrounded claims The final memo states a number (a bond gap, a net-worth shortfall) that doesn't match any tool result actually returned in that run. The model skips the gather step and pattern-matches to a plausible-sounding figure instead of calling client_gap_analysis. Tighten the system prompt to require a tool call backing every numeric claim; have validate-client-checklist.mjs reject a draft whose numbers don't trace to a logged tool result. Move the citation check from a prompt instruction into a hard code gate in the verify step, so it can't be reasoned around by a confident-sounding draft.
Tool-call thrashing The core loop hits MAX_TURNS without producing an answer, having called the same or near-duplicate tool several times. The model isn't sure it has enough information yet, so it re-checks instead of proceeding. Log every tool call's arguments, dedupe repeats, and return the cached result with a note instead of re-invoking the tool. Rewrite the tool's description to state explicitly what a complete result looks like, since an ambiguous tool contract is the usual root cause.
Hallucinated coverage The model answers as if it has real requirements for a state that isn't in the sample dataset, instead of surfacing the "unknown" result and saying so. A plausible-sounding answer is rewarded more than an honest "I don't know" during training — a well-documented general tendency, not specific to this model. Add adversarial test cases that ask about an unsupported state on purpose, and strengthen the "say you don't know" instruction until they pass. If a model keeps failing that specific eval, treat it as a real disqualifier for that step and swap to a model with a demonstrated lower refusal-failure rate, even at a cost premium — this is the one failure mode a licensing firm can't tolerate.
Schema-retry oscillation The structured-output retry loop fixes the field the error flagged, breaks a different one, and hits its retry cap without ever validating. Each retry prompt only shows the latest validation error, so the model "forgets" the earlier fix while chasing the new one. Feed the full validation-error history into every retry attempt, not just the newest one. If a specific field keeps oscillating, simplify its schema (a fixed enum instead of a free-text date, say) rather than continuing to retry against a shape the model can't reliably hit.
Self-critique blind spots The review-loop's own critique step approves a draft that still has a real gap. A model critiquing its own output shares its own blind spots — a known weakness of self-critique chains in general. This is exactly why validate-client-checklist.mjs (code) and the mtl-compliance-reviewer subagent both exist alongside it, per the two-verify-loops section above. If the subagent keeps missing the same class of gap the self-critique missed, that's a sign it shares a model-family blind spot rather than acting as independent judgment — run it on a different model or provider, or add a periodic human spot-check on a sample of real outputs.
Cost/latency assumptions breaking at scale Real per-query cost or latency comes in noticeably higher than plan.html section 10's estimate. That model was sized for the lab's 8–10 states and 3 clients — a real firm's fifty-state, dozens-of-clients dataset changes when compaction triggers and how much caching actually saves. Re-run context-budget.mjs's before/after token measurement at realistic dataset size before trusting the cost estimate for a real deployment. If real costs run meaningfully higher, revisit which query types are assigned to Haiku vs. Sonnet vs. Opus in plan.html section 10 before assuming the architecture itself needs to change.
Model version drift Behavior on the same prompt changes, or breaks outright, with no code change on this project's side. The provider updated or deprecated the pinned model ID on their own release cycle. Pin an exact model version rather than a "latest" alias, and keep a small fixed set of test scenarios to re-run after every version bump. If a version bump changes behavior in a way prompting can't recover, that's the point to seriously weigh prompt iteration vs. a different model tier vs. — only once there's enough real labeled production data to do it responsibly — fine-tuning, in that order.
Untrusted client data read as instructions A client's own free-text notes manipulate the agent into skipping a verification step or taking an action nobody asked for. Free-text fields get treated as instructions instead of as data to reason about — a risk that doesn't really exist yet, since today's client records are curated sample JSON, not real client-submitted intake text. Treat any client-supplied text as data, never as directives, and enforce that at the PreToolUse hook layer (the control-loop section above), not just in the system prompt. The moment a real intake pipeline feeds this project actual client-submitted text, this graduates from "worth watching" to "must fix before launch" — it's the one row here with a real trust boundary attached.

The honest order of operations, given there's no real usage data yet: iterate on prompts and schemas first, since they're the cheapest and fastest to change and most of the table above is addressable that way. Reach for a different or larger model on one specific step only once a failure mode is shown to actually recur across many real cases, not after a single wrong answer. Treat fine-tuning as the last resort, worth doing only once there's enough real, labeled production data to do it responsibly — this lab's synthetic ten-state, three-client sample is nowhere near that bar. None of that ordering can be executed on vibes, though: it depends on having a small held-out set of realistic questions with known-correct answers to check any prompt change, model swap, or version bump against — building that eval set is arguably the real next step once Sessions 5–9 exist, not an afterthought once something breaks.

Beyond the labOngoing monitoring & testing, once this is live

Also a design sketch, not a built system Same caveat as the failure-modes section above: nothing below exists as code or infrastructure. This lab's tests/ suite proves the loops run correctly against sample data, once, in a sandbox with no live traffic — that is a real but narrow kind of confidence. It says nothing about whether the same loops keep behaving correctly next month, against a prompt tweak, a provider's model update, or a real client's actual case file. This section sketches what would have to exist to answer that ongoing question, sized to a firm actually running this in production rather than to the lab's ten-state, three-client scale.

Testing the loops on an ongoing basis

npm test is necessary but not sufficient: it's fast, free, and runs on every change, but every one of its assertions is checked against a stubbed Messages.create or a fixed sample dataset — it can prove the retry logic re-prompts correctly on a fabricated invalid response, but it can't tell you whether the real model, today, actually produces a checklist that's correct against Meridian's real numbers. That second question needs a genuinely different kind of test, run against the live API, and the closing paragraph of the failure-modes section above already names why it matters: none of that section's "cheap first response" / "if it keeps happening" escalation ladder can be executed on vibes — it depends on a held-out set of questions with known-correct answers to check any change against.

  • A small, fixed golden-scenario set — Meridian's TX/FL/IL expansion, Northstar's Washington gap question, Quickship's pending-ownership-change question: the same three query types plan.html section 06 already identified, each with a known-correct expected checklist, gap summary, or touched-states list to diff the real output against.
  • One adversarial case per row of the failure-modes table above — an unsupported-state question to catch hallucinated coverage, a client whose financials clear every bar to make sure the loop doesn't manufacture a gap, a deliberately ambiguous change-impact scenario to stress evaluate-change-impact.mjs's "judgment, not lookup" framing. Turning that table from a prediction into an actual test is the whole point of building it before Sessions 5–9's real runs, not after.
  • A separate, slower suite from tests/ — this lab's tests are framework-free and run in milliseconds with zero network calls on purpose (the repo root CLAUDE.md's own convention); a live-API eval suite is the opposite by necessity — it costs real money and takes real wall-clock time per run. It belongs in its own directory (an evals/ alongside tests/, say), run on a schedule and before shipping a prompt or model change, never on every commit.
  • Retest triggers, not just a retest schedule — a version bump to @anthropic-ai/sdk or the pinned model ID, any change to a system prompt or tool description, and any change to a tool's schema or return shape should each force a run of the golden-scenario set before merging, the same "verified, not recalled" discipline this project already applies to package versions and pricing, applied to model behavior instead of a version string.
  • A scoring method that fits each check — exact-match or schema validation where the answer is genuinely deterministic (does the checklist cover all four standard items, does evaluate_change_impact return the right touched-states set), and an LLM-as-judge rubric only where the output is genuinely prose (does the compliance memo actually state the real gap, not just cover the required states) — reserving the fuzzier, more expensive check for the cases that actually need it rather than defaulting to it everywhere.

What this actually requires

None of the above is free, and most of it isn't code so much as infrastructure and process this lab has had no reason to build yet:

  • Persistent, queryable logs of every real run — today, a run's tool calls, verify outcomes, and usage numbers exist only as console output during a manual invocation. Production traffic needs those retained somewhere a dashboard or alert can query, under the same "sample-tagged, no real identifiers" discipline this project already applies to its data (or a real redaction policy, once actual client intake text is involved).
  • An evals harness distinct from node --test — something that can run the same scenario against several model versions or prompt variants and diff the outputs, whether that's a lightweight custom script (in keeping with this repo's framework-free convention) or Anthropic's own evaluation tooling.
  • A staging path before production data — a way to run a prompt or model change against the golden-scenario and adversarial sets before it ever touches a real client's case file, mirroring this repo's own test vs. test:live split, but for model behavior rather than static pages.
  • Human review capacity, not just automation — the failure-modes table's own escalation ladder ends in a human for exactly the failure mode it calls the one a licensing firm can't tolerate (hallucinated coverage). That has to be a real, staffed periodic audit of a sample of live outputs, not an aspiration living only in that table's last column.
  • Clear ownership — someone who actually gets paged when a cost anomaly, a verify-failure spike, or a canary diff fires, since "ownership" doesn't exist as a concept in a lab project run from a single Claude Code session.

What this looks like in production

Put together, a real deployment's daily shape would look less like "run the agent and read the output" and more like this: every real query gets logged with its tool calls, both verify outcomes, final answer, token usage, cost, latency, and the model version that handled it. A scheduled job — nightly, or gated before any prompt or model change ships — runs the full golden-scenario and adversarial eval set against the current pinned model and prompt set, and a failure there blocks the change rather than surfacing after it's already live. A simple dashboard (this doesn't need to be sophisticated at a 40-client firm's scale, per plan.html section 10's own "API spend is not the constraint" framing) surfaces cost per query-type over time, verify-failure rates, and tool error rates, with alerting on the handful of signals in the table above that genuinely warrant waking someone up — a cost or turn-cap-hit spike, most of all. And the one failure mode the earlier table flags as truly disqualifying — a client-facing claim that turns out to be hallucinated — needs an actual response plan wired to a real trigger (an unusual rate of "unknown state" results, say, or a failed groundedness spot check), not just "swap models" as an abstract fallback with nothing that would actually fire it.

The honest scale note, matching this whole page's caveats: none of this belongs at day one of a three-client pilot. It scales in step with real usage and real stakes, the same way plan.html section 10 already argues API cost does — the investment worth making here is proportional to how much a wrong answer would actually cost a real firm, not to how sophisticated a monitoring stack looks on paper.
