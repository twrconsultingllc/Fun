Why this page existsWhy a UI, and why this is only a plan

The Claude Architect Lab has no backend and no web deployment — every session in build-plan.html is triggered by hand, from a terminal, and its output is whatever prints to stdout. That's a deliberate scope choice (plan.html section 03: "no web/Vercel deployment, the exam doesn't test deployment"), not an oversight.

A static page can't change that — it can't spawn node agent-loop.mjs, can't call the Anthropic API with a real key, and can't run any lab session live. What it can usefully do is act as a cheat sheet (the exact command for each session, one click from a copy) and a live viewer for the lab's own sample data. This page writes that design down now, as a future study/lab-console.html, without building it — so the next time there's an appetite to build it, the decisions below don't need to be re-made.

What it would doScope

Two pieces, combined into one future page:

  • A session console — a cheat-sheet table, one row per build-plan.html session, showing the exact command(s) to run and a link back to that session's real entry.
  • A dataset browser — a live, read-only view of the lab's two real sample JSON files: state-mtl-requirements.json and clients.json.

Locked in for the future buildDecisions already made

File shape Single HTML file, inline <script>, CSP loosened to script-src 'self' 'unsafe-inline' for that page specifically — matching every other interactive toy in this repo (snake.html, tricalc.html), not the stricter script-less CSP this page and build-plan.html use. Chosen over a strict-CSP/external-.js approach because it matches a proven, already-reviewed pattern in this repo rather than being new ground.
Build-plan.html stays the one source of truth The future console must never show its own Done/In-progress badges or duplicate session notes — only a link to build-plan.html's real entry. Forking a second status tracker is exactly the drift this repo's build-plan-sync rule in CLAUDE.md exists to prevent.
Scratch notes, not a second record A personal per-session textarea, saved to localStorage only, explicitly labeled as non-authoritative — handy while running a session live, never synced anywhere, never confused with build-plan.html's real notes.
Live data, not a hardcoded copy The two datasets get fetched from their real repo-relative paths (../claude-architect-lab/mcp-server/data/*.json) rather than duplicated into the page's JS — both files are already committed and not .gitignored, so GitHub Pages serves them normally. A hardcoded copy would drift the moment the lab's own sessions change the sample data.

Section 1 of 2Session console design

One row per session. Every command below runs from claude-architect-lab/, and is verified against this project's real package.json and test file names — not guessed:

#SessionCommand(s)

2Read-only lookup toolsnode --test tests/get-state-requirements.test.mjs tests/client-tools.test.mjs
3Gap analysis & the mutating toolnode --test tests/client-tools.test.mjs
4The MCP servernode --test tests/mcp-server.test.mjs

6Structured output & review loopnpm run lab:2 and npm run lab:3

8Orchestrator & the stretch toolnpm run lab:5
9Claude Agent SDK versionnpm run lab:6

Each row would also link to build-plan.html#s{n} for that session's real status and notes. The planned copy-to-clipboard button reuses tricalc.html's existing navigator.clipboard.writeText pattern with a document.execCommand('copy') fallback, verbatim — no need to invent a new one.

Section 2 of 2Dataset browser design

On page load, two independent fetch() calls (not gated behind a button, since both files are tiny) against the real dataset paths, each rendering through three states:

  • loading — plain dimmed placeholder text.
  • error — a plain-language headline, an actionable note for the likely real cause (opened via file:// instead of a server, so fetch is blocked), the raw error message tucked in a collapsed details, and a "Try again" button that just re-fetches.
  • ready — the data itself, with the JSON's own top-level disclaimer string surfaced above it — that field exists specifically to say the data is a sample, and dropping it would be a mistake.

State requirements render as a filterable table (10 rows). Clients render as one collapsible card each (3 total) rather than a flat table row, since a client's nested control persons and per-state engagements/checklists don't fit one row cleanly.

When it's actually builtTesting & process

The future page would need a window.__labConsole read-only test hook, matching this repo's existing window.__swarm / window.__raceday / window.__snake convention, and a new tests/lab-console.dom.test.mjs registered in tests/run.mjs. Per root CLAUDE.md, it would also need its own numbered security/quality review published as the next tests/secrpts/NN.html before that future work could be called done — the same process this very page went through.

Not decided yetOpen questions

  • The CSP departure from this page's own stricter policy is deliberate, not an oversight — worth restating plainly if it's ever questioned during that future review.
  • Fetching a same-origin local JSON file for app data has no precedent elsewhere in this repo — every other interactive toy hardcodes its data inline. This would be the first.
  • Whether to cross-link the future page from plan.html's and build-plan.html's footers is left for that later decision, not made now.
