Before you startHow to use this plan

This isn't a schedule — there's no requirement to do one session per day, or to do them on consecutive days at all. It's a set of stopping points chosen so that each one leaves you with something that actually runs, rather than half-finished work spread across an arbitrary line count. A few ground rules that make the multi-session approach actually work:

  • Start each new session by reading this plan and the "Done when" line of whatever session you finished last — not by reading raw code you wrote days ago. A fresh Claude Code session has no memory of prior ones, so re-orienting from this document is faster than re-deriving context from files.
  • Don't open a session's next tests as extra credit. Each session already ends at a real boundary — resist folding the next one in just because you have 20 minutes left. Half of Session 5 is worse than none of it, since the agent loop needs the whole scenario in your head at once.
  • An ANTHROPIC_API_KEY is only needed starting Session 5. Sessions 1–4 are pure data, tools, and MCP wiring, tested with stubs or an in-memory transport — zero live calls, zero cost. See the session index below for exactly which sessions touch the real API.
  • Fast-moving packages get re-checked, not assumed. Session 1 and Session 9 both re-verify current npm versions before writing code, per the "verified, not recalled" habit in plan.html section 02 — a version pinned weeks ago in this plan may already be stale by the time you build it.
  • Every session below cross-references the exact file names and shapes already decided in plan.html — this page sequences the work, it doesn't redesign it. If something here seems to contradict that page, plan.html is the source of truth; treat the mismatch as a bug in this page.
  • This page doubles as the tracker. Each session has a Status line (Not started, In progress, or Done) in its meta row, and a Session notes callout underneath its "Done when" line. When a session is finished, flip its badge to Done and log anything worth remembering there — a version that had drifted, a decision made on the spot, a divergence from plan.html, a dead end. Leave a session's notes as "None yet." if nothing came up; an empty callout is fine, a missing one isn't.

Session 2Read-only lookup tools

Status: Done Needs API key: No Est. time: 60–90 min Depends on: Session 1

Goal: every plain lookup tool over both datasets, each with a tight schema and a real "not found" path — no composition, no mutation yet.

  1. tools/get-state-requirements.mjs — one state at a time; an unrecognized state returns an explicit "unknown — needs real research" result, never a guess.
  2. tools/get-client.mjs, tools/list-clients.mjs (optionally filtered by engagement status), tools/get-client-progress.mjs (optionally filtered to one state).
  3. tests/get-state-requirements.test.mjs and the read-only parts of tests/client-tools.test.mjs — schema validation, the not-found path, and at least one passing lookup per tool.
Done when npm test passes for both test files with zero network calls. You should be able to hand-trace, for any of the 3 sample clients, exactly what each tool returns.
Session notes

Added src/lib/load-data.mjs (cached JSON loaders for both datasets) and src/lib/constants.mjs (the ENGAGEMENT_STATUSES enum) — a small shared layer plan.html's directory listing didn't call out, needed because all four tools read the same two files and list-clients.mjs needed the status enum for its filter's zod schema. Not a divergence from the design, just an implementation detail plan.html left unspecified.

The "never guess" rule from plan.html section 04 got applied at two levels, not just one: get-state-requirements.mjs and get-client.mjs return an explicit found: false for an unrecognized state/client id, and get-client-progress.mjs does the same one level deeper — a known client with no engagement in the requested state gets an explicit "no engagement found" result rather than undefined or a thrown error.

Real bug found: the "test": "node --test tests/" script written in Session 1 doesn't actually work in this environment's Node v24.20.0 — passing a bare directory path makes the test runner try to require() it as an entry module instead of globbing it for test files, which fails outright. Fixed by changing the script to node --test tests/**/*.test.mjs, which does glob correctly. This means Session 1's own "Done when" line was satisfied (nothing executed npm test yet), but the script it left behind was silently broken until this session actually ran it — worth remembering that "the script exists" isn't the same as "the script works."

All 16 tests across both files pass; zero network calls, zero mutation (that's Session 3).

Session 3Gap analysis & the mutating tool

Status: Done Needs API key: No Est. time: 90 min Depends on: Session 2

Goal: the tools that combine both datasets or change state — the last session before anything touches the live API.

  1. tools/gap-analysis.mjs — the generic, client-free diff.
  2. tools/client-gap-analysis.mjs — the client-aware version: a real client's net worth and posted bonds against state-mtl-requirements.json, not a generic gap.
  3. tools/update-checklist-item.mjs — the one tool with a side effect. Before writing it, decide and write down (in a code comment or the README stub) whether it mutates an in-memory copy for the session or rewrites clients.json on disk, and what happens if it's called twice with the same input — this is the "side-effecting tools need their own verify step" exam point from plan.html section 06, made concrete.
  4. tools/validate-expansion-checklist.mjs and tools/validate-client-checklist.mjs — the deterministic "verify" tools, kept separate from anything exposed as an MCP tool (see Session 4).
  5. Extend tests/client-tools.test.mjs to cover the mutation and its idempotency.
Done when Tests pass, and you can say out loud what happens if update_checklist_item runs twice with identical input — if you can't answer that without re-reading the code, the tool isn't done yet.
Session notes

What happens if update_checklist_item runs twice with identical input: nothing, the second time. It mutates the in-memory client dataset (never clients.json on disk — see the design-decision comment at the top of the tool file), and only when the requested status actually differs from the checklist item's current status; if it's already at the requested status, the tool returns changed:false and leaves engagement.lastUpdated untouched. Confirmed with a test that calls it twice back-to-back and checks lastUpdated stayed identical the second time, plus a separate test confirming the committed clients.json on disk is untouched after the whole suite runs.

Added two more small shared helpers beyond Session 2's: src/lib/gap.mjs (parses the datasets' human-readable dollar strings like "50,000-500,000 (sample range only)" back into numbers, then compares them) and src/lib/checklist.mjs (the "is this checklist complete against the standard 4 items" logic shared by validate-expansion-checklist.mjs and validate-client-checklist.mjs).

Divergence worth noting: plan.html's test-file list only explicitly assigns client-gap-analysis to client-tools.test.mjs; it never itemizes a home for gap-analysis.mjs, validate-expansion-checklist.mjs, or validate-client-checklist.mjs. Rather than leave them untested or spin up a new file for a handful of small tool tests, all four went into client-tools.test.mjs alongside the mutation tests this session's instructions already called for extending there.

One real ordering constraint documented in the test file itself: every tool in this file reads the same in-memory client dataset cached by load-data.mjs, and update-checklist-item is the only one that mutates it — its tests run last in the file, after every assertion that depends on the original (pre-mutation) checklist data.

Used Northstar-in-Washington as a real test case — it's the exact example question from plan.html section 06 ("Would Northstar Remittance qualify for a Washington MTL today, and what's the gap?"). The answer the tool actually gives: net worth clears the sample minimum, but no bond has been posted anywhere — a real, sensible-reading gap.

All 40 tests across both files pass; zero network calls.

Session 4The MCP server

Status: Done Needs API key: Optional — one manual check only Est. time: 60–90 min Depends on: Session 3

Goal: everything built in Sessions 2–3, exposed as one MCP server with resources alongside the tools.

  1. mcp-server/server.mjs: McpServer + registerTool for every tool from Sessions 2–3, via StdioServerTransport.
  2. Two MCP resources: mtl://dataset and mtl-clients://{clientId} — the "pull everything up front" counterpart to the "look up one thing" tools.
  3. tests/mcp-server.test.mjs using InMemoryTransport.createLinkedPair() — a real Client↔Server round-trip against every tool and both resources, no subprocess.
  4. Optional: one manual run with a real MCP client to eyeball an actual tool call end to end — this is the only place in this session an API key would even come up, and only if you want to see it work outside the test harness.
Done when mcp-server.test.mjs passes with zero subprocesses and zero network calls. This is the last "no API key required" session — everything from here on either needs one or is far more useful with one.
Session notes

server.mjs registers exactly seven MCP tools: the four from Session 2 plus gap_analysis, client_gap_analysis, and update_checklist_item from Session 3. validate-expansion-checklist.mjs and validate-client-checklist.mjs are deliberately not registered — both plan.html section 07 and this plan's own Session 3 called that out ahead of time, so there was no ambiguity to resolve here. evaluate_change_impact (the Session 8 stretch tool) doesn't exist yet either.

Verified the actual @modelcontextprotocol/sdk v1.30.0 API against the installed package rather than assuming a remembered shape: registerTool's inputSchema accepts a full z.object({...}) directly (not just a raw shape), so every Session 2/3 tool's existing inputSchema export plugs straight in with no reshaping.

Both resources are wired: mtl://dataset (static, the full state dataset) and mtl-clients://{clientId} (a ResourceTemplate, one client's full case file) — the "pull everything up front" counterpart to the tools' "look up one thing." An unknown clientId in the templated resource returns an explicit not-found body, same pattern as the tools.

tests/mcp-server.test.mjs uses InMemoryTransport.createLinkedPair() for a real Client<->Server round-trip against all seven tools and both resources — 12 new tests, 52 total across the whole suite, zero subprocesses, zero network calls.

Did the optional manual check: spawned the real server as a subprocess via StdioClientTransport, listed its tools and static resources, called client_gap_analysis, and read the mtl-clients:// resource — all matched the in-memory test results exactly. The throwaway script isn't committed (it lived outside the repo, deleted after the check).

Session 5The hand-rolled agent loop

Status: In progress Needs API key: Yes, for the final manual run Est. time: 90–120 min — the biggest single session in this plan Depends on: Session 3

Goal: agent-loop.mjs — the explicit gather → act → verify loop over raw @anthropic-ai/sdk, run against the full Meridian scenario from plan.html section 08.

  1. Write the loop with a hard max-turn cap and explicit phase transitions (gather → act → verify), not an open-ended while (true).
  2. tests/agent-loop.test.mjs against a stubbed Messages.create — turn-cap enforcement and verify-phase branching, zero network calls.
  3. Set ANTHROPIC_API_KEY and run the loop for real against the Meridian scenario: licensed in CA/NY, expanding into TX/FL/IL. Read the actual transcript, not just the final output — this is where a max-turn cap set too low or a tool schema that's subtly wrong shows up.
Done when The stubbed test suite passes, and one real run produces a checklist for Meridian that's actually correct against the sample data — not just "the loop terminated without an error."
Why this session is bigger than the others This is the first place the whole scenario has to live in your head at once — three datasets' worth of context, a multi-turn loop, and a real model response to read critically. Don't split it across two sittings if you can help it; a half-built agent loop is harder to pick back up than a half-built dataset.
Session notes

Steps 1 and 2 are done; step 3 (the real run against the live API) is still pending — this session was worked without an ANTHROPIC_API_KEY in hand, so everything that can be built and verified without a live call got done, and the manual run is left for a follow-up session once a key is available.

src/agent-loop.mjs implements the loop as three explicit phases rather than one open-ended conversation: a gather phase (read-only get_client / get_state_requirements tools), one or more act phases (client_gap_analysis / update_checklist_item), and a verify step that is deliberately code, not another model call — it calls validate-client-checklist.mjs directly, the same "kept off the MCP server" tool from Session 3. Each tool-calling phase (runToolPhase) enforces its own hard turn cap: if the model still wants to call tools once the cap is hit, the phase just ends rather than looping forever. If verify finds the checklist still incomplete, the loop feeds the specific missing items back to the model and runs one more act phase, bounded by MAX_VERIFY_ROUNDS (default 2) — this is the "verify-phase branching" plan.html section 11 calls out.

Converting each tool's existing zod inputSchema export into the JSON Schema shape the raw Anthropic Messages API wants for tools[].input_schema needed no new dependency: zod 4.6.5 (already pinned in Session 1) ships a built-in z.toJSONSchema(), which the separate zod-to-json-schema package would have duplicated. Confirmed against the installed package rather than assumed.

tests/agent-loop.test.mjs stubs Messages.create exactly as plan.html section 11 specifies — zero network calls — and covers: the turn cap firing when the model keeps requesting tools, a real tool handler actually executing and its result round-tripping back into the message list, and the verify-branching retry using the real (unmutated, since each test file is its own Node process) Meridian/Texas sample data — its two starting-pending checklist items get closed out across two stubbed act rounds. 59/59 tests pass across the whole suite.

Model id used for the eventual real run: claude-sonnet-5, matching plan.html section 03's "Sonnet 5 for day-to-day iteration" decision and this session's own confirmed-current model roster — not a recalled guess.

Committed with step 3 still open — the loop code and its stubbed tests are real, verified work on their own, but the real API run against Meridian's scenario (reading the actual transcript, not just confirming the loop terminates) is a separate follow-up once ANTHROPIC_API_KEY is available. This session's status stays In progress, not Done, until that happens.

Session 6Structured output & review loop

Status: In progress Needs API key: Yes, for the manual runs Est. time: 60–90 min Depends on: Session 5

Goal: turn the agent loop's checklist into validated structured JSON, then into a short prose memo.

  1. structured-output.mjs — force the final checklist through output_config.format (not the deprecated forced-tool_choice trick), with a bounded retry on invalid output.
  2. tests/structured-output.test.mjs — the retry-on-invalid-output logic, stubbed.
  3. review-loop.mjs — a draft → self-critique → revise chain that turns the checklist into a short compliance memo (prompt chaining).
  4. One real run of each against the Meridian scenario's output from Session 5.
Done when The retry-logic test passes, one real structured-output run actually validates against its schema, and one real memo reads as something you'd hand to a person.
Session notes

Same split as Session 5: everything buildable and testable without a live call is done; the two real runs against the live API are still pending an ANTHROPIC_API_KEY.

structured-output.mjs uses the current API exactly as plan.html section 07 specifies — client.messages.parse() with output_config.format built by the SDK's own zodOutputFormat() helper (@anthropic-ai/sdk/helpers/zod), not a hand-rolled JSON-schema-plus-forced-tool-choice workaround. Confirmed by reading the installed @anthropic-ai/sdk 0.127.0 source directly: .parse() throws an AnthropicError when the model's output fails schema validation (see lib/parser.mjs), which is exactly the failure the bounded retry in getStructuredChecklist() catches — each retry appends a corrective note to the conversation rather than silently resending the identical prompt. tests/structured-output.test.mjs stubs client.messages.parse() to cover: first-attempt success, one retry then success, and exhausting every attempt and surfacing the last error — 63/63 tests pass across the whole suite, zero network calls.

review-loop.mjs's draft → critique → revise chain is real prompt chaining: each step is its own Messages.create call that only ever sees the checklist data plus the previous step's own text output, never the raw agent-loop conversation that produced the checklist. Deliberately has no tests/review-loop.test.mjs — plan.html section 07's own test-file list never assigns it one, matching the precedent Session 9's sdk-version/agent.mjs already sets for a file that's manual-run-and-eyeball only. Its three-call chaining mechanics were smoke-checked once against a throwaway stubbed client (not committed) to confirm the sequencing before moving on.

Both scripts share one gap-analysis-to-prompt builder (buildStructuredChecklistRequest(), newly exported from structured-output.mjs) so review-loop.mjs's real run chains directly off the same structured checklist rather than re-deriving the gap analysis a second way.
