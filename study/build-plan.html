Claude Architect Lab — Build Plan

The design in plan.html turned into ten self-contained work sessions, so the actual build can happen a little at a time across separate Claude Code sessions and separate days instead of one long sitting. Each session below ends at a point where something runs and you can stop cleanly — pick this plan back up in a brand-new session any time and it'll be obvious where you left off.

Before you startHow to use this plan

This isn't a schedule — there's no requirement to do one session per day, or to do them on consecutive days at all. It's a set of stopping points chosen so that each one leaves you with something that actually runs, rather than half-finished work spread across an arbitrary line count. A few ground rules that make the multi-session approach actually work:

  • Start each new session by reading this plan and the "Done when" line of whatever session you finished last — not by reading raw code you wrote days ago. A fresh Claude Code session has no memory of prior ones, so re-orienting from this document is faster than re-deriving context from files.
  • Don't open a session's next tests as extra credit. Each session already ends at a real boundary — resist folding the next one in just because you have 20 minutes left. Half of Session 5 is worse than none of it, since the agent loop needs the whole scenario in your head at once.
  • An ANTHROPIC_API_KEY is only needed starting Session 5. Sessions 1–4 are pure data, tools, and MCP wiring, tested with stubs or an in-memory transport — zero live calls, zero cost. See the session index below for exactly which sessions touch the real API.
  • Fast-moving packages get re-checked, not assumed. Session 1 and Session 9 both re-verify current npm versions before writing code, per the "verified, not recalled" habit in plan.html section 02 — a version pinned weeks ago in this plan may already be stale by the time you build it.
  • Every session below cross-references the exact file names and shapes already decided in plan.html — this page sequences the work, it doesn't redesign it. If something here seems to contradict that page, plan.html is the source of truth; treat the mismatch as a bug in this page.

Session 1Scaffolding & both datasets

Needs API key: No Est. time: 45–60 min Depends on: nothing

Goal: the project exists, installs, and both sample datasets are written and valid — nothing reads them yet.

  1. Re-verify current versions of @anthropic-ai/sdk, @anthropic-ai/claude-agent-sdk, and @modelcontextprotocol/sdk (npm view <pkg> version) against plan.html section 02 — don't build against numbers that are already stale.
  2. Scaffold claude-architect-lab/: package.json (type: "module", script stubs for test and lab:1–lab:6), .env.example (ANTHROPIC_API_KEY=), and a README.md with just section headers for now — content comes in Session 10.
  3. Write mcp-server/data/state-mtl-requirements.json: 8–10 states, the exact record shape and disclaimer convention from plan.html section 04.
  4. Write mcp-server/data/clients.json: the 3 sample clients from plan.html section 05 — one per query type from section 06 (established/mid-expansion, brand-new/prospective, existing-with-a-pending-change).
  5. Sanity-check both files with a throwaway node -e "JSON.parse(...)" — not a committed test, just confirming they parse before anything is built on top of them.
Done when npm install succeeds, both JSON files parse, and their contents match the shapes documented in plan.html sections 04–05. Nothing executes against them yet — that's Session 2.

Session 2Read-only lookup tools

Needs API key: No Est. time: 60–90 min Depends on: Session 1

Goal: every plain lookup tool over both datasets, each with a tight schema and a real "not found" path — no composition, no mutation yet.

  1. tools/get-state-requirements.mjs — one state at a time; an unrecognized state returns an explicit "unknown — needs real research" result, never a guess.
  2. tools/get-client.mjs, tools/list-clients.mjs (optionally filtered by engagement status), tools/get-client-progress.mjs (optionally filtered to one state).
  3. tests/get-state-requirements.test.mjs and the read-only parts of tests/client-tools.test.mjs — schema validation, the not-found path, and at least one passing lookup per tool.
Done when npm test passes for both test files with zero network calls. You should be able to hand-trace, for any of the 3 sample clients, exactly what each tool returns.

Session 3Gap analysis & the mutating tool

Needs API key: No Est. time: 90 min Depends on: Session 2

Goal: the tools that combine both datasets or change state — the last session before anything touches the live API.

  1. tools/gap-analysis.mjs — the generic, client-free diff.
  2. tools/client-gap-analysis.mjs — the client-aware version: a real client's net worth and posted bonds against state-mtl-requirements.json, not a generic gap.
  3. tools/update-checklist-item.mjs — the one tool with a side effect. Before writing it, decide and write down (in a code comment or the README stub) whether it mutates an in-memory copy for the session or rewrites clients.json on disk, and what happens if it's called twice with the same input — this is the "side-effecting tools need their own verify step" exam point from plan.html section 06, made concrete.
  4. tools/validate-expansion-checklist.mjs and tools/validate-client-checklist.mjs — the deterministic "verify" tools, kept separate from anything exposed as an MCP tool (see Session 4).
  5. Extend tests/client-tools.test.mjs to cover the mutation and its idempotency.
Done when Tests pass, and you can say out loud what happens if update_checklist_item runs twice with identical input — if you can't answer that without re-reading the code, the tool isn't done yet.

Session 4The MCP server

Needs API key: Optional — one manual check only Est. time: 60–90 min Depends on: Session 3

Goal: everything built in Sessions 2–3, exposed as one MCP server with resources alongside the tools.

  1. mcp-server/server.mjs: McpServer + registerTool for every tool from Sessions 2–3, via StdioServerTransport.
  2. Two MCP resources: mtl://dataset and mtl-clients://{clientId} — the "pull everything up front" counterpart to the "look up one thing" tools.
  3. tests/mcp-server.test.mjs using InMemoryTransport.createLinkedPair() — a real Client↔Server round-trip against every tool and both resources, no subprocess.
  4. Optional: one manual run with a real MCP client to eyeball an actual tool call end to end — this is the only place in this session an API key would even come up, and only if you want to see it work outside the test harness.
Done when mcp-server.test.mjs passes with zero subprocesses and zero network calls. This is the last "no API key required" session — everything from here on either needs one or is far more useful with one.

Session 5The hand-rolled agent loop

Needs API key: Yes, for the final manual run Est. time: 90–120 min — the biggest single session in this plan Depends on: Session 3

Goal: agent-loop.mjs — the explicit gather → act → verify loop over raw @anthropic-ai/sdk, run against the full Meridian scenario from plan.html section 08.

  1. Write the loop with a hard max-turn cap and explicit phase transitions (gather → act → verify), not an open-ended while (true).
  2. tests/agent-loop.test.mjs against a stubbed Messages.create — turn-cap enforcement and verify-phase branching, zero network calls.
  3. Set ANTHROPIC_API_KEY and run the loop for real against the Meridian scenario: licensed in CA/NY, expanding into TX/FL/IL. Read the actual transcript, not just the final output — this is where a max-turn cap set too low or a tool schema that's subtly wrong shows up.
Done when The stubbed test suite passes, and one real run produces a checklist for Meridian that's actually correct against the sample data — not just "the loop terminated without an error."
Why this session is bigger than the others This is the first place the whole scenario has to live in your head at once — three datasets' worth of context, a multi-turn loop, and a real model response to read critically. Don't split it across two sittings if you can help it; a half-built agent loop is harder to pick back up than a half-built dataset.

Session 6Structured output & review loop

Needs API key: Yes, for the manual runs Est. time: 60–90 min Depends on: Session 5

Goal: turn the agent loop's checklist into validated structured JSON, then into a short prose memo.

  1. structured-output.mjs — force the final checklist through output_config.format (not the deprecated forced-tool_choice trick), with a bounded retry on invalid output.
  2. tests/structured-output.test.mjs — the retry-on-invalid-output logic, stubbed.
  3. review-loop.mjs — a draft → self-critique → revise chain that turns the checklist into a short compliance memo (prompt chaining).
  4. One real run of each against the Meridian scenario's output from Session 5.
Done when The retry-logic test passes, one real structured-output run actually validates against its schema, and one real memo reads as something you'd hand to a person.

Session 7Context budget: compaction & caching

Needs API key: Yes, for the real measurement run Est. time: 90 min Depends on: Session 4

Goal: context-budget.mjs — the file the cost estimates in plan.html section 10 were only ever a prediction for. This session produces the real numbers.

  1. Loop every state and every client one at a time, tracking token usage as you go.
  2. Add a compaction trigger with before/after token counts.
  3. Put the static portion of the context (system prompt + full state dataset) behind one cache_control breakpoint; measure a prompt-caching before/after over both datasets.
  4. tests/context-budget.test.mjs — compaction-trigger threshold math and cache accounting, stubbed.
  5. Run it for real. Write the actual measured numbers into the README next to plan.html section 10's estimates, and note plainly where reality agreed or disagreed with the prediction.
Done when The stubbed test passes, and there's a real before/after number on record — not just an estimate — for both compaction and caching. If the real numbers disagree with plan.html section 10, that disagreement is worth writing down, not smoothing over.

Session 8Orchestrator & the stretch tool

Needs API key: Yes, for the manual run Est. time: 90–120 min Depends on: Sessions 3 and 6

Goal: multi-agent decomposition, plus the one tool that's deliberately judgment-based rather than a lookup table.

  1. orchestrator.mjs — a research worker (lookup tools only) and a writing worker (only ever sees the research worker's structured output, never raw tool calls), merged.
  2. tools/evaluate-change-impact.mjs — the stretch tool from plan.html section 06: given Quickship's pending ownership change, return which states it touches and why, without a lookup table pretending to know which ownership changes trigger which state's refiling rules.
  3. Extend tests/client-tools.test.mjs so all three query types from plan.html section 06 (new/prospective, ongoing-change, in-progress) each have at least one passing test exercised directly against the MCP tools.
  4. One real run of the orchestrator on the full 5-target-state Meridian expansion.
Done when All three query types have a passing test, and one real orchestrator run produces a coherent merged memo. Also worth writing down here: did evaluate-change-impact.mjs's "judgment, not lookup" framing actually hold up once you tried to build it, or did it need more structure than planned? That's a real study finding either way.

Session 9Claude Agent SDK version

Needs API key: Yes Est. time: 90 min Depends on: Session 4

Goal: the same MCP server from Session 4, driven through the Claude Agent SDK instead of a hand-rolled loop — the direct contrast plan.html section 02 sets up.

  1. Re-run npm view @anthropic-ai/claude-agent-sdk version — this package ships multiple times a week, so re-check immediately before writing against it, not just once back in Session 1.
  2. sdk-version/agent.mjs: query() with systemPrompt (preset + append), allowedTools, a permissionMode, one PreToolUse hook, and mcpServers pointing at Session 4's server.
  3. .claude/agents/mtl-compliance-reviewer.md — the subagent that reviews a drafted checklist/memo, the LLM-judgment counterpart to validate-client-checklist.mjs's code-based check.
  4. tests/hooks.test.mjs — the PreToolUse callback called directly with fabricated input, no live call.
  5. One real manual run confirming the hook actually fires and the MCP tool is actually reachable through the SDK.
Done when The hooks test passes, and one real run confirms both the hook firing and the MCP tool being reachable. State plainly in the README that this file's true end-to-end behavior is manual-run-and-eyeball only, same as battle-bots-v2.core.test.mjs's convention elsewhere in this repo.

Session 10README, cross-check, cost reality-check

Needs API key: No Est. time: 60 min Depends on: everything above

Goal: turn ten sessions' worth of files into something you'd actually review the night before the exam.

  1. Write the README's exam-domain crib sheet — the table from plan.html section 09, filled in with the real file paths you actually ended up with, not the planned ones (note anywhere they diverged).
  2. Re-check current per-token pricing against plan.html section 10 one more time, and note anything that's drifted since that section was written.
  3. Read the exam-domain mapping table top to bottom: for each row, confirm the named file actually demonstrates the concept, not just that it runs without error.
  4. Fold in whatever you wrote down in Session 7 (the real compaction/caching numbers) and Session 8 (whether the judgment-based tool held up) — these are the parts of this project that are actually yours, not just a rebuild of the plan.
Done when You could hand this README to someone else and they'd understand what every file is for, why it exists, and which exam domain it demonstrates — and you've read it once yourself as an actual study session, not just as a formality.
