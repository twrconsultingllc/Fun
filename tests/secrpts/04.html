01Security

New content adds no external resources, scripts, or exfiltration paths
Confirmed clean

The revision added a whole second dataset and a new section to each page — the kind of change that's easy to accidentally widen the attack surface on. Grepped both files after the edit, not just before it:

  • No new href="http…" anywhere in either file besides the one pre-existing NMLS link, and that link's target="_blank" rel="noopener noreferrer" hardening (fixed in 03.html) is untouched on both pages.
  • No <script> tag, inline event handler, eval(, fetch(, or <form> introduced — both files are still pure static HTML/CSS with zero executable logic.
  • The <head> CSP/referrer/description meta tags from 03.html's fix are intact and unmodified on plan.html; on usecase.html only the description text itself was updated to reflect the new client-tracking framing, the CSP and referrer tags were not touched.
The new client sample dataset contains nothing shaped like a real identifier
Confirmed clean

A "client demographic and pedigree" dataset is exactly the kind of thing that quietly turns into a template for real PII if nobody checks it — a control-person's ownership stake, background disclosure, and identifying details are genuinely sensitive fields on a real license application. Grepped plan.html's sample clients.json excerpt and the surrounding prose for anything shaped like a real identifier: no SSN, no full date of birth, no street address, no phone number, no ZIP code. controlPersons deliberately tracks a birth year only, not a date of birth, and the sample EIN is rendered as literal placeholder characters ("XX-XXXXXXX (sample — never a real EIN)") rather than a plausible-looking number.

Every value in the sample — names, dollar figures, dates — carries an inline (sample) tag, the same convention 03.html already confirmed for the state-rules dataset, extended consistently to the new client data.

Pricing-source wording overstated how the numbers were checked
Fixed

Section 10's opening callout originally said the per-token prices were "checked live against the current API reference," echoing section 02's language for its npm view checks. That's not quite what happened: the pricing table actually came from a bundled, dated reference (a pricing snapshot, not a same-session live fetch of Anthropic's pricing page), which is a meaningfully different confidence level than a live npm view call — closer to "not recalled from memory" than to "live-verified this session." Leaving the stronger claim in place would have been the same category of mistake CLAUDE.md already warns about for model IDs: overclaiming certainty about something outside training data without actually checking it live.

The underlying numbers themselves are still the right call — pulling from a maintained reference is legitimately better than recalling pricing from memory — the issue was purely the wording implying a stronger verification than what occurred.

Fixed: reworded the callout to say the prices came from "a maintained, dated pricing reference," explicitly distinguish that from section 02's same-session live checks, and note it "carries whatever lag that table has against Anthropic's current published pricing" — on top of the callout's existing instruction to re-verify before quoting a real number to anyone, which was already accurate and didn't need changing.
