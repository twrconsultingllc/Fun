01Security and privacy

The CSP: one new address, two old ones gone
Confirmed clean

The test copy's policy is now default-src 'self'; script-src 'self' 'unsafe-inline' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline'; font-src 'self'; img-src 'self' data:; connect-src 'self' https://jarvis-cloud-gamma.vercel.app; object-src 'none'; base-uri 'none'; form-action 'none'. Compared with before, cdnjs.cloudflare.com, fonts.googleapis.com and fonts.gstatic.com are gone, and connect-src gains exactly the proxy's address. The suite pins the whole policy. It also checks that no other directive names Vercel, that the page names no other *.vercel.app address, and that the only requests to the proxy go through cloudFetch(). In Chromium, with the real CSP enforced, the proxy answered and a fetch to another Vercel address was refused (Refused to connect). A copy of the page with a second host in connect-src failed the suite.

Nothing on the page can turn it on
Confirmed clean

The page only ever reads /api/status (a GET) and asks /api/brain. Nothing it sends can switch anything: the switch is a Vercel setting. "Turn on your supercharger" gets "Only Tony can turn it on, and not from this page", and the page makes no request for it. The suite reads the code for anything sending supercharge: true or an /api/switch-style address and finds none. Only on: true means on: "true", 1 or a missing field read as off, and so does a status read that fails.

What the page sends while it's on
Open

Carried from review 72, now real. While the supercharger is on, a question nothing on the device understood goes through the proxy to Google with the skin, the last six exchanges with Gemini, any knowledge-pack facts about what it names, your name if you've given it this visit, the things you've told him this visit, and the command list. Requests go without cookies or a referrer (credentials: 'omit', referrerPolicy: 'no-referrer'), and Vercel sees the visitor's IP address. When it's off, the only request is /api/status, which carries nothing but the address and the page's origin. When it turns on he says so: "<name> has turned on my supercharger for you. While it's on, anything I can't answer on this device goes to Google's Gemini, with the last few things we said, and those answers are marked cloud." Each such answer is tagged CLOUD · GEMINI. This stays open because it's a real change to what leaves the device, which you chose. When it turns off he says "nothing you ask goes to Gemini", not "nothing leaves the device", because the browser's speech recognition still sends your voice to Google or Apple.

What the page accepts from the proxy
Fixed

The page doesn't trust the proxy, in case it's ever replaced or wrong. What Gemini says goes through cleanSay(): no <, >, backticks or ⟦⟧, so it can't make a link, a command button or markup, and it's cut at 320 characters. A crafted answer with an <a> and a command link came out as plain words with no button. Its picks go through the full brain's checkPick(): only BRAIN_PICKS (52 commands, none destructive, no waits), at most three, and only the first scene. An answer asking for proto:delete, settings:reset and wait:3 ran none of them, and said so. The owner's name and the model name are checked before he says them. The first draft only checked those on the proxy, so a status answer with an HTML tag for a name would have been read aloud and shown (as text, not markup, since chat lines are built from text nodes).

Fix: The page checks the name (letters, spaces and .'-, at most 30) and the model (gemini-3.5-flash-style) itself, and anything else becomes "My owner" and "Gemini". Copies of the page without the pick check, without the one-scene rule, or without the name check each failed the suite.
Only the Pages site may ask, but that isn't proof of who's asking
Open

With the supercharger on, anyone who finds the address can ask it questions, 12 a minute per address. The hard limits are the daily quota and budget on Google's side, which are yours to set (Session 17, step 3). The page's address for the proxy is public, as everything in this repo is. Keep the supercharger off when you aren't demonstrating it.

The service worker never touches the supercharger, or any other site or page
Confirmed clean

jarvis-test-sw.js is registered with the page itself as its scope (./jarvis-test.html), so it controls no other page: in Chromium, index.html and jarvis.html had no controller. Inside the page it answers only GETs for a fixed list of Jarvis's own files. Anything else gets no respondWith at all, so the browser handles it exactly as if there were no worker. That covers other sites (the proxy, the old CDNs), other pages and the full brain's weights. The suite runs the worker in a sandbox and checks 18 addresses it must leave alone, including both proxy routes as GET and POST. In Chromium every status check reached the proxy over the network, and no cache held anything from Vercel. Offline, the status read fails and the supercharger reads as off. Copies of the worker that answered other sites, answered POSTs, cached everything under /Fun/, or deleted other pages' caches on activation each failed the suite.

A stale copy can't hide a deploy or a changed library
Fixed

The page, the knowledge pack and the manifest come from the network first, checked past the browser's own cache (no-cache, since GitHub Pages sends max-age=600). The saved copy is used only when the network fails. Libraries are cached under jarvis-test-lib- plus LIB_HASH, a fingerprint of the 23 files the worker keeps, and activation deletes older versions. The suite works the fingerprint out again from the files, so a library changed without a new LIB_HASH fails it. In Chromium a changed page was shown on the next online load and then became the offline copy. When the worker was broken on purpose to fetch the page without no-cache, the suite still passed, because the check was matching the install step's own request.

Fix: The check now looks only at the request made for the page itself, and the same broken copy fails it.

Failures, checked against the real proxy
Confirmed clean

The jsdom suite's fake proxy is the real jarvis/cloud/lib/core.js, with a fake Gemini behind it that answers in Gemini's real shapes. So the page meets the proxy's real 503 {off}, its 429 for Gemini's quota and for its own rate limit (the 13th question in a minute from one address), its 502 when Gemini fails or answers in the wrong format, and its {blocked} answer. The page's request also has to pass the proxy's own field checks, or no answer comes back. Each failure gives a device answer, with a short line first saying why: switched off, busy, didn't answer, too slow (an AbortError after 20 seconds, as a browser's fetch gives), or unreachable (a TypeError).
