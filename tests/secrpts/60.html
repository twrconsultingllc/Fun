Review #60 — J.A.R.V.I.S. Session 9: memory foundation

The test copy now saves into its own IndexedDB database instead of localStorage. It copies what jarvis.html saved once, then never writes localStorage again. Beside the settings it keeps usage counts: a fixed event ID, a day number and a count. Days older than 90 roll up into all-time totals, and the visit streak is worked out from the counts. No wipe command was added, by decision.

01Security and privacy

Head block, CSP and the personal filter unchanged
Confirmed clean

git diff of jarvis-test.html starts inside the script, so the CSP, referrer policy, charset and description are what they were. The PERSONAL patterns and personal() have no changed line. IndexedDB isn't a network fetch and the CSP doesn't govern it, so no directive needed to change. No new outside host, script or link.

One place that saves, widened to IndexedDB
Confirmed clean

Every write goes through save(), which calls fits() on the record itself before queueing it. A setting has to be a key in STORE_KEYS holding text that passes personal(). A usage count has to be exactly {id, day, n}, with an ID from EVENT_IDS and whole numbers. A total has to be exactly {id, n}. The bookkeeping table takes only three named numbers. store() is still the only caller that writes a setting. The suite checks this in the source: no localStorage write call anywhere, exactly one 'readwrite' transaction, in flush(), flush reached only from save(), one pending.push(, and save('kept', …) with a value only inside store(). It also checks fits() directly: an unlisted ID, an extra field, a date string as a day, a key that doesn't match the record, a fractional count, and an unknown table are all refused.

Usage counts hold no words and no dates
Confirmed clean

29 fixed IDs, each a kind:name word that passes personal(). Commands are counted by kind only (intentEvent, chatEvent). Days are whole days since 1 January 2026, so 10 October 2026 is stored as 282. After eleven typed commands in jsdom, the database held no word that was typed. In headless Chromium the real database held {"id":"cmd:joke","day":282,"n":1}-shaped records only, and no date pattern.

The two copies can't change each other's saves
Confirmed clean

From the code: jarvis.html contains no indexedDB, and its scrubStore() only removes jarvis-* localStorage keys missing from its own list. The test copy now writes no localStorage at all, so there's nothing for that scrub to find, and jarvis.html needed no change. In headless Chromium over python3 -m http.server, with one browser profile: jarvis.html saved Panthers, a pink orb and a taught phrase; the test copy copied them in, switched to Morpheus and a blue orb, and kept those across a reload; localStorage stayed exactly as the main page left it; then jarvis.html opened in the same profile with Panthers, pink and its phrase, and the test copy's database read back identical before and after.

The first-run copy happens once and only reads
Confirmed clean

copyIn() runs only while the database has no copied mark, cleans each value the way the scrub does (a saved name, an unlisted key and a taught phrase with a phone number in it aren't copied), and then sets the mark. A second visit with different main-page settings keeps the test copy's own. The jsdom suite compares every localStorage key before and after.

Bad data already in the database is scrubbed
Confirmed clean

A database seeded with a saved name, a personal taught phrase, a phone number as a voice pick, an extra field in the settings, an unlisted event ID, an event with an extra field, an event with a date for a day, an unlisted total and an unknown bookkeeping key loads with only the clean settings and the one valid event left.

No wipe command added
Confirmed clean

As decided. The suite checks the page calls no clear() or deleteDatabase(). The memory core's history star explains that only clearing the site's data removes the counts, and forgetting it leaves them in place. This removed the old streak star, which could be forgotten before. Forgetting it now would mean deleting the counts, which is a wipe. That's recorded in the build plan.

Confirmed clean

fake-indexeddb 6.2.5, Apache-2.0, with no dependencies of its own, added as a dev dependency of tests/ only. tests/node_modules/ is git-ignored, so only the package.json and lock-file entries are published. They hold no secrets or personal data.

02Code quality

Start-up waits for the first read
Confirmed clean

The page runs on its defaults, reads the database, then hydrate() puts the saved skin, settings, voices, phrases and mic note in place. finishBoot() waits for that, so the greeting, the streak line and the opening scene use saved values. The suite holds the database closed with a gated factory: two taps on Skip give no greeting, and releasing it gives one greeting, in the saved skin and colour. A database that never answers is given up on after 4 seconds, and he greets you and says nothing can be saved. With no IndexedDB at all, the page runs, uses the main page's values for the visit, and still writes no localStorage.

Roll-up and streak, checked from first principles
Confirmed clean

The day numbers in the suite are worked out independently of the page. With records 89, 90 and 95 days old, only the 89-day-old one stays by day, and the others' counts are added to the totals (10 + 3 = 13 jokes). From the counts alone: yesterday and the day before give 3, a missed day gives 2, a day with only a joke counts. 95 days in a row before today give 96, with 6 in the carry, and 97 the next day. An old 120-day jarvis-streak from yesterday becomes 121: 90 days kept by day and 31 in the carry and the visit total.

The suite fails when the code is broken
Confirmed clean

Each of these changes to the page was run against the suite, which failed every time: keeping 91 days, copying in on every visit, removing localStorage after the copy (written so the source check wouldn't see it), dropping the carry, greeting before the read, skipping the event checks in fits(), and the scrub skipping events. Failing checks per change: at least 6 for 91 days, 4 for copying every visit, 3 each for moving instead of copying, dropping the carry, greeting early and unchecked events, and 1 for the scrub skipping events.

Chat answers are counted by an approximate kind
Open

chatEvent() sorts a chat answer into help, time, date, joke, fact, coin, die, math or other with its own short list of patterns, not by asking brainKnown() which branch answered. A mixed phrase like "hello, what time is it" is answered as a hello but counted as cmd:time. Only the kind is stored either way, so this affects how accurate later sessions' favourites are, not privacy. Worth tightening if Session 11 relies on chat kinds.

A save that fails is not reported
Open

The page keeps its copy in memory and writes to the database a moment later. If the browser refuses the write (storage full, or the tab closed before the transaction finished), the page still behaves as if it saved for the rest of the visit, and the next visit doesn't have it. localStorage had the same gap for a full disk. Nothing personal is affected. A later session could listen for the transaction's error and say so.
