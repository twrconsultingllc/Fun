02Findings — fixed

Primary button text failed WCAG AA contrast in dark mode
Fixed

All ten interactive pages share one :root palette. Computed WCAG relative-luminance contrast ratios (not eyeballed) for every foreground/background pairing the CSS actually produces. button.btn renders white text (#ffffff) on --accent; in dark mode --accent was #5b8def, giving a ratio of 3.23:1 against the WCAG AA threshold of 4.5:1 for text this size (0.88rem / ~13px, bold — below the "large text" exemption). This affects every primary button across all ten pages: Send, Copy memo, Run expansion analysis, View result.

Fixed: darkened --accent's dark-mode value to #296aea (same hue, same use everywhere else — decorative borders and hover states, which carry no contrast requirement) across all ten files identically. New ratio: 4.83:1, clears AA. Light mode was already compliant (5.63:1) and untouched. Re-ran the full test suite (787 assertions) after the change to confirm nothing else regressed.
Two status-badge components failed AA in one theme each
Fixed

The badge/pill backgrounds are hardcoded rgba(r,g,b,alpha) triples (not theme-aware CSS variables), while their text color does switch per theme — so the actual rendered contrast in each theme had to be computed from the real pairing, not assumed symmetric. Two components that are actually instantiated in shipped markup came up short:

  • .badge.good ("done" checklist items, "Reviewed ✓" badges, and the identically-styled .reviewed-badge in the hybrid variation) — 4.19:1 in light mode (passed dark at 4.83:1).
  • .variant-badge (the "Variation A/B/C" pill in every page's top bar) — 4.28:1 in dark mode (passed light at 4.95:1).
Fixed: lowered the badge family's background alpha from 0.15 to 0.06 (.badge.done/.badge.good, .badge.pending/.badge.warn, and .reviewed-badge) and .variant-badge's from 0.14 to 0.10, applied identically across every file that defines each rule. Recomputed: badge-good now 5.65:1 (dark) / 4.52:1 (light); badge-pending/warn now 6.48:1 (dark) / 5.06:1 (light); variant-badge now 4.55:1 (dark) / 5.15:1 (light) — all clear AA with margin. Verified the palette stayed byte-identical across all ten files after the edit (a script comparison of every --custom-property value, not a visual diff), and re-ran the full suite.
The chat variation's message input had no accessible name
Fixed
mockup-chat-home.html's #chat-input relied on its placeholder alone, which screen readers don't treat as a label. The hybrid variation's equivalent input already carried aria-label="Ask the assistants" — the chat variation was the one inconsistent page.
Fixed: added the same aria-label="Ask the assistants" to the chat variation's input, matching the standard the hybrid variation already set.

03Findings — open

.badge.missing/.badge.danger still fails AA in dark mode, but is unreachable
Open

The same badge family defines a third variant, .badge.missing, .badge.danger { background: rgba(224,100,90,0.15); color: var(--danger); }, at 3.79:1 in dark mode (light mode already passes at 4.50:1). Grepped every page's shipped markup — including the JS template strings that build badge classes dynamically (cls, status.cls, and similar computed values) — for any instance of the danger or missing class: none exists anywhere in this batch. Every checklist item in the sample data is only ever done or pending, so this variant is defined but never rendered.

Open, not fixed: left this alone rather than force a fix with nothing real to verify it against. The same alpha: 0.06 treatment does not clear 4.5:1 for this specific color at any alpha above ~0.01 (a near-invisible tint), so a real fix needs either a different visual treatment (e.g. moving the semantic color to a small dot/icon instead of the full badge background+text) or simply removing the unused rule — a decision for whoever first actually uses a "missing"/error state in a future variant, not something to guess at now.

04Scope & regression checks — confirmed clean

No inline event handlers, no external resources, no fetch() calls
Confirmed clean
Grepped all eleven new pages for on*=" attributes, off-origin src/href, @import, CDN references, and fetch( — zero matches. Every page's data (STATES, CLIENTS, PIPELINE_STEPS, MEMO_TEXT) is a canned inline JS object; nothing is fetched, matching this batch's design intent (a scripted, offline prototype, not a live agent).
Free-text user input never reaches innerHTML
Confirmed clean
The only two pages that echo typed text back into the DOM (mockup-chat-home.html's chat thread and mockup-hybrid-home.html's docked chat panel) both render the user's message with element.textContent = text, never string-concatenated into innerHTML. Every innerHTML assignment across all eleven pages builds its markup from the pages' own canned data, not from anything a visitor types — confirmed by grepping every innerHTML site against input-value variable names.
CSP matches each page's actual script needs, nothing wider
Confirmed clean
The ten interactive pages carry script-src 'self' 'unsafe-inline' — a loosening study/ui-plan.html's own "Decisions already made" section pre-approves for exactly this case (an inline-script page in this repo's existing single-file-toy pattern), not something invented for this batch. ui-mockups.html is a static page with zero <script> tags and keeps the stricter script-src 'self' baseline. Confirmed the exact head block (charset, viewport, referrer, CSP, description) is present and correctly scoped on all eleven pages; no page widens img-src, connect-src, or font-src beyond 'self', since none of them load an image, make a network request, or use a web font.
The chat form can't navigate or submit anywhere
Confirmed clean
mockup-chat-home.html is the only page with a real <form> (the chat input row). Its submit handler calls event.preventDefault() before doing anything else, so it never triggers a real navigation or request — and the head block's form-action 'self' would contain it even if that weren't true.
Every internal link resolves to a real file in the batch
Confirmed clean
Extracted every same-directory href="*.html" across all eleven pages and checked each target exists on disk. One deliberate exception, already handled honestly rather than left as a silent dead link: mockup-dash-clients.html only links Meridian's row to a detail page, since Northstar's and Quickship's rows have no built detail page in this mockup — those two rows render a small "detail view not built in this mockup" note instead of a broken link.
The shared palette is byte-identical across all ten interactive pages
Confirmed clean
Per the approved plan, the three variations were required to share one visual identity so the comparison is about structure, not skin. A script parsed every --custom-property declaration out of each page's <style> block and diffed the resulting maps pairwise — not a visual read, an actual value comparison. All ten pages matched exactly, both before and after the two contrast fixes above (which were applied identically to every file that defines the affected rule).

05Test coverage

Five new suites, 58 assertions, registered in tests/run.mjs
Confirmed clean

Unlike battle-bots-V2 or the WebGL pages, these are plain interactive HTML/CSS/JS with no canvas or GL context, so they run end to end under jsdom the same way tricalc.html does. Each page with a scripted pipeline run exposes a window.__mockup<Variant> hook whose runPipeline() replays the reveal logic with no setTimeout delay, so the DOM state after a run is asserted deterministically. mockup-hybrid.dom.test.mjs specifically pins the hybrid variation's actual differentiator — that running the pipeline cross-highlights the matching Texas/Florida/Illinois tiles in the case-file panel — not just that the trace renders.

Full suite: 787 passed, 0 failed (729 pre-existing + 58 new), run both before and after the contrast fixes in this review.

This is a static-analysis and jsdom-test review, not a rendered-browser check — no browser is available in this environment to screenshot the result (see CLAUDE.md's "No browser or WebGL rendering" note), so every contrast ratio above was computed from the actual shipped hex/rgba values via the WCAG relative-luminance formula in a throwaway Node script, not eyeballed. Worth a quick look on the live pages once deployed.
