01Security

Neither page had a CSP, Referrer-Policy, or description meta tag
Fixed

Both pages were written and published without the <meta http-equiv="Content-Security-Policy">, <meta name="referrer">, and <meta name="description"> tags every other page in this repo carries — a real gap against the convention the site-wide scan (01.html) established, not a stylistic choice.

PageExternal resources actually usedCSP shape now applied
study/plan.htmlNone — no external fonts, scripts, or images; one plain <a href> to nmlsconsumeraccess.org (not a CSP-governed resource load)script-src 'self' (no 'unsafe-inline' needed — neither page has a <script> tag at all); style-src 'self' 'unsafe-inline' (both use a few inline style="…" attributes)
study/usecase.htmlSame — noneSame shape

This is actually a tighter policy than the rest of the repo's pages get, since those load Google Fonts and/or a CDN script and need 'unsafe-inline' on script-src for their inline logic — these two are pure static reference documents with zero external dependencies and zero script of any kind.

Fixed: added the CSP, referrer, and description meta tags to both files' <head>, tailored to their actual (minimal) resource use rather than copy-pasted from a page that loads fonts/scripts they don't have.
External NMLS link had no target/hardened rel
Fixed
Both pages link to nmlsconsumeraccess.org with rel="noopener" but no target="_blank" — since the link opened in the same tab, noopener was doing nothing (it only matters for a link that opens a new browsing context), and following it navigated the reader away from the study page entirely with no referrer protection.
Fixed: both links now use target="_blank" rel="noopener noreferrer" — opens in a new tab (keeps the study page available), noopener now actually applies, and noreferrer stops the study page's URL from being sent to NMLS in the request.
No secrets, no inline handlers, no scripts, no forms, no exfiltration path

  • No API keys, tokens, or .env references — nothing here talks to a server at all.

Not an issue

No X-Frame-Options / Permissions-Policy on GitHub Pages
Open

Same architectural gap the site-wide report already documented (row 2/row 4 of 01.html): GitHub Pages has no meta-tag equivalent for either header, so it can't be set here regardless of what either page needs.

Realistic severity here is low: both pages are read-only reference documents with no forms, no state, no sensitive browser permission requests (unlike signal-scope.html's microphone case in 02.html), and no user input of any kind. An attacker could iframe either page for a visual clickjacking overlay, but there is no click-triggered action on either page for such an overlay to actually weaponize — at worst it's a static page framed inside another site, not a route to tricking a user into an unwanted action.

Not fixed, same reason as the site-wide report's rows 2 and 4: architecturally blocked on GitHub Pages, not unaddressed. If either page ever moves to a host that sets real response headers, add X-Frame-Options: DENY there, mirroring the vercel.json pattern already in place for both battle-bots apps.

02Code quality & accessibility

Several accent colors failed WCAG AA contrast in light mode
Fixed

Computed actual WCAG relative-luminance contrast ratios (not eyeballed) for every text-color CSS variable against every real background it's used on in light mode, including the composited badge/callout backgrounds (an rgba() tint over its actual parent color, not the flat panel color alone). Several failed the 4.5:1 AA threshold for normal-weight/small-bold text:

PageColor / usageWorst-case backgroundBeforeAfter
plan.html--accent/--link (orange links, weight-percent table cells)tinted badge bg over table stripe4.04–4.24:14.64–5.37:1
plan.html--good ("Verified" badge text)tinted badge bg over table stripe4.30:14.66:1
usecase.html--accent/--link (green links, step-circle numbers)page background3.84:14.63:1
usecase.html--accent-2/--warn-border (section eyebrows, disclaimer label)tinted disclaimer box over page bg4.20–4.34:14.63–5.44:1

Dark mode was checked the same way and was already comfortably clear (5.9–10:1 on every pair) — the failures were light-mode-only.

Fixed: darkened each affected light-mode color by hue-preserving lightness reduction until it cleared 4.5:1 against its actual worst-case background (not just the flat page background — the tinted rgba() composite a color sits on in a badge or callout can be lighter than the plain background, which is what made the first pass of colors look fine against the page background alone but still fail in a badge). Re-verified every pair after the change; nothing dropped below 4.6:1 anywhere it's actually used. Dark-mode values were left untouched since they already passed.
