Review #31 — ble-scan-test.html

A new, minimal test page for Chrome's experimental Web Bluetooth scanning API (navigator.bluetooth.requestLEScan). It lists nearby Bluetooth LE advertisements and marks the tracker formats Sentinel recognises, to find out whether a browser version of Sentinel can scan at all. Not linked from index.html: it's a test page, opened by its URL.

01Security

Advertised names are rendered as text, never parsed
Confirmed clean

A Bluetooth device's name and data are chosen by whoever built it, so they're hostile input. Every value is written with createElement and textContent. Grepping the page for innerHTML, outerHTML, insertAdjacentHTML, document.write, eval(, new Function and inline on*= handlers finds nothing. The suite feeds in a device named <img src=x onerror=alert(1)>: no img element is created and the name appears as plain text.

Nothing leaves the page
Confirmed clean

The CSP is the repo's usual one with connect-src 'none' instead of 'self', so the page can't make any request, even to its own origin. It has no external scripts, stylesheets, fonts or images, and no links. Grepping for fetch(, XMLHttpRequest, WebSocket and localStorage finds nothing, so sightings are kept only in memory and are gone when the tab closes. The suite asserts the CSP, the referrer policy and zero script[src].

Scanning is user-started, visible-only and passive
Confirmed clean

A scan starts only when Start is pressed, after Chrome's own permission prompt. It stops when the tab is hidden (visibilitychange) or Stop is pressed. requestLEScan only listens to advertisements, so the page never connects to or sends anything to any device. Chrome gives each device an opaque ID per site rather than its real Bluetooth address, and the page shows only that.

Permissions-Policy can't be set from a meta tag
Open

A Permissions-Policy: bluetooth=(self) header would stop any page that frames this one from using its Bluetooth permission. GitHub Pages can't send custom headers, and the policy has no meta-tag form. The risk is small: the page stores nothing and sends nothing, and Chrome blocks Bluetooth in cross-origin frames by default. Architecturally blocked, the same as the other header-only policies in 01.html.

02Code quality & accessibility

Tracker rules agree with Sentinel
Confirmed clean

The five formats are copied from Sentinel's detection/TrackerSignature.kt: Apple Find My (company 0x004C, payload starting 12), Samsung SmartTag (0xFD5A), Tile (0xFEED), Google Find Hub (0xFEAA service data, frame 0x40 or 0x41) and Chipolo (0xFE33). The suite also checks what must not match: an iPhone's 0x004C 10… nearby message, a plain Eddystone FEAA 10… beacon and Fast Pair 0xFE2C.

Light-theme button contrast
Fixed

The first draft used dark text on the light theme's blue Start button: #0b0e14 on #1565c0 is 3.36:1, below the 4.5:1 AA minimum. It now uses white in the light theme (5.75:1) and keeps dark text in the dark theme (7.87:1 on #5aa9ff). Other measured pairs: body text 14.19:1 (dark) and 15.9:1 (light), dim text at least 5.49:1, status colours at least 5.05:1. All AA or better.

Fix: added a --on-accent colour token, dark in the dark theme and white in the light theme.
Checked in headless Chromium
Confirmed clean

Loaded at 390×780 in the container's headless Chromium, in both colour schemes. Without the flag, the checks show Web Bluetooth and scanning as missing and Start is disabled. With --enable-experimental-web-platform-features, all three checks pass, Start is enabled, and pressing it reports NotFoundError: Bluetooth adapter not available. cleanly, because the container has no Bluetooth. No page errors, and no sideways scroll (scrollWidth 390). Status messages are in an aria-live region, and all controls are real button and label elements.

A real scan hasn't been tested
Open

Nothing here has seen a real advertisement, because the container has no Bluetooth adapter. Still unknown: whether Chrome on the phone returns manufacturer and service data with acceptAllAdvertisements, how often events arrive, and whether a real AirTag or SmartTag gets marked. The new ble-scan suite (25 assertions) covers the logic with hand-built events. The full suite is 1331 passed, 0 failed. Left open until the page is tried on a phone with the flag on.

This is a static snapshot, not a live check. The page was checked in jsdom and headless Chromium only, and the container can't fetch *.github.io, so the deployed copy has to be checked on a real device. See 30.html for the previous review.
