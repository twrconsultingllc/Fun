01Security

CSP, referrer, description, and viewport meta tags present and correctly scoped
Confirmed clean
build-plan.html was written with the full meta-tag set from the start (03.html had to add these after the fact to the two earlier study pages) — Content-Security-Policy, referrer, and description all present in the <head>, matching the same minimal shape as plan.html and usecase.html: script-src 'self' with no 'unsafe-inline' (there is no <script> tag on the page at all), style-src 'self' 'unsafe-inline' for its handful of inline style="…" attributes.
No external resources, scripts, forms, inline handlers, or secrets
Confirmed clean
Grepped the file directly: no <script>, no on*="…" handler, no eval(/fetch(/XMLHttpRequest, no <form>, no API key or .env reference, and — unlike the two earlier study pages — no external href="http…" link at all. The only link on the page is a relative, same-origin reference to plan.html (plus seven anchored references into specific sections of it), which needs no target/rel hardening the way the external NMLS link does — that hardening exists specifically for links that open a new browsing context to a different origin, and this one does neither.
Cross-page anchor links actually resolve, not just internal ones
Confirmed clean

This page introduces something the earlier two didn't have to worry about: links that jump into a specific section of a different file (plan.html#dataset, plan.html#clients, etc.), rather than only within the same page. A typo or a stale reference here fails silently — the browser just scrolls to the top of the target page instead of erroring — so it's a real risk category, not a formality.

Extracted all seven href="plan.html#…" references and checked each fragment against plan.html's actual id attributes directly, rather than trusting that the two pages were written to agree: #versions, #dataset, #clients, #queries, #task, #cost, and #mapping all exist. Also re-ran the same-page checks 03.html established: all 12 of build-plan.html's own section id values are unique, and all 12 nav.toc entries resolve to one of them.

Every file name this page references was cross-checked against plan.html's actual directory layout — one didn't match
Fixed

This page's whole premise is sequencing plan.html's design, so a file name that drifts from that source of truth is a real content bug, not a stylistic quibble — it would send someone building Session 2 looking for a test file plan.html never named. Extracted all 33 distinct .mjs/.md/.json file references from build-plan.html and checked each one against plan.html's directory-layout section verbatim.

32 matched. One didn't: Session 2 introduced tests/get-state-requirements.test.mjs to unit-test the state-lookup tool directly, ahead of the MCP server existing — a reasonable sequencing choice (test a tool's own exported function before wiring it into a server), but plan.html's tests/ listing never named that file; its only per-concept test files are agent-loop.test.mjs, structured-output.test.mjs, context-budget.test.mjs, mcp-server.test.mjs, client-tools.test.mjs, and hooks.test.mjs.

Rather than quietly rename it out of build-plan.html to avoid the mismatch, the underlying idea is correct and worth keeping — a state-lookup unit test ahead of the MCP server is good sequencing, not a mistake.

Fixed: added tests/get-state-requirements.test.mjs to plan.html's directory-layout section (07) as a real entry, with a note on why it exists separately from mcp-server.test.mjs's later round-trip coverage of the same tool — so the two pages now agree, instead of build-plan.html quietly diverging from the document it's supposed to be sequencing.
Time estimates and "done when" language checked for fabricated precision
Confirmed clean
Read every session's time estimate and completion criterion specifically looking for false precision — a plan like this is easy to write with confident-sounding numbers that are actually guesses. Every estimate is a range ("45–60 min," "90–120 min") rather than a fabricated point figure, and every "Done when" callout is a concrete, checkable condition (a test suite passing, a specific manual run producing a specific kind of output) rather than a vague "feels done" statement.
