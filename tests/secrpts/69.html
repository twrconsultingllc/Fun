The failure: a GPU read cut off mid-answer
Partial

With "why?" in place, you reported the error: AbortError: Failed to execute 'mapAsync' on 'GPUBuffer': Buffer was unmapped before mapping was resolved. The wording is Chrome's (Chrome or Edge, desktop or Android). In the bundled WebLLM 0.2.85 runtime, the only unmap() is on the staging buffer it reads each token's results through. When a buffer can't be created (out of memory, for one), tryCreateBuffer() destroys the whole GPU device, which cancels every read in flight. So the likeliest cause is the chip running short of memory with the model, its working memory and the rest of the page all on it. The page treated this as an ordinary error. The engine stayed "on" on a dead device, so every later question failed the same way.

Fix: An AbortError, or anything naming mapAsync, an unmapped or destroyed buffer, or a lost device, now turns the full brain off and unloads it, freeing its memory, as a lost device already did. He says so, and suggests closing other tabs and installing it again (it comes from the browser's cache, so that's quick). "Why?" still names the error. The model's context window is also cut from 4,096 tokens to 2,048. The longest prompt the page sends is about 600 tokens of instructions and facts, plus six short turns and a 160-token answer, so 2,048 is still plenty. It roughly halves the memory set aside for the model's working memory: by its configuration (28 layers, 8 key-value heads of 128 values, 16-bit), about 470 MB at 4,096 tokens and 235 MB at 2,048. The suite pins the exact Chrome error and checks that it ends with the full brain off and unloaded.

Still open: whether the smaller window is enough to stop the error on your device. This container can't run the model, so that needs you to try it.
