Review #62 — J.A.R.V.I.S. Session 8: moving settings to another device

The test copy can now carry its settings to another device two ways: a backup file, jarvis-settings.json, and a QR code shown on one device and scanned on the other. Both carry what the database holds: the kept settings (not the mic note), the protocols and, in the file, the usage counts. A restore merges, and every record goes back in through save(), so fits() checks it as if it were new. The QR encoder and decoder are self-hosted in jarvis/qr/ and loaded with SRI hashes. jarvis.html is unchanged.

01Security and privacy

Head block and CSP unchanged
Confirmed clean

git diff of jarvis-test.html touches no <meta> line except the description, which now mentions moving settings with a backup file or a QR code. The suite now pins the whole CSP string to what it was before Session 8, so a new host can't be added without that check failing. The QR files come from this site ('self'), and the download is a blob: link, which Chromium followed with no CSP change and no Refused message.

QR encoder and decoder are self-hosted, pinned and loaded with SRI
Confirmed clean

jarvis/qr/qrcode.js (qrcode-generator 1.4.4, MIT) and jarvis/qr/jsQR.js (jsqr 1.4.0, Apache-2.0, with its LICENSE-jsQR) are unmodified copies from npm. Neither uses eval or new Function (grepped), and neither makes a network request. The suite pins both by SHA-256 and checks the page's sha384- SRI hashes against the files, and jarvis/qr/README.md lists the same hashes. The page adds each <script> only when a code is shown or scanned, with integrity, crossorigin and referrerpolicy=no-referrer. In Chromium, a copy of the encoder with one byte changed was refused by the browser with an integrity error, and Jarvis pointed to the backup file instead.

A Storage.prototype spy counted zero localStorage writes across a backup, a restore, a hostile restore, a QR show and a scan, and in Chromium device B's localStorage stayed empty.

A restore is checked exactly as a first save
Confirmed clean

In a mixed file only the good records went in, and he counted the six he left out.

Protocol names were trimmed before they were checked
Fixed

Found by the suite during this session. The first version of the restore passed each name through protoName() before saving, which drops a leading "my", "the" or "a". So "my mom" was saved as "mom", which passes personal(), and __proto__ became "proto". Making a protocol checks the name as spoken, so this was a way round that check.

Fix: A restored name must already be in its saved form: it goes to save() unchanged, and fits() refuses it unless protoName(n) === n. The suite's hostile file includes both names, and the mutation that brings the trimming back fails seven checks.
personal() could take seconds on a long value
Fixed

Found while running the hostile-file checks, which took three and a half minutes. Two of personal()'s patterns backtracked: the email pattern [^\s@]+@… and the web-address pattern \b[a-z0-9-]+\.(?:com|…) both rescan to the end of the text from every starting point. Measured in Node: 48.8 s for 150,000 letters (email), 50.9 s and 48.8 s for 75,000 repetitions of "a-" (email and web). The values a page could save until now were short, but a restore file can hold a 100,000-character phrase list, so a hostile file could have frozen the page.

Fix: The email pattern now needs one character before the @ ([^\s@]@), which is exactly what the old pattern needed, so it matches the same text. The web pattern looks at one character before the dot ([a-z0-9-]\.(?:com|…)\b), which matches everything the old one did and a few rare extra cases, so it can only refuse more. Five 98,000-character worst cases now take 9 ms in the suite. On top of that, a restored setting over 100,000 characters or a protocol name over 30 is refused before any check runs (a 300,000-character "the the the…" name would otherwise have made protoName()'s loop slow too). The old email pattern, put back, makes the suite fail with a 63-second check.
Restoring never wipes
Confirmed clean

Decided in the session: a restore merges. Nothing already here is deleted. A setting, taught phrase, voice pick or protocol of the same name is replaced; everything else is kept. Counts take the larger of the two for the same day, so restoring the same file twice changes no count (checked). There's no save(…, undefined) in the restore code (grepped). A device with its own units, phrase, voice, two protocols and counts kept all of them after a restore, in the suite and in Chromium's real IndexedDB. The mutation that clears protocols before restoring fails eight checks.

The camera follows the threat scan's rules
Confirmed clean

Only while scanning; getUserMedia({video:{facingMode:'environment',…},audio:false}), pinned in the suite; the decoder loads first, so a failed load never leaves the camera on. It stops when a code is read, on CLOSE, Escape or "close", when the tab is hidden, after a minute with no code, and if the panel closes while the camera is still starting. Checked with a fake camera in the suite (every track stopped) and in Chromium with the fake device (no live track after the read, no audio track at all). A QR code that isn't a settings code is ignored and doesn't restore anything. Nothing is drawn to a canvas that's kept, and there's still no toDataURL, toBlob or MediaRecorder; the only .download= in the page is the backup's.

No innerHTML, no user text as markup
Confirmed clean

The panel is built with createElement, textContent and dataset; the suite's "no innerHTML anywhere in the page" check passes. The file picker accepts .json only, and its text is only ever passed to JSON.parse. Replies quote nothing from the file: they count what was restored, so a hostile file can't put a ⟦label|command⟧ marker into the chat.

A backup file isn't encrypted
Open

By design, as the plan said: it holds only what personal() lets through, so there's nothing to encrypt. But personal() is a pattern filter, so a taught phrase or protocol name that's personal in a way it doesn't recognise could be in the file, and the file sits in your downloads. The same is true of what's saved in the browser today. Left as it is.

jarvis.html has the same slow patterns
Open

jarvis.html still has the old email and web patterns. Nothing outside the page can give it a long value (it only checks what you type, phrases capped at 120 characters, and its own localStorage), so it isn't reachable there. The rewrite goes across when the test copy is promoted. Left for the promotion rather than changing the main page now.

02Code quality

Phone speech without punctuation
Confirmed clean

Every command is matched on normPhrase(), which drops punctuation. The suite pins 28 phrasings, punctuated and not, with "jarvis" in front and "please" after: "back up my settings", "restore my settings from the backup file", "send my settings to my phone", "scan the settings code" and the rest. Twelve near misses aren't transfer commands, among them "scan the room", "scan this barcode", "reset my settings", "go back" and a bare "back up". None of them can be a protocol step, and he says why.

Two devices, in a real browser
Confirmed clean

Headless Chromium over the local server, with two separate browser profiles. Device A saved jarvis-settings.json through a real download started by voice, and showed its code (326 bytes, QR version 12). The code was cut out of a screenshot of A's screen and made into the fake camera's video with ffmpeg. Device B scanned it with the self-hosted jsQR (headless Chromium on Linux has no BarcodeDetector), at 1280×800 and 390×844, then restored the downloaded file through the real file picker. Both landed in B's real IndexedDB, merged with B's own settings and protocol. No page errors or CSP violations.
