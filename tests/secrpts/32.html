Review #32 — sentinel-web.html

A new page: a browser version of the Sentinel Android tracker detector, with the features the user picked (Sentinel feature numbers 1, 4, 6, 7, 8, 11, 12, 13 and 14). It scans for Bluetooth LE devices while the page is open, tags each sighting with the location, groups fixes into places, flags a device seen at several places using the app's own scoring, and has Nearby, Flagged and Device Detail screens, an OpenStreetMap map and a hot/cold finder. Also a new link on index.html.

01Security & privacy

Advertised data is only ever shown as text
Confirmed clean

Device names and broadcast bytes come from whoever built the device, so they're hostile input. The page builds every element with createElement and textContent through one el() helper, which sets attributes with setAttribute and never parses HTML. The suite asserts the page source has no innerHTML, outerHTML, insertAdjacentHTML, document.write, eval( or new Function. It also feeds in a device named <img src=x onerror="window.__pwned=1">: Device Detail shows the name as text, no img[onerror] exists, and window.__pwned stays unset.

Nothing is sent anywhere; data stays in this browser
Confirmed clean

The CSP is the repo's usual one with connect-src 'none' (no fetch, XHR or WebSocket to any host, including the page's own), form-action 'none', and img-src 'self' https://tile.openstreetmap.org. The page has no external scripts, styles or fonts. Sightings, places, devices and flags are kept in the browser's IndexedDB on the device. Sightings older than 7 days are deleted when the page opens, and a "Delete all data" button clears all four stores. In headless Chromium the data survived a reload: 3 devices, 6 sightings, 3 places and 1 active flag before and after. The page uses no localStorage or cookies.

The map tells OpenStreetMap which area is being viewed
Confirmed clean

Device Detail draws its own map from OpenStreetMap tiles, with no mapping library, so nothing is loaded from a CDN. Each tile request tells tile.openstreetmap.org the area shown, and the page's referrer policy sends the site's origin, which OSM's tile policy asks for. This is the same exception the Android app makes for its map. The setup panel states it, and tiles load only when a device page with places is open. Every tile URL is built from numbers the page computes (/{z}/{x}/{y}.png), never from advertised data. The suite checks that all tiles come from that host, and that the attribution link opens in a new tab with rel="noopener noreferrer".

Location history on the device isn't locked
Open

The stored sightings are a location history. Anyone who can use the unlocked tablet's Chrome can open the page and see them. The Android app plans an app lock and has a discreet mode, but the user didn't pick those features (Sentinel 18 and 19) for this version. What limits it now: 7-day retention and the Delete all data button. Left open as a known gap, not a bug.

Scanning is passive, visible-only, and the finder is limited to flagged trackers
Confirmed clean

requestLEScan only listens. The page never calls connect() or requestDevice(), so it never connects to or writes to a device. Scanning starts only on a button press, behind Chrome's permission prompt, and stops when the page is hidden. Chrome shows each device as an opaque ID for this site, never its real Bluetooth address. The hot/cold finder follows the app's guardrail: it's offered only for an active flag, stops after 5 minutes (the countdown was checked ticking in Chromium: 300, 297, 295 s), stops when leaving the screen, and stores nothing of its own. The suite asserts there's no "Find it" on a device that isn't flagged.

Permissions-Policy can't be set on GitHub Pages
Open

Same as 31.html: a Permissions-Policy header limiting bluetooth and geolocation to this origin has no meta-tag form, and GitHub Pages can't send custom headers. Chrome already blocks both features in cross-origin frames by default. Architecturally blocked.

02Code quality & accessibility

Detection rules match the Android app
Confirmed clean

Ported line by line from Sentinel's LocationClusterer, RotationLinker, FlagScorer, TrackerCorrelationEngine, FlagDecision, FindMyPayload and ProximityTracker, with the app's defaults: 150 m places, 24 h window, 3 places over 20 min, 30 min visit gap, Medium sensitivity (55). Chrome's per-site device ID stands in for the address, so, as in the app, only a recognised tracker is linked across an ID change. The suite checks each rule against values worked out by hand from the Kotlin, for example 15 + 20 + 0 + 35 = 70 for the scripted tag. Raising the threshold to 75 and removing the halving turned 8 of the 71 checks red, so they test real behaviour.

One wrong expectation in the new suite, corrected by re-deriving it
Fixed

The first run had 2 failures, both in the finder checks. The test had fed in "another" tag of the same family 10 dB from the target and expected it to count as a second device. The app's linker treats a same-family device within 12 dB as the target after an address change, and the page did exactly that, so the expectation was wrong, not the page. The test now uses a device 25 dB away, with a comment saying why.

Fix: the test was corrected, not the page. The repo's rule is to re-derive a failing expectation before changing it.
Contrast, layout and controls
Confirmed clean

Measured WCAG ratios for every colour pair: body text at least 13.21:1, dim text at least 5.2:1, buttons 7.87:1 (dark theme) and 5.75:1 (light), status colours at least 5.05:1, flag count badge 9.54:1 and 5.05:1, map markers 6.96:1 and 5.62:1. Checked at 400 px in both themes in headless Chromium, with no sideways scroll (scrollWidth 400). Controls are real button elements with visible focus outlines. The tabs use role="tab" and aria-selected, status chips and notices are in live regions, and the map has an aria-label plus a table listing the same places.

Console message when leaving the page with a map on screen
Open

In headless Chromium, with tile requests stubbed, leaving or reloading the page while Device Detail's map is showing logs one "Refused to connect … violates connect-src 'none'" per tile. While the page is open the tiles load as normal image requests with no errors (request type image, logged). A bare page with the same CSP and an <img> didn't reproduce it, and dropping loading="lazy" didn't change it. The message looks harmless and only appears on the way out, but the cause wasn't found, so it's left open instead of guessed at.

index.html link, with a new suite
Confirmed clean

One new section (section-24, "Sentinel Web") and its selector added to the existing centring rule. Nothing else changed. Not yet tested on a real device
Open

Everything above used jsdom or headless Chromium with a simulated Bluetooth adapter and GPS, and stand-in map tiles, because the container has no radio and can't reach tile.openstreetmap.org or *.github.io. Still unknown: how often Chrome delivers advertisements on the tablet, whether Chrome's ID for a device survives its address rotation, the tablet's location accuracy indoors, and the real map. The user's ble-scan-test.html run showed devices arriving on the tablet, so scanning itself works there. The browser can't scan in the background at all, which the page states. Left open until it's been used on the tablet across a few places.
