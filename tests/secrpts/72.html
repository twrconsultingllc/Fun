01Security and privacy

The key stays on Vercel
Confirmed clean

The key is read from GEMINI_API_KEY in Vercel and goes to Google only in the x-goog-api-key header, for both the question and the model list. The suite checks every URL the proxy fetched for the key and finds none. Any error text passed back is run through scrub(), which redacts AIza… keys, key= and token= values, the header, and Bearer tokens. A Google 403 naming the key, and a network error naming it, both came back with [redacted] in its place. core.js never reads process.env itself (the suite checks), so only api/_app.js touches the environment.

Off unless you turn it on, and off when in doubt
Confirmed clean

The switch is supercharge: true (or "on") in Edge Config. Anything else is off: a missing item, "yes", Edge Config unreachable, Edge Config refusing the token, an unreadable EDGE_CONFIG, an until time that has passed or can't be read, or no Gemini key. Each of those is a check. While it's off, /api/brain answers 503 and Google is never asked. The Edge Config token goes in a Bearer header, as Vercel's own library sends it, never in the URL.

Only the Pages site may ask, but that isn't proof of who's asking
Open

/api/brain refuses any request whose Origin isn't https://twrconsultingllc.github.io (or one listed in ALLOWED_ORIGINS, where * is ignored), including requests with no Origin at all. A browser can't fake that header, so no other website can use your key. A script can, though. While the supercharger is on, anyone who finds the address can ask it questions in Jarvis's voice. They get short spoken-style answers (at most 512 tokens), 12 a minute per address, which resets when Vercel starts a new instance. A passphrase would stop that, and you chose not to have one, for the demo. So the hard limits have to be on Google's side: a daily request quota on the key's project, and a budget alert. Both are in your setup steps. This stays open until you've set them. At about $0.003 a question, a quota of 1,000 a day caps a bad day at about $3.

What a caller can put in the prompt
Confirmed clean

The prompt is built on the server, not sent by the page: the skin's persona (one of three, anything else is Jarvis), fixed rules (spoken style, suitable for children, never ask for personal details, can't browse) and today's date. The page sends only data, each piece bounded: the question (500 characters), six earlier turns (600 each), facts (1,500), up to ten things told (160 each), a name (40), and up to 300 actions whose IDs must look like scene:galaxy. A whole body over 24,000 characters is refused. Action labels are cut to letters, digits and plain punctuation, and facts, the name and what was told lose their line breaks and control characters, so none can start a line of its own in the instructions. A label with a line break and "Ignore all rules" after it stayed on the same line (a check). Whatever Gemini says, the proxy returns only say (600 characters), kind, and at most three action IDs from the list it was sent. An invented launch:missiles was dropped. The page will check them all again against BRAIN_PICKS.

Nothing anyone asks is logged
Confirmed clean

core.js never calls console (the suite reads the code). It logs only through log(): the model, and for an answer its token counts (in, out, thinking), so cost can be read from Vercel's logs; for a failure, the status code. After a question with a name, something told and an answer, the log held none of those words. Copy broken on purpose: the question added to the log failed that check.

The on-device promise, while it's on
Open

Until now, nothing anyone said to Jarvis left the device, apart from the browser's own speech services. While the supercharger is on, what nothing on the device understood is sent through the proxy to Google, with the last few exchanges, the knowledge pack's facts for it, your name if you've given it this visit, and what you've told him this visit. On a paid key, Google's terms say prompts aren't used to improve its products. Those terms couldn't be read from this container (ai.google.dev doesn't resolve), so that's from the third-party listings and Google's long-standing paid-tier policy, not checked today. Even off, the page will ask Vercel whether it's on, so Vercel sees each visitor's IP address. This is the change you chose. What remains is the page side saying so plainly: the announcement when it turns on, the CLOUD tag on each answer, "what do you save", and the build plan's "where your data goes", which is already updated. Open until the page side is reviewed.

The source is public, like everything in this repo
Fixed

GitHub Pages serves jarvis/cloud/ as plain files, so anyone can read the proxy's code. It holds no secret: the key, the Edge Config token and your name are all Vercel settings. The README's example uses "Your first name". A grep of the new files for key, token and private-key patterns and for email addresses found one thing: the suite's fake key, written out as AIza plus 35 characters, the exact shape GitHub's secret scanning and a Full Monty grep look for.

Fix: The fake key is now built at run time from two pieces, so no key-shaped string is in the repo. It still has the real shape when the suite runs, so scrub() is tested on it, and all 113 checks pass.
The proxy's own headers
Confirmed clean

vercel.json sends nosniff, Referrer-Policy: no-referrer, X-Frame-Options: DENY, a CSP of default-src 'none'; frame-ancestors 'none' (it serves only JSON) and a Permissions-Policy turning off camera, microphone, location, USB and payment. Answers are JSON with nosniff; /api/brain is no-store. /api/status is cached only by Vercel's edge (s-maxage=20, max-age=0) with Vary: Origin, so a cached answer never carries another site's CORS header. Another site gets no CORS header at all.

02Code quality

The suite, and the two bugs its first run found
Fixed

tests/jarvis-cloud.test.mjs imports the real lib/core.js and drives it with a fake fetch that answers as Gemini and Edge Config do, status codes and body shapes included (a 400 INVALID_ARGUMENT, a 429 RESOURCE_EXHAUSTED, a 403 PERMISSION_DENIED, a blocked prompt, a SAFETY finish, a thought part, JSON in a code fence), and a fake clock for the switch's cache, until and the rate limit. The first run failed 2 of 112 checks, and both were real bugs. scrub() redacted token= only after ? or &, so a bare one would have been shown. And the cleaner for facts also removed colons and other punctuation, which would have mangled the knowledge pack's facts.

Fix: scrub() matches key= and token= anywhere. Facts, the name and what was told now lose only line breaks and control characters (flat()), while action labels keep the strict cleaner. A check was added for each. 113 checks, all passing. The actual Vercel functions were also run once with a fake req and res and no settings: status {"on":false} with CORS for the Pages site, and the brain 503.

Broken on purpose
Confirmed clean

Eight copies of core.js, each with one guard removed, were run against the suite, and every one failed: the key in the URL (4 failures), no origin check (3), a failed Edge Config read treated as on (1), the question logged (1), Gemini's picks not filtered to the list (1), until ignored (2), no rate limit (1), action labels not flattened (1). The original was put back and compared byte for byte afterwards.

The real services can't be reached from here
Open

From a claude.ai/code container, Google's API answers 403, and ai.google.dev and vercel.com don't resolve. So the request shapes came from Vercel's and Google's own client libraries, read from npm: @vercel/edge-config 1.5.1 (GET https://edge-config.vercel.com/<id>/items?version=1, Authorization: Bearer) and @google/genai 2.28.0 (generateContent, x-goog-api-key, thinkingConfig.thinkingLevel with minimal to high). The model name gemini-3.5-flash comes from third-party listings. Neither library is a dependency. Three things soften what can't be checked here: the proxy picks the model from Google's live list, a model that refuses a thinking level is asked again without one, and every failure reaches the page as a status code it can explain. Still, the first real answer, and whether Edge Config changes show without a redeploy, are for you to check once it's deployed.

Vercel's Hobby limits
Confirmed clean

Vercel's Hobby plan includes 100,000 Edge Config reads a month, and pauses a feature for the rest of the month if it's exceeded. Reads are bounded twice: /api/status is cached at Vercel's edge for 20 seconds, and each instance reads Edge Config at most once every 30 seconds. One instance kept busy all month would make about 86,000 reads. If the limit were still reached, the read fails, and a failed read is off. The worst case is that the supercharger can't be turned on, never that it can't be turned off. Function calls are well inside the Hobby plan's million a month.
