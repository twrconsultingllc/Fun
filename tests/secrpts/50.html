01Security & privacy

The CSP is unchanged: nothing the camera sees can leave the page
Confirmed clean

The face model is a file on this site (jarvis/hands/blaze_face_short_range.tflite, 229,746 bytes), loaded through the same vision bundle and WebAssembly as hand control, so connect-src 'self' still covers it. The CSP meta tag is byte-for-byte the same, and the suite still pins script-src. In headless Chromium, a full scan, a tap, close, reopen and a switch to hand control requested only 127.0.0.1, Google Fonts (already allowed) and cdnjs (three.js, only for the hand-control step), with no Refused messages in the console.

The model file is pinned
Fixed

SHA-256 b4578f35940bf5a1a655214a1cce5cab13eba73c1297cd78e1a04c2380b0152f, fetched from Google's mediapipe-models bucket, the source listed in the README. The suite checks the file against that hash and checks that the README lists it, the same way it pins the four hand-tracker files. Apache-2.0, like the rest of the folder. The folder keeps the name jarvis/hands/: renaming it to jarvis/vision/ would break jarvis.html, which loads from it and isn't being changed.

Camera only when asked, off on close, nothing saved
Confirmed clean

The camera opens only from "scan the room" and similar phrasings, asks for video only (audio:false, so it can never compete with speech recognition for the mic), and stops every track in the scene's dispose(). That runs on the close button, Escape, "close" or "stop the scan", opening another scene, switching to hand control, and when the tab is hidden. In Chromium, a wrapper around getUserMedia counted 0 live tracks after each of those, and the scan canvas was removed. There's no screenshot, recording or download: a grep finds no toDataURL, toBlob, MediaRecorder or .download= in the page, and the suite keeps it that way. Nothing about the scan goes into localStorage. The hint says so on screen: "Camera stays on this device. Nothing is saved or recorded."

It finds faces, it doesn't recognise or judge them
Confirmed clean

The detector returns boxes only. Targets are numbered in the order they appear, and a face that leaves for over half a second comes back as a new number, so nothing is remembered about anyone even within a visit. The readouts ("threat level: fluffy", "snack level: critical") are picked at random from fixed lists and are never derived from the picture: scanReadout takes only a random-number function. None of them comment on looks, age or anything else about a person. Faces of people who walk into the frame are processed the same way, on the device, and are never kept, which is the same position as hand control.

No new injection path
Confirmed clean

All scan text is drawn on a canvas with fillText or set with textContent, from fixed strings and numbers. The new code adds no innerHTML, eval or event-handler attribute.

02Code quality & accessibility

Brackets land on the face, at both sizes
Fixed

Chromium's fake camera was fed a 640×480 frame made from a portrait photo (in a scratch folder, not committed). At 1280×800 the target box was x 558, y 40, 186×186, against an expected face area of x 544 to 744 and y 6 to 246, worked out from where the face sits in the frame and coverMap. At 390×844 it was x 123, y 106, 164×164 against x 111 to 286 and y 76 to 287. With a blank frame the stat line read "SCANNING… NO TARGETS". No page errors at either size. The mapping (cover-fit, then mirrored) and the tracker are tested as plain functions in the suite, with values worked out by hand.

Readouts stay readable over any camera picture
Confirmed clean

Each readout sits on an 85% dark box. Computed over pure white, the worst case: text 12.35:1 (Jarvis), 12.52:1 (Matrix), 12.47:1 (Panthers); the amber "TARGET 01" heading 8.55:1, and 6.94:1 in the Panthers gold. The box is kept between the top HUD and the caption and on screen, and moves above or below the face when there's no room beside it, as at 390 px. The canvas isn't read by screen readers, so the first lock and every tap are also spoken and added to the chat log (which is aria-live), and the stat line gives the target count. Under reduced motion the scan line doesn't sweep and the brackets don't zoom in.

Not tried on a real phone or a real face
Open

Headless Chromium proves the model loads, finds a face in a still photo and draws on it. It can't show how well it keeps up with a moving face, how fast it runs on a phone, or how it behaves on iPhone Safari, which draws the camera from a video element that isn't on the page (as hand control already does). These are for the user to try on the live test copy.

Hand control doesn't stop when the tab is hidden
Open

The scan closes itself when the tab is hidden, so the camera can't be left on in the background. Hand control, which already shipped, doesn't do the same. Phones suspend a hidden tab's camera anyway, so the risk is mostly on desktop. Left for a later change, since this session doesn't touch hand control's behaviour.
