01Security

Path-traversal bypass in preview-server.mjs — never reviewed before
Fixed

This small local dev static-file server (loopback-only, 127.0.0.1:4173, never deployed anywhere) had never appeared in any prior numbered review — exactly the kind of file a page-by-page review misses because it isn't a page. Its traversal guard was the classic prefix-check bug: path.join(root, urlPath) correctly collapses ../ sequences, but the check !filePath.startsWith(root) has no boundary after the prefix, so a request resolving to a sibling path that merely starts with the same string as root (e.g. root = /workspaces/Fun, target = /workspaces/Fun-secret-notes.txt) would pass the check and be served.

Confirmed the bug is real before fixing it — tested path.join('/workspaces/Fun', '/../Fun-secret-notes.txt') directly in Node: it resolves to /workspaces/Fun-secret-notes.txt, which .startsWith('/workspaces/Fun') evaluates to true, incorrectly passing the guard.

Fixed: changed the check to filePath !== root && !filePath.startsWith(root + path.sep), which requires a real path-separator boundary after the root instead of a bare string prefix. Verified against the actual running server, not just the logic in isolation: started it for real and sent both a URL-encoded traversal attempt (curl default) and a raw, unencoded one (curl --path-as-is, since a compliant HTTP client normalizes ../ client-side before sending — the real attack vector is a raw TCP client that doesn't) — both now return 403 Forbidden, while a legitimate request for / still returns 200 with the real index.html. Real-world severity was always low (loopback-only local tool, never exposed to a network, never referenced by any deployment or test), but it's a genuine, textbook boundary-check bug (CWE-22-shaped) that deserved fixing regardless of today's blast radius.

Confirmed clean

GitHub Pages serves the whole repo as static files, so everything under tests/ — every *.mjs suite, tests/lib/'s three helper modules, tests/secrpts/'s own reports, package.json/package-lock.json — is exactly as publicly fetchable as any toy page, confirmed already by this project's own build-plan.html notes about npm run test:live reaching these files. Checked that the payload example is HTML-entity-escaped in the actual source (&lt;img src=x onerror=...&gt;) so it's inert text, not executable markup, and confirmed every documented issue is either already fixed or, for the two GitHub Pages header gaps, an honestly-disclosed and still-accurate architectural limit rather than a live secret being handed to an attacker. Publishing this level of detail is a real tradeoff for a site with no user data, no auth, and no money moved — worth the user's awareness that these reports function as a public disclosure log, not something to silently hide, since CLAUDE.md's own stance is that an honest "Open" is better than a false "Fixed."
