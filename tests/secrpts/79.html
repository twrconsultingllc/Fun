01Security and privacy

/api/voice: who may call it, and what it takes
Confirmed clean

The new route has the same gates as /api/brain, in the same order: a preflight gets CORS and nothing else, anything but POST is 405, and a missing or foreign Origin is 403. While the supercharger is off, or with no key, it answers 503 {off} and never asks Gemini. Each address gets 20 lines a minute on a limiter of its own, so voicing can't use up the 12 questions a minute. The body is at most 2,000 characters. The text is at most 600 characters, must be a non-empty string, and has its line breaks and control characters flattened, the way facts are, so it can't start a line of its own. An unknown skin becomes Jarvis. The proxy suite checks every gate, and none of them calls Gemini.

What goes to Google, and what is logged
Confirmed clean

The request to Gemini holds the skin's fixed style, the words and the voice name, and nothing else: no system prompt, no tools, no earlier turns. The key goes in the x-goog-api-key header, never a URL, and error text is scrubbed of it (checked with an upstream error and a network error that both name the key). Only {event, model, in, out} is logged. A check that the log never holds the words passed.

What comes back from Gemini is checked before it reaches the page
Confirmed clean

readVoice() takes only an inlineData part whose type is audio/L16 or audio/pcm, with a sample rate between 8 and 48 kHz, plain base64, and at most about 4 MB (about 80 seconds at 24 kHz). An image, text instead of audio, a silly rate, data that isn't base64 or audio that's far too long is a 502, and the page uses the browser's voice. The proxy writes the WAV header itself, so what the page decodes is always the proxy's file, served as audio/wav with nosniff and no-store. vercel.json's CSP still allows nothing (default-src 'none'), which is fine for audio fetched with fetch().

The page's CSP is unchanged
Confirmed clean

Recordings come from this site (connect-src 'self') and the live voice from the proxy address the CSP already allows. Both are fetched and decoded through Web Audio, not loaded in an <audio> element, so no media-src is needed. The suite pins the policy to exactly the Session 17 one, and Chromium logged no CSP violation in step 13.

Which spoken lines are kept on the device
Fixed

The plan asked for lines voiced live to be kept so a repeat isn't voiced again. That cache is outside IndexedDB, so the save() checks don't cover it. Kept audio has the words in it, so the "no personal data" rule had to be applied here by hand. A line is kept only if it's the page's own words (never an answer from Gemini or the full brain), has no digit, contains no name, and passes personal(). Kept lines go in jarvis-test-voice-live, at most 150, oldest first out, and "update Jarvis" clears them.

Fix: The first version checked only your name. The jsdom check found the supercharger's turn-on announcement being kept, with the owner's name in it. voiceKeepable() now refuses the owner's name too. With the check removed again (broken copy b7) the suite fails.
The recordings' manifest and file names, read by the page and the worker
Confirmed clean

The page reads only lines, only for the three skins it knows (Object.hasOwn, so __proto__ can't add one), and only file names of exactly 16 hex characters and .mp3. Anything else, like a path that climbs out of the folder, another type or an overlong line, is dropped. The service worker answers only jarvis/voice/(jarvis|matrix|panther)/[a-f0-9]{16}.mp3, saves only same-origin 200 answers, and keeps at most 2,000. The proxy is still never answered or cached, /api/voice included.

The recording workflow and its key
Confirmed clean

.github/workflows/jarvis-voice.yml runs only by hand (workflow_dispatch, no schedule, no push trigger), and a dry run is the default. The key is read in one place, the Record step's environment, which runs only for record. Inputs reach the shell through the environment, never as ${{ }} in a run line. Checkout keeps no token (persist-credentials: false). Both actions are pinned to the same commits as the knowledge pack's. The workflow commits only jarvis/voice/, as github-actions[bot], with a fixed message. The recorder sends the key only as a header and scrubs it from what it prints. Its log names counts and the model, never a line's words.

It is marked Partial because the announcement is the only notice, and it's given once a visit.

02Code quality

Three tiers, in order, with a fallback for every failure
Confirmed clean

The page tries a recording, then the live voice while the supercharger is on, then the browser's voice. All of an answer's pieces load at once and play in order: a slow live piece in the middle still plays second. jsdom checks each fallback through a real turn: a recording that won't download (404) or won't decode, Gemini failing (502), busy (429), unreachable, switched off between status reads (503, after which the page stops asking), and sound not yet allowed on a phone. Each one moves only that piece to the browser's voice, in place.

A recorded line is a whole line, matched across sentences
Fixed

The first collector split every line into sentences. A joke became two recordings, and "Stanley C. Panther" was cut at "C.". A recording is now the whole fixed line. The page takes the longest run of an answer's sentences that was recorded, so a skin's opener and a joke are two files played back to back.

Fix: voicePlan() searches longest first. The collector stores each line with its sentences joined by one space, the way the page joins them, and the voice suite checks every line is written that way.
Every recorded line is something he really says
Fixed

The voice suite drives each skin through typed turns ("hello", "thank you", jokes, fun facts, "how are you", "launch countdown", "who are you", a miss, "voice samples", skin switches), with six different random picks, and requires every collected line to appear word for word in an answer. That check found the three "databanks" misses, which no typed turn reaches, and the voice menu's sample.

Fix: The misses are no longer collected. The voice menu's sample now always plays in the browser voice you just picked (say(…, {browser: true})), which is what that menu is for, so it isn't recorded either.
Nothing with a time, a date, a name or a worked-out number is recorded
Confirmed clean

voiceRecordable() refuses any digit, any month or weekday, "today", "tomorrow", "o'clock" and so on, and anything personal() flags. The greeting is collected without a name. The suite checks every collected line against the same patterns. The Eiffel Tower fact (15 centimetres) is left out.

His voice by default; mixed only if you choose it
Confirmed clean

The plan worried that switching between a recording and the phone's voice would be jarring. With the default, an answer that can't be all in his voice is all in the browser's, so he never switches voice mid-answer. "Mix the voices" allows switching, and "use the browser voice" turns his voice off. The setting is saved in jarvis-settings through store(), is read back by "what do you save", can't go in a protocol, and with the browser setting a tap never starts Web Audio.

Everything that asked "is he speaking?" now asks about his own voice too
Fixed

Four places read speechSynthesis.speaking: always listening ignoring his own voice, the dream timer, protocol pacing and the supercharger announcement waiting for a gap. Audio the page plays itself doesn't show there. All four now use speakingNow(), which also counts his own voice while it loads and plays. A tap on the mic stops it too.

The recordings offline
Fixed

Chromium step 13 found that offline he fell back to the browser's voice. On the first visit the page read the manifest before the service worker took over, so it was never saved, and with no manifest there are no recordings.

Fix: The worker now saves jarvis/voice/manifest.json when it installs, as it does the page. The page tries a failed manifest read again after a minute instead of keeping it empty for the visit. Step 13 now plays the recording offline from the cache, with no request to the server.
The orb follows the real audio
Confirmed clean

While a recording or the live voice plays, orbPulse() takes the audio's loudness from an AnalyserNode. In Chromium, sampled every 50 ms during a real MP3 and a real WAV from the proxy, the level rose above 0.2, with SPEAKING shown while it played and STANDBY after. Reduced motion still holds it steady.

The Chromium step that timed out
Fixed

Step 7 ("jarvis upgrade your brain please") failed twice at 1280×800. The same command on the page from before this session also took about 2 seconds to answer under SwiftShader, so the step's fixed 900 ms wait was already too short. This session didn't cause it.

Fix: The step now waits up to 10 seconds for the answer to appear, then 900 ms, as before.
Cost before anything is recorded
Open

Until the workflow has run, every line he says while the supercharger is on is a text-to-speech call, the greeting and every command's reply included. After that, only Gemini's answers and lines with numbers or names go live. A WAV of 600 characters is about 2 MB on a phone's data.
