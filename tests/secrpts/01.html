Open proxy / cost-abuse risk on the battle-bots API endpoints
Fixed
battle-bots-V2/api/get-actions.js and the V1 equivalent had no rate limiting, auth, or origin check, and accepted an arbitrary client-supplied model name — anyone with the deployed URL could burn the owner's Gemini quota.
Fixed: added three server-side guards to both apps — a client-requested model is only honoured if it's actually in Google's live model catalog (cached 5 min); every field that reaches the prompt (gameState, prompt/promptA/promptB, memory) is now size- and shape-checked before use; and requests without a same-host Origin/Referer are rejected with 403. Verified live on both funv2.vercel.app and fun-xi-rouge.vercel.app — a spoofed cross-site Origin now returns 403, and malformed payloads return a specific 400 instead of reaching Gemini.

Real XSS bug in battle-bots V1
Fixed
battle-bots/public/game.js's addLog() injected LLM-derived text into innerHTML unescaped, and the server didn't whitelist the skill field before passing it through — a crafted model response (e.g. a skill value of <img src=x onerror=...>) could execute arbitrary JS in the victim's browser.
Fixed: ported V2's two-layer fix back to V1. Server-side, battle-bots/api/get-actions.js now builds each bot's order from a whitelisted skill name only (falling back to SNIPE_STANCE if the model's response isn't a real SKILL_CATALOG key), instead of spreading the model's raw object straight into the response — so an arbitrary/malicious string can no longer leave the server at all. Client-side, battle-bots/public/game.js's addLog() now runs the same escapeHtml() helper V2 uses before writing anything into innerHTML, as defense-in-depth. Verified in Node against a simulated malicious skill payload: the server now returns SNIPE_STANCE instead of the injected string, and even a hypothetical bypass would render as inert HTML entities, not executable markup. Verified live on fun-xi-rouge.vercel.app — curl'd the deployed game.js and confirmed it contains the escapeHtml() fix, and confirmed /api/get-actions still responds normally (GET model list) after the deploy.
