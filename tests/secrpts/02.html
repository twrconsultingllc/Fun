01Security

Not an issue

Every page carries the same shape of <meta http-equiv="Content-Security-Policy"> the rest of the repo uses, built from an actual inventory of each page's resources rather than a copy-pasted default — the same discipline the site-wide report insisted on for the original 13 pages.

Subresource Integrity — not applicable
Not an issue
The site-wide report's SRI fix targeted pinned CDN <script>/<link> files loaded at a fixed version (three.js, gsap, crypto-js, Font Awesome). None of the four new pages load anything like that — the only external reference on any of them is the Google Fonts CSS endpoint, which the site-wide report's own SRI fix also left alone everywhere else in the repo, because Google serves that endpoint as a dynamically-generated, per-request stylesheet rather than a fixed file, so there is no single hash to pin.
No secrets, no inline handlers, no eval, no exfiltration path
Confirmed clean
Grepped all four files directly rather than assuming:
  • No on*="…" inline event-handler attributes anywhere — every interaction is wired with addEventListener.
  • No eval( or new Function( anywhere.
  • Every .innerHTML assignment (five, all in widget-kit.html's Shadow DOM setup, one each in scroll-transit.html/shader-lab.html) either clears a container to '' or assigns a fixed, hand-written template string with no interpolated data — anything that could contain user- or model-derived text (labels, ratings, copy-chip text) is written with .textContent instead, never concatenated into markup. This is the exact bug class the site-wide report's battle-bots V1 XSS finding was about; none of that pattern exists here.
  • No fetch(, XMLHttpRequest, WebSocket, or sendBeacon anywhere in any of the four pages — there is no network code at all, so connect-src 'self' in each page's CSP is a real, enforced ceiling with nothing to restrict in practice yet, not a false sense of safety.
  • No API keys, tokens, or .env references — these are static front-end demos with no server component, unlike battle-bots/battle-bots-V2.
signal-scope.html is the first page in the repo to request microphone access
Open

The site-wide report's Permissions-Policy row (row 4) was left partial — fixed on Vercel via vercel.json, unfixable on GitHub Pages because there is no meta-tag equivalent for that header — but justified leaving GitHub Pages as-is with "nothing in this repo currently uses those APIs, so today this is pure defense-in-depth." signal-scope.html's optional "Use microphone instead" toggle removes that justification: this is now the first GitHub Pages page in the repo with a real reason to request a sensitive permission, and there is still no way to scope or block that request at the platform level here.

Concretely, what this does and doesn't expose:

  • The mic is never requested automatically — only on an explicit click of the "Use microphone instead" checkbox, and the browser's own native permission prompt still gates the request regardless of any Permissions-Policy header. This is not a silent-access bug.
  • If access is granted, the stream is routed only to a local AnalyserNode for the visualizer and never leaves the page — confirmed above, there is no network code anywhere in the file, so there is no path for captured audio to be transmitted anywhere even if the permission were obtained under false pretenses.
  • The realistic residual risk is the same shape as the site-wide report's row 2 (missing X-Frame-Options, also architecturally unfixable on GitHub Pages): an attacker could iframe signal-scope.html and use a clickjacking overlay to trick a visitor into clicking the mic checkbox at an unexpected moment, surfacing the browser's real permission prompt out of context. The prompt itself still can't be bypassed, but a confused user could click "Allow" believing they're interacting with the attacker's page.
Not fixed, same reason as the site-wide report's row 4: no meta-tag equivalent for Permissions-Policy or X-Frame-Options exists on GitHub Pages — this is architecturally blocked, not unaddressed. If this page (or any future one that requests a sensitive permission) ever moves to a host that sets real headers, add Permissions-Policy: microphone=(self) and X-Frame-Options: DENY there, mirroring the vercel.json pattern already in place for both battle-bots apps. Recorded here rather than silently left out, so this doesn't quietly become "not actually missing" the way Strict-Transport-Security turned out to be in the original scan — it did check that assumption before writing this, not skip it.

02Code quality & bugs

Number(x) || fallback silently discards a legitimate 0
Fixed
Three clamp helpers used the pattern Math.max(min, Math.min(max, Number(x) || fallback)): shader-lab.html's setSpeed(), and signal-scope.html's setTempo()/setCutoff(). Since 0 is falsy in JavaScript, calling e.g. setCutoff(0) silently produced 2400 (the fallback) instead of clamping to the real lower bound of 200 — a real, user-reachable bug (dragging the filter slider to its own minimum value would have been indistinguishable from an invalid input).
Fixed: replaced all three with Number.isFinite(x) ? x : fallback, which only substitutes the fallback for genuinely invalid input (NaN, undefined), not for a valid 0. Caught by writing the test suite for these pages, not by manual review — the tests now assert setCutoff(0), setTempo(0), and setSpeed(0) explicitly, on top of the more obvious out-of-range clamps, so this exact bug class can't silently return.
signal-scope.html's canvas draw functions would throw if getContext('2d') returns null
Fixed
drawNoSignal(), drawBars(), and drawRadial() called canvas 2D methods unconditionally. This repo's own CLAUDE.md already documents that getContext('2d') returns null without a native canvas package (as in this test environment, and in principle any environment without a working 2D backend) — and drawNoSignal() runs unconditionally at page load regardless of Web Audio support, so this would have thrown on the very first paint in exactly that situation.
Fixed: all three functions now return early if the 2D context is unavailable. This has no effect on real browsers (which always provide a 2D context) — it only matters in a test/embedded environment without one — but it's the same defensive posture race-day.html's webglAvailable() already models for missing rendering capability, applied to canvas 2D instead of WebGL. Confirmed by the DOM test suite, which loads the real page and asserts the script runs with zero errors.
play() not idempotent in shader-lab.html / signal-scope.html
Fixed
Both pages expose play() on their window.__pagename debug hook. Calling it twice in a row without an intervening pause()/stop() would schedule a second, independent requestAnimationFrame chain — not reachable through the actual UI (the Play/Pause button toggles based on tracked state, so a real click sequence can't double-invoke it), and each duplicate chain self-terminates within one extra frame once state.playing goes false, so this was never a permanent leak — but it's a real gap in the guarantee "safe to call from outside code" that the debug hooks are supposed to offer.
Fixed: both play() functions now no-op if state.playing is already true. Low severity — this could only be observed via direct misuse of the debug API — but cheap and correct to close. Noted honestly in the added regression test that jsdom cannot provide a real GL/AudioContext to prove the guard actually prevents a second scheduled frame; the test only confirms calling play() twice remains side-effect-free where jsdom can observe it.
<collapse-panel> missing aria-expanded, chevron not hidden from screen readers
Fixed
The disclosure header in widget-kit.html's <collapse-panel> toggled visually and dispatched a toggle event, but had no aria-expanded state for assistive tech to read, and its decorative › chevron glyph had no aria-hidden, so a screen reader could announce it as meaningful content. Same category of gap as the accessibility fixes in the site-wide report (unlabeled/unannounced interactive state).
Fixed: the header button now carries aria-expanded, kept in sync with the open property/attribute in both directions (click and programmatic), and the chevron span now has aria-hidden="true". Verified by a new assertion in the widget-kit test suite that reads aria-expanded before and after toggling.
Viewport, keyboard operability, and control labeling
Confirmed clean
Checked against the exact accessibility gaps the site-wide report previously found and fixed elsewhere in the repo (blocked pinch-zoom, unlabeled sliders, unkeyboard-operable clickable <div>s):
  • All four pages use a plain width=device-width, initial-scale=1.0 viewport — none add maximum-scale or user-scalable=no.
  • Every interactive control on all four pages is a native <button>, <input>, or <select> — there are no custom clickable <div>/<span> elements anywhere, unlike the pre-fix ai-swarm.html rows the site-wide report had to retrofit with a keyboard-clickable helper. Native elements get Tab focus and Enter/Space activation for free.
  • signal-scope.html's sliders and select (waveform, tempo, cutoff) and its mic checkbox all have a visible <label for="…"> paired to the control's id, rather than relying on placeholder text or an aria-label retrofit.
Minor, left as-is
Open — not a functional gap
<rating-stars> in widget-kit.html renders as a row of individually-labeled, independently focusable star buttons (each with its own aria-label, e.g. "3 stars") rather than a single compound widget with role="radiogroup" and one group-level label. It is fully keyboard-operable and each button's purpose is announced correctly on its own, so nothing is broken — a screen-reader user would just hear five separate buttons rather than one rating control with a spoken current value. Left alone for the same reason the site-wide report left the repeated sound-envelope boilerplate alone: it's a nice-to-have refinement, not a gap that blocks use, and over-engineering a demo widget-kit page's already-working control wasn't worth doing without being asked.
