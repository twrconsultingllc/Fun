The re-hash command was wrong for files saved with Windows line endings
Fixed

Browsers hash an inline script after the HTML parser has turned every CRLF into LF, so the page still runs after a Windows editor saves it with CRLF. Headless Chromium confirmed this: a CRLF copy rendered 10:48:48 with no console errors. The node -e command in the comment read the raw bytes instead. For a CRLF copy it printed 9O3IFVH+… instead of the real hDDK4wH4…. Anyone who edited the script on Windows and pasted that value into the CSP would have stopped the page from running.

Fix: the command now applies .replace(/\r\n?/g,'\n') before hashing, and the comment says it handles Windows line endings. A new check runs the exact command from the comment on the file saved with LF and with CRLF, and compares both results with the CSP hash. It failed on the previous file (Windows endings) and passes on this one. The script itself is unchanged, so its hash is too.
