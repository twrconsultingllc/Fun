01Security

No exposed secrets or API keys anywhere
Not an issue
The Gemini key is read from process.env.GEMINI_API_KEY server-side only in both battle-bots/api/get-actions.js and battle-bots-V2/api/get-actions.js, sent via header, and scrubbed from error messages before they reach the browser. No .env was ever committed, in history or working tree. Confirmed clean — nothing to fix.
Open proxy / cost-abuse risk on the battle-bots API endpoints
Fixed
battle-bots-V2/api/get-actions.js and the V1 equivalent had no rate limiting, auth, or origin check, and accepted an arbitrary client-supplied model name — anyone with the deployed URL could burn the owner's Gemini quota.
Fixed: added three server-side guards to both apps — a client-requested model is only honoured if it's actually in Google's live model catalog (cached 5 min); every field that reaches the prompt (gameState, prompt/promptA/promptB, memory) is now size- and shape-checked before use; and requests without a same-host Origin/Referer are rejected with 403. Verified live on both funv2.vercel.app and fun-xi-rouge.vercel.app — a spoofed cross-site Origin now returns 403, and malformed payloads return a specific 400 instead of reaching Gemini.
commit 9b582bd — "Harden battle-bots API endpoints against quota abuse"
Real rate limiting (a hard cap on requests/minute) is intentionally not included — it needs an external store (e.g. Upstash Redis) and a new dependency, which is a separate decision still pending on the user's side.
Real XSS bug in battle-bots V1
Open
battle-bots/public/game.js's addLog() injects LLM-derived text into innerHTML unescaped, and the server doesn't whitelist the skill field before passing it through. battle-bots-V2 already fixed both (an escapeHtml() helper in ui.js and a strict SKILL_CATALOG whitelist server-side). Recommend porting V2's fix back to V1, or retiring V1 in favor of V2.
No Subresource Integrity on pinned CDN scripts
Fixed
three.js, gsap, ScrollTrigger, crypto-js and font-awesome were all loaded from cdnjs at a pinned version but with no integrity attribute — a compromised CDN could have silently served different code.
Fixed: added integrity="sha512-…", crossorigin="anonymous" and referrerpolicy="no-referrer" to all 10 affected tags across index.html, race-day.html, ai-swarm.html, threejsGallery.html, secret.html, 51d6d17b…html and tricalc.html. Hashes were pulled from cdnjs's own published SRI metadata and cross-verified by independently downloading and hashing each file. Verified live on the deployed GitHub Pages site. cdn.tailwindcss.com (in bots.html/tricalc.html) is intentionally left alone — it's a JIT compiler with no fixed file to hash.
commit a10bf6f — "Add Subresource Integrity and no-referrer policy to pinned CDN assets"
No security headers configured (CSP, X-Frame-Options, etc.)
Open

No vercel.json exists for either battle-bots deployment, and GitHub Pages has no header-config mechanism at all — everything relies on platform defaults. Checked the actual response headers (curl -I) on GitHub Pages, funv2.vercel.app, and fun-xi-rouge.vercel.app to confirm exactly what's really missing rather than guessing. Not actually missing: Strict-Transport-Security (HSTS) — both hosts send this automatically by default, nothing to fix there. Everything below is genuinely missing, confirmed on every URL tested.

#1. Problem2. Fix3. Pages affected4. Status
1 No Content-Security-Policy. Nothing restricts which domains a page's scripts can load from or connect to. Doesn't stop the confirmed battle-bots V1 XSS bug from executing (a no-build CSP needs 'unsafe-inline'), but would block it from phoning home to an attacker domain. Partial fix on GitHub Pages — a <meta http-equiv="Content-Security-Policy"> tag can be added to each page's <head>, but 'unsafe-inline' is required, so it won't block inline-handler injection. Full fix on Vercel via a vercel.json headers block. Set A + Set B + Set C Open
2 No X-Frame-Options / frame-ancestors. Any external site can load these pages in a hidden iframe (clickjacking). Concretely: lets an attacker's page trick a visitor into clicking "Start Match" on the real battle-bots app, burning the owner's Gemini quota with a genuinely same-origin request — which slips right past the Origin/Referer check added in the quota-abuse fix (commit 9b582bd). NO FIX AVAILABLE on GitHub Pages. There is no meta-tag equivalent for this header — browsers only honor it as a real HTTP header, and GitHub Pages gives you no way to set one. Full fix on Vercel via vercel.json. Set A: no fix exists, period. Set B: fixable. Open
3 No X-Content-Type-Options: nosniff. Browser can MIME-sniff a response instead of trusting its declared content type. Narrowest real exposure: the two API routes echo model-generated text back as JSON. NO FIX AVAILABLE on GitHub Pages — no meta-tag equivalent exists for this header either. Full fix on Vercel via vercel.json. Set A: no fix exists, period. Set B + Set C: fixable. Open
4 No Permissions-Policy. Nothing blocks a page — or anything injected into it — from requesting camera, microphone, geolocation, USB, fullscreen, etc. Nothing in this repo currently uses those APIs, so today this is pure defense-in-depth. NO FIX AVAILABLE on GitHub Pages — no reliable meta-tag equivalent exists. Full fix on Vercel via vercel.json. Set A: no fix exists, period. Set B: fixable. Open
5 No page-wide Referrer-Policy. Full page URL can leak in the Referer header when a visitor clicks an outbound link. (Different from the per-<script> referrerpolicy="no-referrer" already fixed on CDN tags — that only covers those specific asset requests.) Checked every outbound link in the repo: all go to Google Fonts/cdnjs or the app's own other deployment, so real-world exposure is low right now. Full fix on GitHub Pages too — <meta name="referrer" content="strict-origin-when-cross-origin"> is a standard mechanism, not a workaround, and behaves the same as the real header. Full fix on Vercel via vercel.json (or the same meta tag). Set A + Set B — fixable everywhere Fixed

Bottom line on "no fix": rows 2, 3, and 4 are genuinely unfixable for every GitHub Pages page as long as the site stays on GitHub Pages — not "not done yet," but architecturally blocked, because GitHub Pages has zero mechanism for setting arbitrary response headers. The only way to close that gap for the 13 static pages is migrating hosting (e.g. Cloudflare Pages or Netlify, both free and both deploy from this same repo) or putting a reverse proxy/CDN in front of GitHub Pages. Row 1 can also be patched (partially) today on GitHub Pages via a meta tag; rows 2–4 cannot, by design of the platform.

Row 5 fixed: added <meta name="referrer" content="strict-origin-when-cross-origin"> to the <head> of all 13 GitHub Pages pages (index.html, new.html, threejsGallery.html, tricalc.html, araknoid.html, pong.html, bots.html, snake.html, fullcircle.html, ai-swarm.html, race-day.html, secret.html, 51d6d17b…html), this report page itself, and both Vercel apps' entry pages (battle-bots/public/index.html, battle-bots-V2/public/index.html, battle-bots-V2/public/guide.html) — 17 files in total. This is a standard, non-experimental mechanism (part of the Referrer Policy spec, not a workaround), so it's a full fix everywhere, not a partial one like row 1's meta-tag CSP.
