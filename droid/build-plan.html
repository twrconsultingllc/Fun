Sentinel — Build Plan

The design in plan.html turned into seven self-contained work sessions, following that page's own section 10 build order exactly. The actual Kotlin/Gradle project lives in its own standalone repo, developed in Android Studio on a Windows PC and tested on a Samsung phone (no tablet involved) — this page just tracks that separate project's progress from inside Fun/droid/, the way the Claude Architect Lab build plan tracks that project.

Status: nothing started yet As of this writing no Kotlin/Gradle project exists — Session 1 below hasn't been run. Every session's Not started badge reflects that; update them here as the standalone repo actually gets built.
Key: who does each step Every numbered step below is tagged Claude or You, sometimes both. Claude marks anything this assistant can do directly once it has a terminal in the right place — writing code, editing Gradle/manifest config, seeding data, running gradlew.bat test/assembleDebug — from inside a terminal on the Windows PC, once one exists there. You marks anything no coding agent can do on your behalf: tapping through an app-store install or a system permission dialog, flipping an Android Settings toggle, physically carrying hardware between locations, or tapping an NFC tag to a phone. A step tagged with both means it splits — Claude builds it, you tap through the install or eyeball the result on the real device.

Before you startHow to use this plan

Development happens on a Windows PC running Android Studio — not on a tablet via Termux, which is how this plan originally started. A Samsung phone (assumed to have NFC hardware) is the one physical device used for on-device testing, connected over USB or wireless ADB; Android Studio's bundled emulator covers most iteration in between. There's no tablet anywhere in this version of the plan.

  • Start each new session by reading this plan and the "Done when" line of whatever session you finished last — a fresh Claude Code session on the Windows PC has no memory of prior sessions, so re-orienting from this document is faster than re-deriving context from code.
  • Don't open a session's next steps as extra credit. Each session ends at a real boundary — Session 1 stops at a launching "Hello Compose" APK, not a taste of Room; Session 4 stops at a running foreground service, not the UI. Resist folding the next session in just because time is left.
  • Sessions 2 and 3 need no device at all — they're pure JVM logic (the correlation engine, the clusterer, the BLE payload parser) verified with gradlew.bat test, the same "no live dependency" split the Claude Architect Lab plan uses for its own no-API-key sessions. Sessions 1, 4, 5, 6 can mostly run against the emulator; only Session 5's NFC half and Session 7 strictly require the Samsung phone.
  • Every session below cross-references the exact section of plan.html it implements — this page sequences the work, it doesn't redesign it. If something here seems to contradict that page, plan.html is the source of truth; treat the mismatch as a bug in this page.
  • This page doubles as the tracker. Each session has a Status line (Not started, In progress, or Done) in its meta row, and a Session notes callout underneath its "Done when" line. When a session is finished, flip its badge to Done in both places (the session's own meta row and the session-index table) and log anything worth remembering — a Windows/Gradle gotcha beyond what plan.html already documents, a real device quirk, a divergence from plan.html, a dead end. Leave a session's notes as "None yet." if nothing came up.

Session 1Windows toolchain & Hello Compose

Status: Not started Needs hardware: the Windows PC, plus the Samsung phone for the final on-screen check Est. time: 60–90 min Depends on: nothing

Goal: validate the entire build-and-install pipeline with a trivial app before writing any real feature code, per plan.html section 10's own first step.

  1. YouInstall Android Studio on the Windows PC and step through its first-run setup wizard. The one step in this whole session that's entirely yours from the very first click — nothing exists yet for Claude to run, and installers/GUI wizards are GUI-only.
    1. Download and run the Android Studio installer from its official site, then launch it once installed.
    2. Step through the Setup Wizard: accept the SDK license, and let it install its default SDK platform, build-tools, and platform-tools. This also installs a matching JDK bundled with Android Studio — no separate JDK download needed.
    3. Open Device Manager and create at least one emulator (AVD) — a recent API level is fine. This is what most of Sessions 1, 4, and 6 will run against, so it's worth having ready now.
  2. YouPrepare the Samsung phone and connect it to the PC.
    1. Confirm the phone is on Android 12+ (Settings → About phone → Android version) — plan.html section 07's minSdk 31 decision depends on it.
    2. Enable Developer Options (Settings → About phone → tap "Build number" 7 times), then turn on USB debugging under the new Developer Options menu.
    3. Connect the phone to the PC with a USB cable, and accept the "Allow USB debugging?" prompt on the phone's own screen — or set up Wireless debugging instead (Developer Options → Wireless debugging → pair) if a cable is inconvenient for a given session.
  3. YouInstall the Claude Code CLI on Windows, then log in. Nothing exists yet for a Claude Code session to run the remaining steps below with — the same bootstrapping reason steps 1 and 2 above were entirely yours. Windows is a directly supported platform — no Node.js install and no workaround needed, unlike the Termux/Android path this plan used to document.
    1. Open PowerShell and run the official installer: 
      irm https://claude.ai/install.ps1 | iex
    2. Recommended: also install Git for Windows if it isn't already on the machine, so Claude Code has a real Bash available for shell commands. Without it, Claude Code falls back to PowerShell for shell commands, which mostly works but is a rougher fit for Unix-style commands (like ./gradlew invocations documented elsewhere as the Git-Bash form).
    3. Run claude and log in — pick one:
      • Your Claude.ai account (Pro/Max). It opens a browser for login normally on Windows — sign in when it appears.
      • An Anthropic Console API key instead. Generate one at platform.claude.com first, then set it before running claude: 
        $env:ANTHROPIC_API_KEY = "…"
        No browser step, but this bills per-token from Console credits rather than a Pro/Max subscription.
  4. ClaudeYouConnect this Windows terminal to GitHub and a new repo for the project.
    1. Install the GitHub CLI — Claude, now that the step above gives it a shell to run in: 
      winget install --id GitHub.cli
    2. Log in — a fresh terminal may be needed after the install above picks up the new PATH entry: 
      gh auth login
      Choose GitHub.com → HTTPS → Login with a web browser, then sign in when the browser opens (you).
    3. Set your git identity — your call whether to use a real address or a GitHub-provided @users.noreply.github.com one, since this is its own repo with no CLAUDE.md of its own yet (a decision only you can make; Claude can type it once you've decided): 
      git config --global user.name "…"
git config --global user.email "…"
    4. Once the project exists (the scaffolding step below), create and push the repo in one shot from inside its directory: 
      gh repo create sentinel --private --source=. --remote=origin --push
      — or create an empty repo on github.com first and run git remote add origin … / git push -u origin main by hand instead.
  5. ClaudeScaffold a minimal Kotlin/Gradle/Compose project directly (not via Android Studio's New Project wizard — Claude writes the Gradle files and MainActivity.kt straight into a folder) — package root com.twrconsulting.sentinel (placeholder), just MainActivity showing "Hello Compose," nothing else — in its own standalone git repo, not inside Fun. Connect it to GitHub using the step above once the folder exists, then open that folder in Android Studio so its Gradle sync and Device Manager are available for the rest of this session.
  6. ClaudeBuild from the command line: 
    gradlew.bat assembleDebug
    (or ./gradlew assembleDebug from Git Bash — Gradle's wrapper script is POSIX shell, so Git Bash runs the Unix-style form directly). If this is the very first build and Gradle needs to fetch an SDK component Android Studio didn't already install, it may prompt for a license acceptance that only Android Studio's own UI can answer — opening the project in Android Studio once and letting it sync resolves that.
  7. ClaudeYouInstall and launch it — Claude runs adb install (or uses Android Studio's Run button) targeting either the emulator or the Samsung phone; either way, confirming the app actually launches means looking at the screen (you) — the emulator window, or the phone itself.
Done when A "Hello Compose" APK builds on the Windows PC and launches, on either the emulator or the Samsung phone. This proves the whole toolchain end to end — nothing else gets built until this works.

Session 2Data model & correlation engine

Status: Not started Needs hardware: No — pure JVM, inside the project scaffolded in Session 1 Est. time: 90–120 min Depends on: Session 1

Goal: the Room schema and the core TrackerCorrelationEngine, verified with synthetic fixtures — no scanning code yet, per plan.html section 10's own ordering ("get this right first").

  1. ClaudeAdd Hilt (DI) and Room with KSP — not kapt — to the project's Gradle config.
  2. ClaudeWrite the six Room entities from plan.html section 03's table: DeviceEntity, SightingEntity, KnownTrackerSignatureEntity, IgnoredDeviceEntity, FlagEventEntity, LocationClusterEntity.
  3. ClaudeSeed KnownTrackerSignatureEntity with the documented public formats: Apple Find My (manufacturer ID 0x004C), Samsung SmartTag/SmartTag2 (0x0075), Tile and Chipolo (service-UUID based).
  4. ClaudeImplement LocationClusterer (incremental centroid clustering, 150m threshold, Haversine distance) and TrackerCorrelationEngine plus FlagScorer per plan.html section 04: the hard gates (≥3 distinct clusters, ≥20 minutes first-to-last span) before any scoring, then the 0–100 suspicion score with its known-signature bonus and weak-identity discount.
  5. ClaudeSet android:allowBackup="false" and exclude the Room database from auto-backup rules now, while the database is first created — this data is a de facto location history and shouldn't have a window where it's backed up by default.
  6. Claudegradlew.bat test against synthetic sighting fixtures: at minimum, one stationary device across many sightings in a single cluster that never flags, one tracker-like device seen across 3+ clusters with a plausible time span that does flag, and one case confirming the known-signature match adds its scoring bonus.
Done when gradlew.bat test passes with synthetic fixtures covering at least one true-flag case and one true-negative (stationary device) case — no device or emulator needed for this session.

Session 3BLE parsing & MAC-rotation linking

Status: Not started Needs hardware: No for this session — a real BLE tracker only matters later, in Session 7 Est. time: 60–90 min Depends on: Session 2

Goal: BleAdvertisementParser and the rotation-tolerant identity-linking heuristic from plan.html section 03's "Why raw MAC address can't be trusted as identity" subsection.

  1. ClaudeImplement BleAdvertisementParser: recognize each signature family seeded in Session 2 from its manufacturer payload, since that format is far more stable than a rotating address.
  2. ClaudeImplement the linking heuristic: if a same-family device disappears and a new MAC of the same family appears within roughly 15 minutes, at similar RSSI and location, merge the sightings under the same stableDeviceKey — while still keeping the raw per-sighting address, so nothing is lost if the heuristic mis-links two devices.
  3. ClaudeFor unrecognized BLE devices, discount MAC continuity heavily past roughly 20–30 minutes, treating it as a weak, short-term-only signal.
  4. ClaudeExplicitly do not attempt to cryptographically defeat address rotation (e.g. Apple's Find My rolling-key derivation) — out of scope, matching plan.html section 03's fourth point.
  5. ClaudeUnit tests: a synthetic MAC-rotation sequence that should link (same family, short gap, similar RSSI/location) and one that shouldn't (too long a gap, or a different family).
Done when The parser correctly classifies each seeded signature family from a synthetic payload, and the linking-heuristic tests demonstrate both a correct merge and a correct non-merge.

Session 4Foreground scanning service & permissions

Status: Not started Needs hardware: the Samsung phone — the first real on-device milestone Est. time: 90–120 min Depends on: Sessions 2, 3

Goal: real BLE and WiFi sightings landing in the database from a running foreground service, per plan.html section 05 and section 07.

  1. ClaudeAdd the manifest permissions and uses-feature entries exactly as listed in plan.html section 07: BLUETOOTH_SCAN with neverForLocation, BLUETOOTH_CONNECT, fine/coarse location, WiFi state, NFC as an optional feature, the three FOREGROUND_SERVICE* permissions, POST_NOTIFICATIONS, and the battery-optimization request permission.
  2. ClaudeImplement ScanForegroundService (Android 14+ types connectedDevice|location) with duty-cycled BLE bursts (SCAN_MODE_BALANCED, every 2–5 minutes), one WiFi startScan() per cycle, and a passive SCAN_RESULTS_AVAILABLE_ACTION receiver to catch scans the OS triggers on its own.
  3. ClaudeImplement ScanScheduler/ScanWorker as the periodic WorkManager watchdog that restarts the foreground service if Samsung's OEM battery management kills it.
  4. ClaudeWire DeviceRepository's Room @Transaction upsert keyed on stableDeviceKey, using Session 2's schema and Session 3's parser/linker.
  5. ClaudeYouBuild and install (gradlew.bat assembleDebug then adb install, or Android Studio's Run button) — Claude. Confirming it worked needs a human: tapping through the live system permission dialogs Android pops up (no agent can dismiss those), then looking at the phone to confirm the foreground-service notification shows and real BLE/WiFi sightings start populating the database (no UI to view them yet — a debug log or a direct DB query is enough).
  6. YouManually apply the Samsung One UI battery exclusion (Device Care → Battery → Background usage limits) — plan.html section 07 and 09 both note this can't be done by the app itself, and it's a Settings-UI toggle no agent can flip for you.
Done when The service runs on the Samsung phone, survives a short screen-off spot check without being killed (the full multi-hour check is Session 7), and real sightings are landing in the database.

Session 5WiFi polish & the NFC screen

Status: Not started Needs hardware: the Samsung phone (WiFi + NFC), plus the emulator for the "no NFC hardware" negative check Est. time: 60–90 min Depends on: Session 4

Goal: accept WiFi's real throttling ceiling rather than fighting it, and add the manual NFC tag-inspection screen from plan.html section 06.

  1. YouConfirm WiFi scanning lands at roughly 30–60 second effective resolution per plan.html section 07 — this is an OS throttle on stock, unrooted Android, not a bug to chase away; confirming the real cadence means watching it happen on the Samsung phone.
  2. ClaudeImplement NfcTagReader and the NFC Tag Read screen: UID, tech list, NDEF dump if present; MIFARE Classic reports "detected, sectors not readable without keys" rather than attempting key-cracking.
  3. ClaudeSet the foreground-dispatch PendingIntent to FLAG_MUTABLE — the specific gotcha plan.html section 07 calls out; the usual post-Android-12 FLAG_IMMUTABLE default breaks tag delivery here.
  4. YouConfirm the emulator (which has no NFC radio at all) shows a graceful "no NFC hardware" state instead of crashing — a visual check, and a convenient built-in negative test now that there's no second physical device to borrow for it.
  5. YouTest real tag reads on the Samsung phone — physically tapping a tag to it and reading the result on screen. (This assumes the phone has NFC hardware — confirm that if it hasn't already come up; most modern Samsung phones do.)
Done when The NFC screen reads a real tag's UID/tech list/NDEF on the Samsung phone, and shows a graceful unavailable state on the emulator.

Session 6Compose UI wired to live data

Status: Not started Needs hardware: emulator or Samsung phone Est. time: 90 min Depends on: Sessions 4, 5

Goal: all five v1 screens from plan.html section 06, live against the real data flowing in from Sessions 4–5.

  1. ClaudeNearby: live BLE+WiFi list via Room Flow, signal strength, swipe-to-ignore, manual "scan now" button.
  2. ClaudeFlagged: sorted-by-score list with the human-readable reason string (e.g. "seen at 4 locations up to 6.2km apart over 5h; matches Apple Find My format"), dismiss/view actions.
  3. ClaudeDevice Detail: identity, all linked raw addresses, sighting history on a map via OSMDroid (not Google Maps, to avoid the API-key/Play-Services dependency), ignore/nickname actions.
  4. ClaudeSettings: scan interval, sensitivity (Low/Medium/High mapped to the flag threshold), cluster-distance (advanced), ignore-list management, data retention/export/clear, scanning kill switch.
  5. ClaudeOnboarding wizard: auto-suggest ignoring the user's own bonded Bluetooth devices and the currently-connected WiFi network, per plan.html section 04's false-positive suppression.
  6. ClaudeThe NFC screen from Session 5 becomes reachable from this UI rather than a standalone test harness.

Every step above is code Claude can write; actually looking at the five screens (emulator or Samsung phone) and confirming they feel right is You — see this session's "Done when" line below.

Done when All five screens are live against real on-device data, and the ignore/dismiss actions actually suppress future flags rather than just updating the display.

Session 7On-device validation

Status: Not started Needs hardware: the Samsung phone + a real or simulated BLE tracker Est. time: spans at least one multi-hour period, not a single sitting Depends on: everything above

Goal: the real-world checks from plan.html section 11 — this is native Android code that can't be honestly signed off from a CLI sandbox, so this session is where the actual claims get tested against reality.

  1. ClaudeRun the full gradlew.bat test suite one more time (correlation engine, clusterer, signature matcher, parser, linking heuristic) as a baseline before the real-hardware checks.
  2. YouPlace a known BLE tracker (or a phone advertising a similar payload) at 3+ physically distinct locations over time; confirm it gets flagged. Physically carrying hardware around is inherently a you-task.
  3. YouConfirm a stationary device (a home router) never gets flagged — check the Flagged screen yourself; Claude can help interpret an exported log if you hand it one, but can't watch the device over time on its own.
  4. ClaudeYouadb logcat over several hours, including a screen-off/Doze period and an app-switch/backgrounding test — Claude can run and parse the log if it has a terminal connected to the device, but you're the one putting the phone through a real screen-off/Doze period and switching apps on it.
  5. YouRe-confirm the NFC screen on the Samsung phone and the graceful unavailable state on the emulator, now as part of the full app rather than a standalone test harness.
  6. ClaudeYouWrite down real-world findings in this session's notes: any false positives/negatives encountered, whether the co-traveler hard case (plan.html section 09) actually showed up, whether the default flag threshold of roughly 55 felt right in practice, and any Windows/Gradle/Android Studio gotchas hit beyond what plan.html section 08 already documents. You supply the raw observations; Claude can help write them up.
Done when A real tracker gets flagged after being carried to 3+ locations, a stationary device never gets flagged, the service survives a multi-hour real-world run including a Doze period, and the findings above are written into this session's notes — not just "it didn't crash."
