Sentinel — Build Plan

The design in plan.html turned into seven self-contained work sessions, following that page's own section 10 build order exactly. The actual Kotlin/Gradle project lives in its own standalone repo, developed entirely inside a GitHub Codespace and tested on a Samsung phone bridged over ADB (no tablet, no Android Studio, no local install of Claude Code) — this page just tracks that separate project's progress from inside Fun/droid/, the way the Claude Architect Lab build plan tracks that project.

Status: nothing started yet As of this writing no Kotlin/Gradle project exists — Session 1 below hasn't been run. Every session's Not started badge reflects that; update them here as the standalone repo actually gets built.
Key: who does each step Every numbered step below is tagged Claude or You, sometimes both. Claude marks anything this assistant can do directly once it has a terminal in the right place — writing code, editing Gradle/manifest config, seeding data, running ./gradlew test/assembleDebug — from inside the GitHub Codespace's own terminal, once one exists there. You marks anything no coding agent can do on your behalf: tapping through an app-store install or a system permission dialog, flipping an Android Settings toggle, physically carrying hardware between locations, or tapping an NFC tag to a phone. A step tagged with both means it splits — Claude builds it, you tap through the install or eyeball the result on the real device.

Before you startHow to use this plan

Development happens entirely inside a GitHub Codespace (a cloud Linux dev container, opened via VS Code or github.dev) — not Android Studio on a Windows PC, and not a tablet via Termux, which is how this plan went through two earlier revisions. Neither Android Studio nor Claude Code is installed directly on the Windows laptop; a Samsung phone (assumed to have NFC hardware) is the one physical device used for on-device testing, reached from the Codespace over an ADB bridge (see plan.html section 08) since a cloud container can't see a USB-connected phone by itself. There's no emulator and no tablet anywhere in this version of the plan.

  • Start each new session by reading this plan and the "Done when" line of whatever session you finished last — a fresh Claude Code session inside a Codespace has no memory of prior sessions, so re-orienting from this document is faster than re-deriving context from code.
  • Don't open a session's next steps as extra credit. Each session ends at a real boundary — Session 1 stops at a launching "Hello Compose" APK, not a taste of Room; Session 4 stops at a running foreground service, not the UI. Resist folding the next session in just because time is left.
  • Sessions 2 and 3 need no device at all — they're pure JVM logic (the correlation engine, the clusterer, the BLE payload parser) verified with ./gradlew test, the same "no live dependency" split the Claude Architect Lab plan uses for its own no-API-key sessions. Every other session needs the Samsung phone and its ADB bridge, since there's no emulator to fall back on in this version of the toolchain.
  • Every session below cross-references the exact section of plan.html it implements — this page sequences the work, it doesn't redesign it. If something here seems to contradict that page, plan.html is the source of truth; treat the mismatch as a bug in this page.
  • This page doubles as the tracker. Each session has a Status line (Not started, In progress, or Done) in its meta row, and a Session notes callout underneath its "Done when" line. When a session is finished, flip its badge to Done in both places (the session's own meta row and the session-index table) and log anything worth remembering — a Codespaces/ADB-bridge gotcha beyond what plan.html already documents, a real device quirk, a divergence from plan.html, a dead end. Leave a session's notes as "None yet." if nothing came up.

Session 1Codespace toolchain & Hello Compose

Status: Not started Needs hardware: the Samsung phone, reached from the Codespace over the ADB bridge Est. time: 60–90 min Depends on: nothing

Goal: validate the entire build-and-install pipeline with a trivial app before writing any real feature code, per plan.html section 10's own first step.

  1. YouCreate the GitHub repo and open a Codespace on it. The one step in this whole session that's entirely yours from the very first click — nothing exists yet for Claude to run, and this is all browser/GUI.
    1. Create a new (or reuse an existing) GitHub repository for the project.
    2. From the repo's page: <> Code button → Codespaces tab → Create codespace on main. This opens a full VS Code environment — in the browser, or the desktop VS Code app connected to it, your choice — backed by a cloud Linux container. Git and gh are already authenticated inside it; there's no separate git-identity or gh auth login step to do here, unlike the two earlier versions of this plan.
  2. YouInstall the Claude Code CLI in the Codespace's terminal, then log in. Nothing exists yet for a Claude Code session to run the remaining steps below with — the same bootstrapping reason step 1 above was entirely yours. Linux is a directly supported platform, same self-contained installer as macOS, no Node.js needed: 
    1. curl -fsSL https://claude.ai/install.sh | bash
    2. Run claude and log in — pick one:
      • Your Claude.ai account (Pro/Max). Normally opens a browser via the Codespace's own port-forwarding and completes automatically; if the browser shows a login code instead of redirecting back, paste that code into the "Paste code here if prompted" terminal prompt instead.
      • An Anthropic Console API key instead. Generate one at platform.claude.com, then either export ANTHROPIC_API_KEY="…" before running claude, or — better for a Codespace, since it survives a rebuild — add it as a Codespaces secret (repo/org Settings → Secrets → Codespaces) so it's already set as an environment variable next time.
      Note for later: ~/.claude (the logged-in session) is cleared on a full Codespace rebuild (a plain stop/resume keeps it) — an occasional re-login after a rebuild is normal, not a bug.
  3. ClaudeInstall the Android command-line SDK and a JDK — no Android Studio, no emulator, the same standard pattern CI pipelines already use to build Android apps in Linux containers: 
    sudo apt-get update && sudo apt-get install -y openjdk-17-jdk unzip
    then download the Android cmdline-tools into ~/android-sdk/cmdline-tools/latest, export ANDROID_HOME/ANDROID_SDK_ROOT + PATH, and run sdkmanager for platform-tools, a current platforms;android-XX, and matching build-tools.
  4. YouPrepare the Samsung phone and bridge it to the Codespace. This is the one genuinely new problem this toolchain has that the Windows/Android-Studio version didn't: a cloud container can't see a USB-connected phone on its own. Neither option below has been tested end-to-end for this exact plan yet — treat this step as something to validate this session, not a guarantee.
    1. Confirm the phone is on Android 12+ (Settings → About phone → Android version) — plan.html section 07's minSdk 31 decision depends on it. Enable Developer Options (tap "Build number" 7 times), then turn on USB debugging.
    2. Option 1 — a local ADB-server bridge via gh (recommended default). On the Windows PC, install just the small Android SDK Platform-Tools zip (not all of Android Studio) to get adb.exe, plus the GitHub CLI if it isn't already there. Connect the phone by USB, confirm adb.exe devices sees it, then run: 
      gh codespace ports forward 5037:5037 -c <codespace-name>
      which forwards port 5037 from the Codespace to the Windows PC's local ADB server. Inside the Codespace, point its own adb at that forwarded port (ADB_SERVER_SOCKET=tcp:localhost:5037) so adb install/adb logcat run from Claude's own terminal reach the real phone.
    3. Option 2 — Wireless Debugging + ngrok. Pair the phone's Wireless debugging feature from a local machine once, then use an ngrok TCP tunnel so the Codespace can adb pair/adb connect to it directly, with nothing needing to keep running on the Windows side afterward. Needs a free ngrok account, and briefly exposes the phone's debug port to a public address each session.
  5. ClaudeScaffold a minimal Kotlin/Gradle/Compose project directly (Claude writes the Gradle files and MainActivity.kt straight into a folder, no wizard) — package root com.twrconsulting.sentinel (placeholder), just MainActivity showing "Hello Compose," nothing else — in its own standalone git repo, not inside Fun. Push it with gh repo create sentinel --private --source=. --remote=origin --push, or push to the repo already created in step 1.
  6. ClaudeYouBuild, install, and launch — all from the Codespace's terminal: 
    ./gradlew assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
    Claude runs both; confirming it actually launches means looking at the phone's screen (you).
Done when A "Hello Compose" APK builds inside the Codespace and launches on the Samsung phone over the ADB bridge. This proves the whole toolchain end to end, bridge included — nothing else gets built until this works.

Session 2Data model & correlation engine

Status: Not started Needs hardware: No — pure JVM, inside the project scaffolded in Session 1 Est. time: 90–120 min Depends on: Session 1

Goal: the Room schema and the core TrackerCorrelationEngine, verified with synthetic fixtures — no scanning code yet, per plan.html section 10's own ordering ("get this right first").

  1. ClaudeAdd Hilt (DI) and Room with KSP — not kapt — to the project's Gradle config.
  2. ClaudeWrite the six Room entities from plan.html section 03's table: DeviceEntity, SightingEntity, KnownTrackerSignatureEntity, IgnoredDeviceEntity, FlagEventEntity, LocationClusterEntity.
  3. ClaudeSeed KnownTrackerSignatureEntity with the documented public formats: Apple Find My (manufacturer ID 0x004C), Samsung SmartTag/SmartTag2 (0x0075), Tile and Chipolo (service-UUID based).
  4. ClaudeImplement LocationClusterer (incremental centroid clustering, 150m threshold, Haversine distance) and TrackerCorrelationEngine plus FlagScorer per plan.html section 04: the hard gates (≥3 distinct clusters, ≥20 minutes first-to-last span) before any scoring, then the 0–100 suspicion score with its known-signature bonus and weak-identity discount.
  5. ClaudeSet android:allowBackup="false" and exclude the Room database from auto-backup rules now, while the database is first created — this data is a de facto location history and shouldn't have a window where it's backed up by default.
  6. Claude./gradlew test against synthetic sighting fixtures: at minimum, one stationary device across many sightings in a single cluster that never flags, one tracker-like device seen across 3+ clusters with a plausible time span that does flag, and one case confirming the known-signature match adds its scoring bonus.
Done when ./gradlew test passes with synthetic fixtures covering at least one true-flag case and one true-negative (stationary device) case — no device needed for this session.

Session 3BLE parsing & MAC-rotation linking

Status: Not started Needs hardware: No for this session — a real BLE tracker only matters later, in Session 7 Est. time: 60–90 min Depends on: Session 2

Goal: BleAdvertisementParser and the rotation-tolerant identity-linking heuristic from plan.html section 03's "Why raw MAC address can't be trusted as identity" subsection.

  1. ClaudeImplement BleAdvertisementParser: recognize each signature family seeded in Session 2 from its manufacturer payload, since that format is far more stable than a rotating address.
  2. ClaudeImplement the linking heuristic: if a same-family device disappears and a new MAC of the same family appears within roughly 15 minutes, at similar RSSI and location, merge the sightings under the same stableDeviceKey — while still keeping the raw per-sighting address, so nothing is lost if the heuristic mis-links two devices.
  3. ClaudeFor unrecognized BLE devices, discount MAC continuity heavily past roughly 20–30 minutes, treating it as a weak, short-term-only signal.
  4. ClaudeExplicitly do not attempt to cryptographically defeat address rotation (e.g. Apple's Find My rolling-key derivation) — out of scope, matching plan.html section 03's fourth point.
  5. ClaudeUnit tests: a synthetic MAC-rotation sequence that should link (same family, short gap, similar RSSI/location) and one that shouldn't (too long a gap, or a different family).
Done when The parser correctly classifies each seeded signature family from a synthetic payload, and the linking-heuristic tests demonstrate both a correct merge and a correct non-merge.

Session 4Foreground scanning service & permissions

Status: Not started Needs hardware: the Samsung phone — the first real on-device milestone Est. time: 90–120 min Depends on: Sessions 2, 3

Goal: real BLE and WiFi sightings landing in the database from a running foreground service, per plan.html section 05 and section 07.

  1. ClaudeAdd the manifest permissions and uses-feature entries exactly as listed in plan.html section 07: BLUETOOTH_SCAN with neverForLocation, BLUETOOTH_CONNECT, fine/coarse location, WiFi state, NFC as an optional feature, the three FOREGROUND_SERVICE* permissions, POST_NOTIFICATIONS, and the battery-optimization request permission.
  2. ClaudeImplement ScanForegroundService (Android 14+ types connectedDevice|location) with duty-cycled BLE bursts (SCAN_MODE_BALANCED, every 2–5 minutes), one WiFi startScan() per cycle, and a passive SCAN_RESULTS_AVAILABLE_ACTION receiver to catch scans the OS triggers on its own.
  3. ClaudeImplement ScanScheduler/ScanWorker as the periodic WorkManager watchdog that restarts the foreground service if Samsung's OEM battery management kills it.
  4. ClaudeWire DeviceRepository's Room @Transaction upsert keyed on stableDeviceKey, using Session 2's schema and Session 3's parser/linker.
  5. ClaudeYouBuild and install (./gradlew assembleDebug then adb install over the phone bridge) — Claude. Confirming it worked needs a human: tapping through the live system permission dialogs Android pops up (no agent can dismiss those), then looking at the phone to confirm the foreground-service notification shows and real BLE/WiFi sightings start populating the database (no UI to view them yet — a debug log or a direct DB query is enough).
  6. YouManually apply the Samsung One UI battery exclusion (Device Care → Battery → Background usage limits) — plan.html section 07 and 09 both note this can't be done by the app itself, and it's a Settings-UI toggle no agent can flip for you.
Done when The service runs on the Samsung phone, survives a short screen-off spot check without being killed (the full multi-hour check is Session 7), and real sightings are landing in the database.

Session 5WiFi polish & the NFC screen

Status: Not started Needs hardware: the Samsung phone (WiFi + NFC) — the "no NFC hardware" negative check is a unit test, no second device needed Est. time: 60–90 min Depends on: Session 4

Goal: accept WiFi's real throttling ceiling rather than fighting it, and add the manual NFC tag-inspection screen from plan.html section 06.

  1. YouConfirm WiFi scanning lands at roughly 30–60 second effective resolution per plan.html section 07 — this is an OS throttle on stock, unrooted Android, not a bug to chase away; confirming the real cadence means watching it happen on the Samsung phone.
  2. ClaudeImplement NfcTagReader and the NFC Tag Read screen: UID, tech list, NDEF dump if present; MIFARE Classic reports "detected, sectors not readable without keys" rather than attempting key-cracking.
  3. ClaudeSet the foreground-dispatch PendingIntent to FLAG_MUTABLE — the specific gotcha plan.html section 07 calls out; the usual post-Android-12 FLAG_IMMUTABLE default breaks tag delivery here.
  4. ClaudeUnit test the "no NFC hardware" state with a mocked/null NfcAdapter.getDefaultAdapter() — there's no emulator or second physical device in this toolchain to run a live negative check on, so this is verified in code instead (./gradlew test).
  5. YouTest real tag reads on the Samsung phone — physically tapping a tag to it and reading the result on screen. (This assumes the phone has NFC hardware — confirm that if it hasn't already come up; most modern Samsung phones do.)
Done when The NFC screen reads a real tag's UID/tech list/NDEF on the Samsung phone, and the mocked-NfcAdapter unit test confirms the graceful unavailable state.

Session 6Compose UI wired to live data

Status: Not started Needs hardware: the Samsung phone Est. time: 90 min Depends on: Sessions 4, 5

Goal: all five v1 screens from plan.html section 06, live against the real data flowing in from Sessions 4–5.

  1. ClaudeNearby: live BLE+WiFi list via Room Flow, signal strength, swipe-to-ignore, manual "scan now" button.
  2. ClaudeFlagged: sorted-by-score list with the human-readable reason string (e.g. "seen at 4 locations up to 6.2km apart over 5h; matches Apple Find My format"), dismiss/view actions.
  3. ClaudeDevice Detail: identity, all linked raw addresses, sighting history on a map via OSMDroid (not Google Maps, to avoid the API-key/Play-Services dependency), ignore/nickname actions.
  4. ClaudeSettings: scan interval, sensitivity (Low/Medium/High mapped to the flag threshold), cluster-distance (advanced), ignore-list management, data retention/export/clear, scanning kill switch.
  5. ClaudeOnboarding wizard: auto-suggest ignoring the user's own bonded Bluetooth devices and the currently-connected WiFi network, per plan.html section 04's false-positive suppression.
  6. ClaudeThe NFC screen from Session 5 becomes reachable from this UI rather than a standalone test harness.

Every step above is code Claude can write; actually looking at the five screens on the Samsung phone and confirming they feel right is You — see this session's "Done when" line below.

Done when All five screens are live against real on-device data, and the ignore/dismiss actions actually suppress future flags rather than just updating the display.

Session 7On-device validation

Status: Not started Needs hardware: the Samsung phone + a real or simulated BLE tracker Est. time: spans at least one multi-hour period, not a single sitting Depends on: everything above

Goal: the real-world checks from plan.html section 11 — this is native Android code that can't be honestly signed off from a CLI sandbox, so this session is where the actual claims get tested against reality.

  1. ClaudeRun the full ./gradlew test suite one more time (correlation engine, clusterer, signature matcher, parser, linking heuristic) as a baseline before the real-hardware checks.
  2. YouPlace a known BLE tracker (or a phone advertising a similar payload) at 3+ physically distinct locations over time; confirm it gets flagged. Physically carrying hardware around is inherently a you-task.
  3. YouConfirm a stationary device (a home router) never gets flagged — check the Flagged screen yourself; Claude can help interpret an exported log if you hand it one, but can't watch the device over time on its own.
  4. ClaudeYouadb logcat over several hours, including a screen-off/Doze period and an app-switch/backgrounding test — Claude can run and parse the log if it has a terminal connected to the device, but you're the one putting the phone through a real screen-off/Doze period and switching apps on it.
  5. YouRe-confirm the NFC screen's real tag read on the Samsung phone, now as part of the full app rather than a standalone test harness (the graceful-unavailable state stays covered by Session 5's unit test).
  6. ClaudeYouWrite down real-world findings in this session's notes: any false positives/negatives encountered, whether the co-traveler hard case (plan.html section 09) actually showed up, whether the default flag threshold of roughly 55 felt right in practice, and any Codespaces/ADB-bridge/Gradle gotchas hit beyond what plan.html section 08 already documents. You supply the raw observations; Claude can help write them up.
Done when A real tracker gets flagged after being carried to 3+ locations, a stationary device never gets flagged, the service survives a multi-hour real-world run including a Doze period, and the findings above are written into this session's notes — not just "it didn't crash."
