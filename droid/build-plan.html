Sentinel — Build Plan

The design in plan.html turned into seven self-contained work sessions, following that page's own section 10 build order exactly. The actual Kotlin/Gradle project lives in its own standalone repo, built and tested via Termux directly on the Galaxy Tab S11 Ultra — this page just tracks that separate project's progress from inside Fun/droid/, the way the Claude Architect Lab build plan tracks that project.

Status: nothing started yet As of this writing no Kotlin/Gradle project exists — Session 1 below hasn't been run. Every session's Not started badge reflects that; update them here as the standalone repo actually gets built.
Key: who does each step Every numbered step below is tagged Claude or You, sometimes both. Claude marks anything this assistant can do directly once it has a terminal in the right place — writing code, editing Gradle/manifest config, seeding data, running ./gradlew test/assembleDebug — including from inside a Termux shell on the tablet itself, if that's where a session happens to be running. You marks anything no coding agent can do on your behalf: tapping through an app-store install or a system permission dialog, flipping an Android Settings toggle, physically carrying hardware between locations, or tapping an NFC tag to a phone. A step tagged with both means it splits — Claude builds it, you tap through the install or eyeball the result on the real device.

Before you startHow to use this plan

Unlike a pure-software plan, most of these sessions need real hardware in hand — the Galaxy Tab S11 Ultra for Sessions 1, 2, 4, 5, 6, and 7, plus a phone with NFC hardware for the NFC half of Sessions 5 and 7. There's no CLI-sandbox or emulator fallback for the on-device sessions: this environment has no Android SDK, no emulator, and no ADB link (the same limit plan.html section 11 already states), so those steps genuinely have to happen on the tablet itself, via Termux.

  • Start each new session by reading this plan and the "Done when" line of whatever session you finished last — a fresh Claude Code session run from Termux has no memory of prior sessions, so re-orienting from this document is faster than re-deriving context from code.
  • Don't open a session's next steps as extra credit. Each session ends at a real boundary — Session 1 stops at a launching "Hello Compose" APK, not a taste of Room; Session 4 stops at a running foreground service, not the UI. Resist folding the next session in just because time is left.
  • Sessions 2 and 3 need no device at all — they're pure JVM logic (the correlation engine, the clusterer, the BLE payload parser) verified with ./gradlew test, the same "no live dependency" split the Claude Architect Lab plan uses for its own no-API-key sessions. Everything from Session 4 onward needs the tablet.
  • Termux/SDK package versions drift. Re-check current aapt2/NDK/cmdline-tools behavior against plan.html section 08 before assuming a fix documented there still applies exactly as written — that section already required one real workaround (the aapt2FromMavenOverride escape hatch) that wouldn't have been obvious from a fresh Android Studio setup.
  • Every session below cross-references the exact section of plan.html it implements — this page sequences the work, it doesn't redesign it. If something here seems to contradict that page, plan.html is the source of truth; treat the mismatch as a bug in this page.
  • This page doubles as the tracker. Each session has a Status line (Not started, In progress, or Done) in its meta row, and a Session notes callout underneath its "Done when" line. When a session is finished, flip its badge to Done in both places (the session's own meta row and the session-index table) and log anything worth remembering — a Termux gotcha beyond what plan.html already documents, a real device quirk, a divergence from plan.html, a dead end. Leave a session's notes as "None yet." if nothing came up.

Session 1Termux toolchain & Hello Compose

Status: Not started Needs hardware: Galaxy Tab S11 Ultra Est. time: 60–90 min Depends on: nothing

Goal: validate the entire build-and-install pipeline with a trivial app before writing any real feature code, per plan.html section 10's own first step.

  1. YouInstall Termux and its Termux:API companion app on the tablet. The one step in this whole plan that's entirely yours from the very first tap — nothing exists yet for Claude to run, and app installs and their permission prompts are GUI-only. Broken into order, with the one real decision called out:
    1. Decide your install source — pick one:
      • Option 1 — F-Droid (recommended default). If F-Droid itself isn't already on the tablet, install it first from f-droid.org; then use F-Droid's own search to find and install both "Termux" and "Termux:API". What you get: automatic updates through F-Droid going forward. Trade-off: F-Droid's build occasionally lags a version or two behind GitHub's newest tag.
      • Option 2 — GitHub releases (.apk files). Download the newest release APK for each app directly from github.com/termux/termux-app/releases and github.com/termux/termux-api/releases, then sideload them. What you get: always the newest version the day it ships. Trade-off: no auto-update — you redownload by hand whenever you want a newer one — and whichever app you use to download the APK will need a one-time "allow installs from this source" toggle in Android Settings before it'll install.
      Either option is fine; what matters is picking one and using it for both apps below, not which one you pick. Not fine either way: the Google Play Store's "Termux" listing — plan.html section 08 already flags it as a years-stale, abandoned build, and installing it here would cause confusing failures several steps from now (package installs failing, a mismatched aapt2), not immediately.
    2. Install Termux itself, through the source you picked in (a).
    3. Install Termux:API the same way, through the same source as (b) — mixing sources works too, but keeping them matched keeps future updates simpler.
    4. Open Termux once. Confirm it actually launches to a shell prompt, and grant whatever storage permission it asks for on first run (needed later for things like installing a built APK via termux-open).
  2. YouInstall the Claude Code CLI itself inside Termux, then log in. Nothing exists yet for a Claude Code session to run the remaining steps below with — the same bootstrapping reason step 1 above was entirely yours.
    1. pkg install nodejs git -y, then npm install -g @anthropic-ai/claude-code.
    2. If the shell doesn't find claude afterward, alias it straight at the installed script and reload the shell: echo "alias claude='node /data/data/com.termux/files/usr/lib/node_modules/@anthropic-ai/claude-code/cli.js'" >> ~/.bashrc && source ~/.bashrc. Confirm with claude --version.
    3. Run claude and log in — pick one:
      • Your Claude.ai account (Pro/Max). Termux has no default browser to catch the OAuth redirect, so when it shows a login URL, copy it, open that URL in a browser on any device, sign in, and paste the code back into the Termux prompt.
      • An Anthropic Console API key instead. Generate one at platform.claude.com first, then export ANTHROPIC_API_KEY="…" before running claude — no browser step, but bills per-token from Console credits rather than a Pro/Max subscription.
      Not officially supported: Claude Code's own docs list only macOS, Windows, Ubuntu, Debian, and Alpine — Android/Termux works via a community-tested workaround, not a documented platform, so treat an odd failure here as that first, not a bug in this plan.
  3. ClaudeYouConnect this Termux session to GitHub and a new repo for the project.
    1. pkg install gh -y — Claude, now that the step above gives it a shell to run in.
    2. gh auth login → GitHub.com → HTTPS → Login with a web browser — the same copy-the-URL-paste-the-code flow as logging into Claude Code itself (you).
    3. git config --global user.name "…" and git config --global user.email "…" — your call whether to use a real address or a GitHub-provided @users.noreply.github.com one, since this is its own repo with no CLAUDE.md of its own yet (a decision only you can make; Claude can type it once you've decided).
    4. Once the project exists (the scaffolding step below), create and push the repo in one shot from inside its directory: gh repo create sentinel --private --source=. --remote=origin --push — or create an empty repo on github.com first and git remote add origin … / git push -u origin main by hand instead.
  4. Claudepkg install openjdk-17 wget unzip git aapt2 termux-api android-tools, run from inside the Termux shell once it exists.
  5. ClaudeSet up the Android cmdline-tools under ~/android-sdk, export ANDROID_HOME/ANDROID_SDK_ROOT + PATH, then run sdkmanager for platform-tools, a current platforms;android-XX, and matching build-tools.
  6. ClaudeApply both gradle.properties fixes from plan.html section 08 up front: android.aapt2FromMavenOverride pointing at the Termux-native aapt2, and org.gradle.vfs.watch=false.
  7. ClaudeScaffold a minimal Kotlin/Gradle/Compose project — package root com.twrconsulting.sentinel (placeholder), just MainActivity showing "Hello Compose," nothing else — in its own standalone git repo, not inside Fun. Connect it to GitHub using the gh setup from the step above once the repo directory exists.
  8. YouConfirm the test tablet is actually on Android 12+ before going further (Settings → About tablet → Android version); plan.html section 07's minSdk 31 decision depends on it.
  9. ClaudeYou./gradlew assembleDebug (Claude), then either termux-open the debug APK (manual tap-through install) or set up wireless ADB per section 08 if faster iteration is worth the one-time pairing step — either way, confirming the app actually launches means looking at the tablet's screen (you).
Done when A "Hello Compose" APK builds under Termux and launches on the tablet. This proves the whole toolchain end to end — nothing else gets built until this works.

Session 2Data model & correlation engine

Status: Not started Needs hardware: No — pure JVM, inside the project scaffolded in Session 1 Est. time: 90–120 min Depends on: Session 1

Goal: the Room schema and the core TrackerCorrelationEngine, verified with synthetic fixtures — no scanning code yet, per plan.html section 10's own ordering ("get this right first").

  1. ClaudeAdd Hilt (DI) and Room with KSP — not kapt — to the project's Gradle config.
  2. ClaudeWrite the six Room entities from plan.html section 03's table: DeviceEntity, SightingEntity, KnownTrackerSignatureEntity, IgnoredDeviceEntity, FlagEventEntity, LocationClusterEntity.
  3. ClaudeSeed KnownTrackerSignatureEntity with the documented public formats: Apple Find My (manufacturer ID 0x004C), Samsung SmartTag/SmartTag2 (0x0075), Tile and Chipolo (service-UUID based).
  4. ClaudeImplement LocationClusterer (incremental centroid clustering, 150m threshold, Haversine distance) and TrackerCorrelationEngine plus FlagScorer per plan.html section 04: the hard gates (≥3 distinct clusters, ≥20 minutes first-to-last span) before any scoring, then the 0–100 suspicion score with its known-signature bonus and weak-identity discount.
  5. ClaudeSet android:allowBackup="false" and exclude the Room database from auto-backup rules now, while the database is first created — this data is a de facto location history and shouldn't have a window where it's backed up by default.
  6. Claude./gradlew test against synthetic sighting fixtures: at minimum, one stationary device across many sightings in a single cluster that never flags, one tracker-like device seen across 3+ clusters with a plausible time span that does flag, and one case confirming the known-signature match adds its scoring bonus.
Done when ./gradlew test passes with synthetic fixtures covering at least one true-flag case and one true-negative (stationary device) case — no device or emulator needed for this session.

Session 3BLE parsing & MAC-rotation linking

Status: Not started Needs hardware: No for this session — a real BLE tracker only matters later, in Session 7 Est. time: 60–90 min Depends on: Session 2

Goal: BleAdvertisementParser and the rotation-tolerant identity-linking heuristic from plan.html section 03's "Why raw MAC address can't be trusted as identity" subsection.

  1. ClaudeImplement BleAdvertisementParser: recognize each signature family seeded in Session 2 from its manufacturer payload, since that format is far more stable than a rotating address.
  2. ClaudeImplement the linking heuristic: if a same-family device disappears and a new MAC of the same family appears within roughly 15 minutes, at similar RSSI and location, merge the sightings under the same stableDeviceKey — while still keeping the raw per-sighting address, so nothing is lost if the heuristic mis-links two devices.
  3. ClaudeFor unrecognized BLE devices, discount MAC continuity heavily past roughly 20–30 minutes, treating it as a weak, short-term-only signal.
  4. ClaudeExplicitly do not attempt to cryptographically defeat address rotation (e.g. Apple's Find My rolling-key derivation) — out of scope, matching plan.html section 03's fourth point.
  5. ClaudeUnit tests: a synthetic MAC-rotation sequence that should link (same family, short gap, similar RSSI/location) and one that shouldn't (too long a gap, or a different family).
Done when The parser correctly classifies each seeded signature family from a synthetic payload, and the linking-heuristic tests demonstrate both a correct merge and a correct non-merge.

Session 4Foreground scanning service & permissions

Status: Not started Needs hardware: Galaxy Tab S11 Ultra — the first real on-device milestone Est. time: 90–120 min Depends on: Sessions 2, 3

Goal: real BLE and WiFi sightings landing in the database from a running foreground service, per plan.html section 05 and section 07.

  1. ClaudeAdd the manifest permissions and uses-feature entries exactly as listed in plan.html section 07: BLUETOOTH_SCAN with neverForLocation, BLUETOOTH_CONNECT, fine/coarse location, WiFi state, NFC as an optional feature, the three FOREGROUND_SERVICE* permissions, POST_NOTIFICATIONS, and the battery-optimization request permission.
  2. ClaudeImplement ScanForegroundService (Android 14+ types connectedDevice|location) with duty-cycled BLE bursts (SCAN_MODE_BALANCED, every 2–5 minutes), one WiFi startScan() per cycle, and a passive SCAN_RESULTS_AVAILABLE_ACTION receiver to catch scans the OS triggers on its own.
  3. ClaudeImplement ScanScheduler/ScanWorker as the periodic WorkManager watchdog that restarts the foreground service if Samsung's OEM battery management kills it.
  4. ClaudeWire DeviceRepository's Room @Transaction upsert keyed on stableDeviceKey, using Session 2's schema and Session 3's parser/linker.
  5. ClaudeYouBuild and install (termux-open or wireless ADB) — Claude. Confirming it worked needs a human: tapping through the live system permission dialogs Android pops up (no agent can dismiss those), then looking at the tablet to confirm the foreground-service notification shows and real BLE/WiFi sightings start populating the database (no UI to view them yet — a debug log or a direct DB query is enough).
  6. YouManually apply the Samsung One UI battery exclusion (Device Care → Battery → Background usage limits) — plan.html section 07 and 09 both note this can't be done by the app itself, and it's a Settings-UI toggle no agent can flip for you.
Done when The service runs on the tablet, survives a short screen-off spot check without being killed (the full multi-hour check is Session 7), and real sightings are landing in the database.

Session 5WiFi polish & the NFC screen

Status: Not started Needs hardware: Galaxy Tab S11 Ultra (WiFi) + a phone with NFC hardware (NFC half) Est. time: 60–90 min Depends on: Session 4

Goal: accept WiFi's real throttling ceiling rather than fighting it, and add the manual NFC tag-inspection screen from plan.html section 06.

  1. YouConfirm WiFi scanning lands at roughly 30–60 second effective resolution per plan.html section 07 — this is an OS throttle on stock, unrooted Android, not a bug to chase away; confirming the real cadence means watching it happen on the tablet.
  2. ClaudeImplement NfcTagReader and the NFC Tag Read screen: UID, tech list, NDEF dump if present; MIFARE Classic reports "detected, sectors not readable without keys" rather than attempting key-cracking.
  3. ClaudeSet the foreground-dispatch PendingIntent to FLAG_MUTABLE — the specific gotcha plan.html section 07 calls out; the usual post-Android-12 FLAG_IMMUTABLE default breaks tag delivery here.
  4. YouConfirm the tablet (if it lacks NFC hardware) shows a graceful "no NFC hardware" state instead of crashing — a visual check on the device.
  5. YouTest real tag reads on the phone that has NFC hardware — physically tapping a tag to the phone and reading the result on screen.
Done when The NFC screen reads a real tag's UID/tech list/NDEF on the phone, and shows a graceful unavailable state on the tablet if it lacks the radio.

Session 6Compose UI wired to live data

Status: Not started Needs hardware: Galaxy Tab S11 Ultra Est. time: 90 min Depends on: Sessions 4, 5

Goal: all five v1 screens from plan.html section 06, live against the real data flowing in from Sessions 4–5.

  1. ClaudeNearby: live BLE+WiFi list via Room Flow, signal strength, swipe-to-ignore, manual "scan now" button.
  2. ClaudeFlagged: sorted-by-score list with the human-readable reason string (e.g. "seen at 4 locations up to 6.2km apart over 5h; matches Apple Find My format"), dismiss/view actions.
  3. ClaudeDevice Detail: identity, all linked raw addresses, sighting history on a map via OSMDroid (not Google Maps, to avoid the API-key/Play-Services dependency), ignore/nickname actions.
  4. ClaudeSettings: scan interval, sensitivity (Low/Medium/High mapped to the flag threshold), cluster-distance (advanced), ignore-list management, data retention/export/clear, scanning kill switch.
  5. ClaudeOnboarding wizard: auto-suggest ignoring the user's own bonded Bluetooth devices and the currently-connected WiFi network, per plan.html section 04's false-positive suppression.
  6. ClaudeThe NFC screen from Session 5 becomes reachable from this UI rather than a standalone test harness.

Every step above is code Claude can write; actually looking at the five screens on the tablet and confirming they feel right is You — see this session's "Done when" line below.

Done when All five screens are live against real on-device data, and the ignore/dismiss actions actually suppress future flags rather than just updating the display.

Session 7On-device validation

Status: Not started Needs hardware: Galaxy Tab S11 Ultra + a phone with NFC + a real or simulated BLE tracker Est. time: spans at least one multi-hour period, not a single sitting Depends on: everything above

Goal: the real-world checks from plan.html section 11 — this is native Android code that can't be honestly signed off from a CLI sandbox, so this session is where the actual claims get tested against reality.

  1. ClaudeRun the full ./gradlew test suite one more time (correlation engine, clusterer, signature matcher, parser, linking heuristic) as a baseline before the real-hardware checks.
  2. YouPlace a known BLE tracker (or a phone advertising a similar payload) at 3+ physically distinct locations over time; confirm it gets flagged. Physically carrying hardware around is inherently a you-task.
  3. YouConfirm a stationary device (a home router) never gets flagged — check the Flagged screen yourself; Claude can help interpret an exported log if you hand it one, but can't watch the device over time on its own.
  4. ClaudeYouadb logcat over several hours, including a screen-off/Doze period and an app-switch/backgrounding test — Claude can run and parse the log if it has a terminal connected to the device, but you're the one putting the tablet through a real screen-off/Doze period and switching apps on it.
  5. YouRe-confirm the NFC screen on the phone and the graceful unavailable state on the tablet, now as part of the full app rather than a standalone test harness.
  6. ClaudeYouWrite down real-world findings in this session's notes: any false positives/negatives encountered, whether the co-traveler hard case (plan.html section 09) actually showed up, whether the default flag threshold of roughly 55 felt right in practice, and any Termux/build gotchas hit beyond what section 08 already documents. You supply the raw observations; Claude can help write them up.
Done when A real tracker gets flagged after being carried to 3+ locations, a stationary device never gets flagged, the service survives a multi-hour real-world run including a Doze period, and the findings above are written into this session's notes — not just "it didn't crash."
