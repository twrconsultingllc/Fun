Sentinel — Tracker Detector

A native Android app, planned but not yet built, to answer one question: is a Bluetooth/WiFi device following me? It scans nearby BLE and WiFi signals, logs sightings with time and location, and flags anything seen repeatedly across places a stationary device (a router, a shop beacon) never would be. It also includes a manual NFC tag-inspection screen. Everything stays on the device — no cloud backend.

Status: plan only, nothing built yet This page records the design so it survives between sessions. No Kotlin/Gradle project exists yet, and the actual app will live in its own standalone git repo — not in this Fun repo, whose single-file-HTML-toy conventions don't fit a native app. This page is the plan and progress record, not the app itself.

01 · Locked inDecisions already made

Build & test Android Studio on a Windows PC — not Termux on a tablet, which is how this plan originally started. The emulator (bundled with Android Studio) covers most iteration; a Samsung phone, connected over USB or wireless ADB, is the one physical device used for real-device and on-device validation. No tablet is involved at all.
v1 scope BLE + WiFi ambient scanning, and a manual NFC tag-inspection screen — tested on the Samsung phone, which is assumed to have NFC hardware (confirm this; most modern Samsung phones do). The emulator has no NFC radio at all, which conveniently doubles as the "no NFC hardware" negative-path test without needing a second physical device.
Detection logic The full time+location repeat-sighting correlation engine for v1 — not just known-tracker-signature matching (though signature matching is folded in as a scoring boost, since it's free extra evidence).
Privacy All data stays local/on-device. No cloud backend, no telemetry.
Repo Standalone git repo for the actual Kotlin/Gradle project — this page just tracks the plan inside Fun/droid/ because that's where it was asked to live.

This is the same problem space Apple's and Google's built-in "unknown tracker alerts" and the open-source AirGuard app solve, and the design below follows the same public, non-exploitative approach they use: recognizing publicly-broadcast tracker advertisement formats, and noticing repeat sightings across locations. No cracking of rotating identifiers, no root required.

02 · StructureApp architecture

Single-module Kotlin app using Jetpack Compose. State-heavy, live-updating scan lists map naturally onto Compose + Room Flow, with far less boilerplate than Views/RecyclerView, and there's no legacy code to preserve. Suggested package root: com.twrconsulting.sentinel (placeholder name).

Use Hilt for dependency injection and KSP (not kapt) for Room's annotation processing — KSP is Google's modern replacement for kapt and noticeably faster, with no real downside now that Room fully supports it. Set android:allowBackup="false" and exclude the Room database from Android's auto-backup rules: this data is a de facto location history and must never leave the device via cloud backup.

03 · SchemaData model & MAC randomization

EntityPurpose
DeviceEntitykind (BLE/WIFI_AP), stableDeviceKey, lastKnownAddress, displayName, manufacturerId, vendorGuess, first/last seen, sighting count, isIgnored, userLabel
SightingEntityper-observation row: raw address at time of sighting, RSSI, timestamp, lat/lon/accuracy (nullable), locationClusterId, raw manufacturer-data payload (hex, for re-parsing)
KnownTrackerSignatureEntityseed table of publicly documented BLE advertisement formats — Apple Find My (manufacturer ID 0x004C), Samsung SmartTag/SmartTag2 (0x0075), Tile, Chipolo (service-UUID based) — with a match rule and a suspicion-score weight
IgnoredDeviceEntity, FlagEventEntity, LocationClusterEntityignore-list, raised flags, and incremental location clusters (see section 04)

Why raw MAC address can't be trusted as identity

Trackers and modern BLE devices rotate their MAC address periodically — a naive "same MAC = same device" match fails. The strategy:

  1. Prefer manufacturer-payload-derived identity for recognized tracker families (the payload format itself is far more stable than the rotating address).
  2. Apply a rotation-tolerant linking heuristic: if a same-family device disappears and a new MAC of the same family appears within roughly 15 minutes, at similar RSSI and location, merge the sightings under the same stableDeviceKey — while still keeping the raw per-sighting address, so nothing is silently lost if the heuristic mis-links two devices.
  3. For unrecognized BLE devices, treat MAC continuity as a weak, short-term-only signal, discounted heavily in the correlation engine past ~20–30 minutes.
  4. Never attempt to cryptographically defeat address rotation (e.g. breaking Apple's Find My rolling-key derivation) — that's out of scope and unnecessary. Payload-format recognition plus statistical/temporal correlation is exactly the approach AirGuard, Apple's own "Tracker Detect," and Google's "unknown tracker alerts" already use publicly.

04 · The core algorithmCorrelation / detection algorithm

Runs periodically (DetectionWorker, roughly every 30 minutes) over a rolling 24-hour window.

1. Location clustering

Incremental centroid clustering, 150m threshold (tunable) via Haversine distance. This single gate is what naturally suppresses stationary false positives — a home router or shop beacon only ever lands in one cluster, so it can never satisfy the "seen at multiple places" test below.

2. Hard gates before scoring

  • At least 3 distinct location clusters
  • At least 20 minutes between first and last sighting

3. Suspicion score (0–100)

  • Points for distinct cluster count (capped)
  • Points for the maximum distance between clusters — a bigger geographic spread is stronger evidence than GPS jitter within one place
  • Points for distinct time-sessions — repeat visits score higher than one long continuous dwell
  • A large bonus for matching a known tracker signature
  • A confidence discount when identity evidence is weak (unrecognized payload plus long-span MAC-only linkage)

Flag threshold defaults to roughly 55, exposed to the user as a simple Low/Medium/High sensitivity setting rather than raw numbers.

4. False-positive suppression

  • An onboarding wizard auto-suggests ignoring the user's own bonded Bluetooth devices and the currently-connected WiFi network
  • Swipe-to-ignore from the Nearby list for anything else
  • Dismissed flags don't re-fire unless new anomalous behavior appears
  • A daily-commute "co-traveler" device (e.g. another rider's phone on the same bus every day) is a known hard case even for tools like AirGuard — v1 surfaces full sighting detail so the user can judge and dismiss it, rather than trying to solve it algorithmically

05 · Keeping it runningBackground scanning

Hybrid: a foreground service (primary) plus WorkManager (a watchdog). WorkManager's 15-minute floor and Doze throttling are too coarse to reliably catch a transient tracker, so ScanForegroundService (Android 14+ types connectedDevice|location) owns duty-cycled scanning: BLE bursts every 2–5 minutes using SCAN_MODE_BALANCED (not low-latency), one WiFi startScan() per cycle, plus a passive SCAN_RESULTS_AVAILABLE_ACTION receiver to catch scans the OS triggers on its own for free. A separate periodic ScanScheduler worker restarts the foreground service if Samsung's OEM battery management kills it. All writes go through DeviceRepository using a Room @Transaction upsert keyed on stableDeviceKey; the UI reads live via Room Flow.

07 · Android platform mechanicsPermissions, NFC, WiFi throttling, battery

minSdk 31 (Android 12) — drops the entire legacy pre-BLUETOOTH_SCAN permission branch; confirm the test phone is on 12+ before finalizing. targetSdk/compileSdk: whatever is newest via sdkmanager --list at build time.

neverForLocation decouples BLE scanning from the system Location toggle, but ACCESS_FINE_LOCATION is still requested separately, since the app independently wants to tag each sighting with GPS coordinates. Running scans from a foreground service means the while-in-use location grant is enough — ACCESS_BACKGROUND_LOCATION and its separate "Allow all the time" settings flow is likely avoidable, simplifying the permission UX.

NFC gotcha to remember

The foreground-dispatch PendingIntent must be FLAG_MUTABLE on API 31+, or tag delivery silently breaks. FLAG_IMMUTABLE — the usual post-Android-12 hardening default reached for everywhere else — is wrong here specifically, because the system needs to populate the actual Tag extra into the fired intent.

WiFi scanning is throttled by the OS, not by permissions

Roughly 4 startScan() calls per 2 minutes while foregrounded, near-zero while backgrounded. Realistic design: request a scan once per 30–60 second cycle, and also passively listen for scans Android triggers on its own for its own connectivity heuristics. True continuous WiFi visibility isn't achievable on stock, unrooted Android.

Battery

Duty-cycled BLE (SCAN_MODE_BALANCED, bursts every few minutes) and periodic balanced-priority location fixes, not continuous high-accuracy GPS. All-day operation is realistic with duty-cycling, but should be validated empirically; scan cadence is a user-facing setting. Samsung's One UI battery management is more aggressive than stock Doze and needs a manual, one-time exclusion (Device Care → Battery → Background usage limits) beyond the standard exemption API — an install-checklist item, not something the app can guarantee automatically.

08 · Build environmentWindows / Android Studio toolchain

Why this replaced the original Termux plan This section originally documented a Termux-on-tablet toolchain, including a real aapt2 architecture blocker (x86_64-only binary failing under Termux's aarch64 userland) and a hard wall around same-device APK installs without root. Switching development to Android Studio on a Windows PC eliminates both problems entirely rather than working around them — there's no architecture mismatch to patch, and ADB install (silent, from the Run button or the command line) is completely standard on a dev-machine-to-phone setup. This is the current, actual toolchain; nothing below needs a workaround.
  1. Install Android Studio (latest stable) from its official site. The installer bundles a matching JDK, the Android SDK, platform-tools, and the emulator/AVD manager — there is no separate cmdline-tools/sdkmanager bootstrap to do by hand, unlike the old Termux path.
  2. On first launch, step through the Setup Wizard: accept the SDK license, and let it install its default SDK platform, build-tools, and at least one system image for a Compose-capable emulator (a recent API level, arm64 or x86_64 depending on the PC's own CPU).
  3. Create at least one emulator (AVD) via Android Studio's Device Manager — this is what most Session 1–3 iteration runs against, with the Samsung phone reserved for real-radio (BLE/WiFi/NFC) and final validation work.
  4. On the Samsung phone: enable Developer Options (Settings → About phone → tap Build number 7 times), then turn on USB debugging under Developer Options. Connect it to the PC by USB cable, and accept the "Allow USB debugging?" RSA key prompt on the phone's screen the first time — or set up Wireless debugging (Developer Options → Wireless debugging → pair) if a cable is inconvenient for a given session.
  5. No gradle.properties escape hatches are needed — the aapt2FromMavenOverride and org.gradle.vfs.watch=false workarounds this section used to require were both specific to Termux's aarch64/bionic userland and don't apply on Windows.
  6. Build and run from either Android Studio's Run button (installs to whichever target — emulator or the phone — is selected in the device dropdown) or the command line: gradlew.bat assembleDebug from PowerShell/Command Prompt, or ./gradlew assembleDebug from Git Bash (Gradle's wrapper script itself is POSIX shell, so Git Bash can run the Unix-style invocation directly).

09 · Say the quiet partKnown infeasibilities / compromises

OS-level limit, not a permissions problem True continuous WiFi scanning is blocked by Android's own throttling regardless of what's granted; ~30–60 second effective resolution is the realistic ceiling on stock, unrooted Android.
Manual step required Samsung's One UI background-kill behavior needs a manual, device-specific opt-out beyond the standard Android battery-exemption API — there's no way for the app to set this for itself.
Real cost, not eliminated All-day BLE+WiFi+GPS scanning has a genuine, non-zero battery cost. Duty-cycle settings manage it but don't make it free.
Structurally hard case A daily "co-traveler" device (e.g. the same commute every day) is a hard case even for mature tools like AirGuard — v1 surfaces full sighting detail for the user to judge, rather than solving it algorithmically.

Spreading this across sessions This is the summary; build-plan.html breaks it into seven self-contained sessions — each ending at a point where something runs or, for the on-device ones, at a concrete verified behavior — so the actual build doesn't have to happen in one sitting.

11 · How this gets checkedVerification plan

This is native Android code that must run on real hardware to be honestly verified. The authoring sandbox this plan is written from has no Android SDK, emulator, or ADB link at all — but the actual Windows dev machine does, via Android Studio, so more of this can now genuinely run from a terminal there (Claude included) than was possible under the old Termux setup. Once scaffolded:

  • gradlew.bat test (or ./gradlew test from Git Bash) for the correlation-engine, clusterer, and signature-matcher JVM unit tests — no device needed, runs on the Windows PC directly
  • gradlew.bat assembleDebug, then install via Android Studio's Run button or adb install, onto either the emulator or the Samsung phone; confirm permission prompts appear correctly, the foreground-service notification shows, and the Nearby list populates with real BLE/WiFi results (the emulator can fake some of this but not real ambient BLE/WiFi — that needs the phone)
  • Manually place a known BLE tracker (or a phone advertising a similar payload) at 3+ physically distinct locations over time and confirm it gets flagged; confirm a stationary device (a home router) never gets flagged
  • Test the NFC screen on the Samsung phone (real tag read), and separately confirm the graceful "unavailable" state on the emulator, which has no NFC hardware at all — a built-in negative test rather than a second physical device
  • adb logcat for background-service reliability over several hours, including a screen-off/Doze period and an app-switch/backgrounding test, to confirm Samsung doesn't silently kill the service once battery exclusions are set
